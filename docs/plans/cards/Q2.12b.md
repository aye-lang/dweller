# Q2.12b: navigation fetches stop blocking the browser's window loop

- goal: with `DWELLER_PROCESS=tab` or `site`, and for Spaces hosted on renderers (`DWELLER_SPACES=renderer`), the browser answers a renderer's navigation `fetch` (`nav` set: a tab's, a frame's, a hosted Space's) without running the request to its end on the window's loop. A slow server no longer stalls input, painting and the other tabs (Q2.12 measured one loop iteration of 1502 ms in `window_spaces_responsive` with the switch on). Everything else stays: redirects, cookies and `Sec-Fetch-*` across them, Basic auth, the COOP/CORP/CSP/XFO checks on the response, the site lock, the process swap (`swap_to`/`primed`) and cancellation.
- source: Q2.12's Left, first item.
- design:
  - one held-fetch path (Q2.4e's `holdFetch` / `HeldFetch` / `answerHeld`), no second machinery. `answerFetch` now holds a navigation too (`holdFetch(..., navigates, ...)`, `HeldFetch.nav`); a non-`http(s)` URL, a replayed archive (`liveRequest` false) and a primed response (`sendPrimed`, after a swap) are answered at once, as before.
  - net: `net.startNavigation(target, req)` (`start-navigation.aye`) is a script request of the loader (`newRequest`, `startHop`, `finishRequest`) marked `nav`, with the synchronous `transfer`'s semantics where they differed from a background request: the chain's state across hops (`Hop`: the SameSite initiator, `crossed`, `Sec-Fetch-Site` from `none` or `same-origin` on, and the 32 MB document limit; `startJob` takes a `Hop`, loads and other requests pass a fresh one per hop, so they are unchanged), the initiator `Browser` and `user_activated` (`Sec-Fetch-User`, `hopRequest`), the SameSite initiator of a navigation without a referrer (the first URL after an HSTS or mixed-content upgrade, `navigationFrom`), Basic auth (`afterAuth` after each hop, one retry with the realm's credentials, the page's challenge noted for the login prompt; `retriesAuth`), the private-network record of a public page (`notePublicPage`) and the failure telemetry (`noteFailure`). `initiatorMayLoad` refuses before anything starts (0: the synchronous path then fails as before).
  - ui: when the held navigation lands, `finishNavigation` takes its response out of the load (`net.takeResponse`, owned, since `takesSwap` keeps it as `swap_to`) and `sendNavigation` does what `answerFetch` did after the blocking request: `framingRefused` (XFO, `frame-ancestors`) for a frame, `takesSwap` (site change, COOP), then `sendFetched` (the committed URL, COOP of the new document). A failure sets `nav_failed` and sends `fetch_fail` with the request's code (`requestFailure`), as before. The commit's site-lock check (`Loaded`) is unchanged.
  - the window picks up a swap set by a held navigation where it looked before: `serviceSpeculative` (tabs and hosted Spaces) and `serviceChildren` (OOPIFs) each round; the agent relay's blocking `askRenderer` now also calls `followSwap` after `answerHeld`.
  - cancellation: `fetch_cancel` of the id releases the held load (the transfer is aborted), and ending the renderer (`endTabProcess`: close, crash, hang stop) releases it too. The renderer still waits for its navigation document (Q2.4e left), so it sends neither meanwhile; it answers pings while it waits, so no hang is reported.
- references: Chromium (read over HTTPS from `main`): `content/browser/loader/navigation_url_loader_impl.cc` (`Start`, `OnReceiveRedirect`, `OnReceiveResponse` → `NotifyResponseStarted`, `OnComplete` → `NotifyRequestFailed`: the navigation's network request runs off the UI thread and only its results are posted back to it). Dweller takes: the navigation is a request the browser's loop starts and polls, and its response or failure is handled when the loop sees it. `content/browser/renderer_host/navigation_request.cc` (`OnResponseStarted`: COOP, the response throttles, then `SelectFrameHostForOnResponseStarted`): the order of `sendNavigation`'s checks.
- files: new `browser/net/{hop,hop-request,navigation-from,retries-auth,start-navigation,take-response}.aye`, `browser/ui/{finish-navigation,send-navigation}.aye`; changed `browser/net/{loader,multi}.aye`, `browser/ui/{answer-fetch,hold-fetch,held-fetch,finish-held,ask-renderer}.aye`; tests `tests/browser/window_renderer_loads.rs` (new `window_renderer_loads_slow_navigation`), `tests/browser/window_spaces.rs` (new `window_spaces_responsive_in_renderer`; `responsive_session` takes the environment and its own socket name, and both variants also check that loop iterations pass while B's navigation is out); `docs/process-model.md` §8.

## Status: done, 2026-11-09

Left:
- The renderer still blocks on its own navigation document (Q2.4e left): the old page does not run meanwhile, and Stop or a new URL typed during the fetch waits for it (`queueNavigate` waits while `loading`); Chromium cancels the `NavigationRequest` instead.
- The response is sent once the browser has all of it (no streaming of the document, Q2.4e left).
- The window polls held fetches every 2 ms, a navigation included (`HELD_POLL_MS`), instead of waking on libcurl's sockets.
- The DWELLER_TIMING record of a held navigation is `background_requests`, not `requests`.
