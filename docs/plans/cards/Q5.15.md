# Q5.15: print to PDF and `@media print`

- goal: a page prints to a PDF file, laid out for paper with its print styles, from the command line, from Cmd+P and from `window.print()`, in all three process modes. Row Q5.15 of `foundations.md` (F1; Chromium `components/printing/`, `core/paint/` (print), `core/page/print_context.cc`).
- facts found first (2026-11-16):
  - The media type `print` is always false (`css/media.aye`); no `break-*` property, no `@page` (the parser skips it), no `window.print`, no PDF code anywhere.
  - Layout has no fragmentation: a page is one tall column. The display list (`paint.Item`) has fills, quads, text runs (a string, a font, a baseline), images, SVG, clips, tiles, shadows and layers; text is drawn by FreeType and HarfBuzz into the canvas.
  - `paint.zlib` writes a zlib stream (the PNG encoder's), which is what PDF's `FlateDecode` reads.
  - A sandboxed renderer writes no file: its PDF has to cross to the browser.
- how it works: the page is styled with the media type `print` and laid out as wide as the paper's content box (A4 or Letter less 10 mm margins, at 96 CSS px per inch); the tall layout is cut into pages where no line of text, image or `break-inside: avoid` box is cut and where `break-before` or `break-after` force a page; each page is painted at 2 device px per CSS px (192 dpi) into an image; the PDF has one image per page and, over it, the page's Latin-1 text runs as invisible text (render mode 3, Helvetica), so the text can be selected and searched. Then the page gets its screen styles and layout back.
- slices (each with its verify):
  1. CSS: the media type (`css.setPrinting`), `break-before`, `break-after`, `break-inside` and the legacy `page-break-*` as keyword properties. Verify: slice 3's goldens (a rule in `@media print` applies, one in `@media screen` does not).
  2. `browser/print/`, pure: the papers, the page cuts of a display list (`pageCuts`), the PDF writer (objects, the cross-reference table, the image stream, the text layer). Verify: Aye unit tests (`aye test browser --module print`): cuts around lines and forced breaks, a PDF whose offsets and lengths are right.
  3. `dweller print FILE|URL -o OUT.pdf [--paper a4|letter] [--font fixed|system]` (the `--print-to-pdf` of Chromium): `beforeprint`, print styles, the pages, `afterprint`. Verify: `tests/browser/print.rs`: the page count, the media box, the text layer's strings per page, each page's image decoded and compared at a few pixels (a print-only block is there, a screen-only block is not), `matchMedia('print')` and the two events seen by the page.
  4. The window: Cmd+P and `window.print()` write `TITLE.pdf` into the downloads directory (`DWELLER_PRINT_TO` names the file, for tests) and say so in the status line. One process: the window prints its page. `DWELLER_PROCESS=tab|site`: IPC kinds 194 `Print{paper}` (B→R), 195 `Printed{chunk}`, 196 `PrintedEnd{pages}` (R→B), 197 `PrintAsk` (R→B, `window.print()`); the renderer makes the PDF, the browser writes the file. Verify: window tests in one process and with `DWELLER_PROCESS=site`: the same PDF bytes as `dweller print`.
- decisions (nobody to ask; the plan's defaults):
  - Pages are images with a text layer, not vector drawings: the display list's text is shaped by HarfBuzz with system or web fonts, and a vector PDF needs those fonts embedded as subsets. The image is what the screen would show, at 192 dpi. Left: vector text.
  - A4 by default (`--paper letter`, `DWELLER_PAPER=letter`): `@page { size }` is not read. Chromium takes the default from the locale.
  - Backgrounds print as the page has them (Chromium's "Background graphics" is off by default and needs `print-color-adjust`).
  - No preview and no system print dialog: the PDF is the output; the person prints it from the PDF viewer. Chromium has its own preview.
  - `page-break-before`, `-after`, `-inside` are longhands of their own here, not aliases of `break-*`: both force a page.
  - No headers and footers (title, URL, page number, date).
- references: PDF 32000-1:2008 (§7.5 file structure, §8.9 images, §9.3.6 text rendering mode); CSS Fragmentation 3 (https://www.w3.org/TR/css-break-3/); Chromium `components/printing/renderer/print_render_frame_helper.cc`, `third_party/blink/renderer/core/page/print_context.cc`.

## Follow-up: vector text (2026-11-19, lane feat-ui)

- goal: text in the PDF is drawn from glyph outlines, sharp at any zoom, and can be selected and searched in any script; everything else of a page stays the 192 dpi image.
- facts found first: `font.System.shapeText` gives the face and glyph id of each glyph; FreeType has every scalable face's outline (`FT_LOAD_NO_SCALE`), also for a face of a collection (`.ttc`, most of macOS's fonts), a weight instance of a variable font and a web font, which embedding the font file would each need more for (a rebuilt sfnt, an instancer, a subsetter). With `--font fixed` there is no font: the tests' boxes stay in the image.
- decision: the outlines go into PDF Type 3 fonts (PDF 32000-1 §9.6.5; what Skia's PDF backend falls back to for fonts it cannot embed): one font per 256 used glyphs of a face, each glyph a small content stream in 1000 units per em, a `ToUnicode` map from the text each glyph came from. No font file is embedded, so nothing is subset. Cost: no hinting (print does not want it) and one PDF object per glyph used.
- slices:
  1. `font.glyphOutline`: a glyph's outline as moves, lines and cubic curves (TrueType's quadratic ones converted), in 1000 units per em, with synthetic bold as the screen draws it. Verify: an Aye unit test on a test font's glyph (closed contours, the advance).
  2. `browser/print/`: which text runs are vector (a font system, not turned text, an opaque color, not inside a layer (opacity, filter, mask), every glyph has an outline, and nothing painted later overlaps the run); the image is rendered without those runs; the glyph book (face, glyph, bold -> font and code), the Type 3 font objects, the runs in the page's content stream after the image (`Tf`, `rg`, one `Tm` and `Tj` per glyph, inside the clip rectangles the run had). A vector run is not repeated in the invisible Helvetica layer. Verify: `tests/browser/print.rs` with `--font system` and a web font of `browser/tests/fuzz/font/`: the font objects, the glyphs' codes and places, the `ToUnicode` map, the image without the text's ink; a covered run and a translucent run stay in the image; `pdftotext` when poppler is there.
  3. The window (Cmd+P, `window.print()`), all three process modes: the same bytes as `dweller print` with system fonts. Verify: `window_print` with `--font system`.
