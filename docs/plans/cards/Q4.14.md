# Q4.14: CSS animation and transition checks visit only animated elements

- goal: `animatedElements` (the CSS animation hook's list) and `showTransitions` (after each full layout) stop walking the whole document. The style recalc keeps the set of elements with CSS animations or transitions, and both visit only that set. Events and computed values stay as before.
- cause: Q4.1 counted 18–22 ms per `animatedElements` call (youtube-search 2112 ms in 116 calls) and 5 ms per forced layout in `showTransitions` (zol). Both walked every node of the document.
- design (Blink: `CalculateAnimationUpdate`/`CalculateTransitionUpdate` run inside style recalc, `core/animation/css/css_animations.cc`):
  - `css.Styles` has two sets, `animating` and `transitioning` (`IntMap(u32, NodeId)`). `css/note-animated.aye` `noteAnimated` updates them where the cascade stores an element's values (`styleElement`, so both `computeStyles` and `restyleSubtrees`). An element is in `animating` when `animation-name` is not `none`. It is in `transitioning` when `transition-duration` or `transition-delay` is not the initial `0s`. This is a superset of `transitionsWanted`, which `showTransitions` still checks. An element leaves a set when a restyle drops the property. It also leaves when its index is styled again for another node.
  - `dom/in-tree-order.aye` `inTreeOrder` puts a list of nodes in document order, with no duplicates. It drops dead nodes and nodes outside the document's light tree, as the old walk did. It marks the nodes and their ancestors, then walks the document. It goes into marked subtrees only, so the cost is the nodes' ancestors and those ancestors' children.
  - `akAnimatedElements` returns `inTreeOrder(animating)`. `styledElements` (the full path of `showTransitions`) returns `inTreeOrder(transitioning + Transitions.before + Transitions.shown)`. This is the same set of elements the old walk's filter let through, in the same order. `animation.Shown` now holds its `el`, so a shown entry is still visited. The local path (restyled and moved elements) does not change.
- files: `browser/css/cascade.aye` (fields, call), `browser/css/note-animated.aye` (new) and `_test`, `browser/dom/in-tree-order.aye` (new) and `_test`, `browser/engine/ak-animated-elements.aye`, `browser/engine/styled-elements.aye`, `browser/engine/show-transitions.aye`, `browser/animation/shown.aye`
- verify: `aye test browser` (159 passed, including the 2 new tests), `aye check browser`, `cargo test --release --test browser -- anim transition window_ jsdom` → 0 with no golden changes, WPT, `check_taste.py` → 0.

Finding: the walks cost much less than Q4.1 counted, 0.3–1.4 ms for each `animatedElements` call and 0.07–0.27 ms for each `styledElements` call. Q4.1's 18–22 ms per call includes `geometry(s)`, the style and layout that `akAnimatedElements` forces. The hook runs after every task that changes the layout version (`afterTask` → `runAnimationHook`). On youtube-search, the hook makes 60 calls of 32–38 ms each in this run, against 19 frame relayouts. That forced layout is what keeps the idle CPU of youtube-search and zol over 5%. Blink updates CSS animations once per frame, inside the frame's style recalc. The next step is to run the hook from the frame's own layout (`afterLayout`) and not after each task.
