# Q4.7: a layout result cache keyed by the constraint space

## Status: done, 2026-11-19: the cache is not needed; one bug that repeated layouts is fixed

- goal (the integrator's row): first the measurement that says whether the cache pays. Under 5% of layout time in repeated subtree layouts on the perf pages: close as "not needed".
- what exists: `keepsLayout` (layout/block.aye) keeps a child's layout in an incremental relayout when its containing block is the same; `has_intrinsic` keeps a box's intrinsic widths; `relayoutAt` (layout/flex.aye) lays a stretched flex item out a second time only when its content can depend on its height (`heightDependent`: a flex or grid container, or a child with a percentage height).
- probe (a throwaway build, not committed): every `layoutContents` call timed; a call is repeated when the same box had its contents laid out earlier in the same pass (one `layoutRoot` or `relayoutUp`), and "same" when its width and the height of its containing block were equal too. Call sites tagged to see which pair repeats. A first version of the probe kept its maps in a tree's allocator and crashed or hung the browser partway; the numbers of the card's work-in-progress version (2026-11-17) came from those truncated runs and are replaced by the ones below, from runs that exit 0.

## Cause and fix

`heightDependent` asks `hasPercentChild`: has a child a percentage `height`, `min-height`, `max-height` or `flex-basis`? A text box shares its parent element's values (layout.aye, `Box.style`), so the text child of an item with `flex: 1` (`flex-basis: 0%`) answered yes with the item's own flex-basis, and every such item was laid out twice with the same width. `hasPercentChild` now skips text boxes (1 line, `layout/has-percent-child.aye`). An item with a real child of percentage height is still laid out again (`flex_text_items.html`: the 50% child of a 40px line is 20px).

After, with the probe: 0 repeated calls on all six pages (flex rows 1602 → 1202 calls, column flex 1352 → 1052, grid cards 2403 → 1803).

Without the probe, `browser/build.sh` safe, before = the wave tip aadc7134, the page's first layout (`layout` record of `dump --tree --js` with one `offsetHeight` read, 5 runs, ms):

The runs overlap (a shared 4-core machine); the medians fall 12%, 22% and 11%. `dump --layout` of the six pages is byte for byte the same with both binaries.

- WPT (before = the wave tip's binary): `css/css-flexbox` 4610/5816 (79.3%) and `css/css-grid` 11104/17578 (63.2%) before and after, no test whose result differs.
- files: `browser/layout/has-percent-child.aye` (1 line; shared with css-layout and css-writing); fixture `browser/tests/layout/flex_text_items.html` (`.layout`, the same output as the tip's binary).

## Decision

No layout result cache. After the fix nothing repeats a content layout with the same constraints on the perf pages, the layout fixtures or the six stress pages. What a cache keyed by the constraint space would still save is the relayout of items whose content does depend on their height (nested flex and grid containers, percentage-height children): there the second layout has another height, so a cache keyed by the constraints misses too; Blink's gain in that case comes from simplified layout, not from the cache.

## Left

- The intrinsic-size passes (`primeIntrinsic`, `intrinsic.aye`) were not counted: they lay out nothing, and `has_intrinsic` keeps their result per box, but a relayout clears it up the chain (`relayoutUp`).
- `heightDependent` is true for every flex or grid container that is itself a stretched item, whatever is in it (the column-flex page's growing item): the second layout is real work there.
- The probe is not in the tree (about 45 lines in six layout files and a file of counters).
