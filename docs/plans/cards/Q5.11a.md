# Q5.11a: IndexedDB 1: databases, object stores, transactions, in the browser process

- goal: `indexedDB.open`, `deleteDatabase`, `databases`, `cmp`; version
  upgrades with `versionchange` and `blocked` across pages and
  processes; object stores (`createObjectStore`, `deleteObjectStore`,
  `put`, `add`, `get`, `getKey`, `getAll`, `getAllKeys`, `delete`,
  `clear`, `count`), key paths and key generators; transactions
  (scopes, modes, the active flag, auto-commit, `commit`, `abort` with
  rollback); values by structured clone; saved in the profile. The
  data and the scheduling are in the browser process; a renderer asks
  over IPC. Indexes, cursors and the rest of `IDBKeyRange`'s users are
  Q5.11b.
- verify: WPT `IndexedDB` (`wpt.py run IndexedDB`), 5/1085 (0.5%)
  before; the Rust tests `indexeddb_*` in one process and with
  `DWELLER_PROCESS=site`.

## Design

Chromium keeps the backing store and the transaction coordinator in the
browser (`content/browser/indexed_db/`: `indexed_db_database.cc`,
`indexed_db_connection_coordinator.cc`, `indexed_db_transaction.cc`)
and the request, event and key-path work in the renderer
(`third_party/blink/renderer/modules/indexeddb/`). Dweller splits at
the same place:

- `browser/indexeddb/` (Aye, browser process): per storage key (the
  origin, prefixed by the partition) the databases, their versions and
  object stores, the records (sorted by key bytes), the connections,
  the open/delete request queue of each database, the transactions and
  when each may start, the undo log of a `readwrite` transaction, and
  the file in the profile. It knows nothing of JavaScript values: a key
  is a byte string whose byte order is the key order, a value is an
  opaque byte string, a name is an opaque byte string.
- `browser/engine/indexeddb/*.js` (renderer): the interfaces, argument
  checks and exceptions, key conversion and encoding, key paths,
  structured clone, requests and their events, the transaction's
  active flag and auto-commit.
- One call joins them: `ak.idb(request) -> reply`, both text, lines
  separated by `\n`, the first line the operation. It is synchronous
  (as `ak.storage`): the browser answers from its own state. What
  happens later (an open request's turn, `versionchange`, `blocked`, a
  waiting transaction's start) comes back as an event line for a client
  (a page): in one process a task of that page, across processes
  `IdbEvent`.
- IPC (lane range 160-189): 160 `Idb{doc, page, request}` (R to B,
  sync), 161 `IdbReply{reply}`, 162 `IdbEvent{page, event}` (B to R).
  The browser takes the origin from the document it committed (`doc`),
  checks the site lock as for `Storage`, and never reads an origin from
  the request. A client is (process, page id); a renderer that dies
  drops its clients (their transactions abort, their connections
  close).

Key encoding (ASCII, bytewise order = IndexedDB key order): number `b`
+ 16 hex digits of the big-endian double with the sign bit flipped (all
bits flipped when negative); date `c` + the same; string `d` + 4 hex
digits per UTF-16 code unit + `!`; binary `e` + 2 hex digits per byte +
`!`; array `f` + the items + `!`. `!` sorts below every hex digit and
tag, so a prefix sorts first.

Scheduling (`indexed_db_transaction_coordinator.cc`): a transaction
starts when no transaction created before it and not yet finished has an
overlapping scope with either of the two `readwrite`; a `versionchange`
transaction runs alone on its database (every other connection is
closed first).

Rollback: a `readwrite` transaction logs the record each write replaced
(and the key generator's old value); abort replays the log backwards. A
`versionchange` transaction keeps a copy of the database from before it
started; abort puts the copy back.

Persistence: with a profile, `<profile>/indexeddb/<origin>/<name>`
holds one database, rewritten whole (atomically) after a commit, at
most once a second, and at exit. Without a profile, and for an
isolated Space's partition, in memory only.

## Slices

1. Backend 1 (`browser/indexeddb/`): the request line format, storage
   keys, databases, connections, the open/delete queue (`upgradeneeded`,
   `versionchange`, `blocked`, `success`), `databases`, dropping a
   client. Verify: `aye test browser` (unit tests of the module).
2. Backend 2: object stores and records (`put`, `add`, `get`, `getAll`,
   `delete`, `clear`, `count`, the key generator), transactions (start
   order, commit, abort with undo, the `versionchange` copy). Verify:
   unit tests.
3. Front end 1: `ak.idb` and the event task in the engine; `IDBFactory`,
   `IDBRequest`, `IDBOpenDBRequest`, `IDBVersionChangeEvent`,
   `IDBDatabase`, events that bubble request -> transaction ->
   database, key conversion and `cmp`. Verify: `indexeddb_open` (Rust,
   `dump --js`).
4. Front end 2: `IDBTransaction` (active flag, a microtask checkpoint
   after each listener, auto-commit, `commit`, `abort`, an exception in
   a listener aborts), `IDBObjectStore`, key paths, key generator,
   structured clone, `IDBKeyRange`. Verify: `indexeddb_store`,
   `indexeddb_transaction`.
5. Processes: messages 160-162, the renderer's hook, the browser's
   answer with the site-lock check, events to the right renderer, a
   dead renderer's clients dropped. Verify: `window_renderer_indexeddb`
   with `DWELLER_PROCESS=tab` and `site`; the forged-origin kill test.
6. The profile: load on first use, save after commit. Verify:
   `indexeddb_profile` (two runs on one profile).
7. WPT: run the area, fix the largest one-cause clusters that belong to
   this row, record the score and the baseline.

## Status: done, 2026-11-16

Done note:
- All seven slices. `browser/indexeddb/` (backend, 97 files),
  `browser/engine/idb/*.js` (front end, 8 files), the natives `ak.idb`,
  `ak.idbHandler`, `ak.idbFresh`, `ak.checkpoint` in `engine/`, the IPC
  path in `ipc/`, `renderer/` and `ui/`.
- As built, beyond the design above: an open request that upgraded
  stays at the head of its database's queue until the page has fired
  its `success` or `error` (`opened`), so a later request's
  `versionchange` finds the handler the page sets in `success`. A
  request or reply over 256 KiB goes in parts (`more`). A transaction
  with an empty request list is `committing` as soon as its last event
  was dispatched, and finishes in a later task (after a 0 ms timer set
  in that handler, as in Chromium). The saver skips a database that has
  a live `readwrite` or `versionchange` transaction, so a file never
  holds uncommitted writes.
- Decisions: `wpt_areas.json` gets the area `IndexedDB` (threshold 0)
  so `wpt.py fetch` checks the tests out; the baseline is
  `tools/conformance/IndexedDB.json`. `file:` pages share one area
  (`file://`), as `localStorage` does.
- Changes outside the lane's files, each small: `engine/prelude.aye`
  (a listener added by an `on*` handler no longer runs for the event
  being dispatched; `ak.dispatchAlong`, `ak.defineHandlers`; `Blob` and
  `File` have a `toStringTag`), `engine/workers/wire.js` (`Blob`,
  `File` and BigInt objects clone; `encode` and `decode` exported),
  `js/lib.aye` (`__defineGetter__`, `__defineSetter__`,
  `__lookupGetter__`, `__lookupSetter__`: WPT's `support.js` needs
  them), `engine/script.aye` (the cleanup after a microtask
  checkpoint).
- Measured: WPT `IndexedDB` 5/1085 (0.5%) -> 502/1370 (36.6%);
  `cargo test --release --test browser` 269 passed after the merge of the wave branch (6 new:
  `indexeddb_open`, `_store`, `_transaction`, `_versions`, `_profile`,
