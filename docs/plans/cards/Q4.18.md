# Q4.18: what relayouts mistral each frame

- goal: find what starts the relayout and restyle of each mistral idle frame (Q4.17 left: 32.5 ms a frame, of it the rAF script about 29 ms and relayout + style 7.3 ms). If canvas draws bumping the DOM version (`canvasChanged`) start it, make a draw mark only the canvas's paint dirty; if something else starts it, fix that only when the fix is small and clear, else write it here and stop.
- profile: `browser/build.sh` (safe) build of `origin/q4-17-canvas2d-cost` f713802, mistral replay, `window_perf.py idle` with `DWELLER_TIMING=1 DWELLER_LAYOUT_WHY=1 --log`, every build and run through `scripts/capped.sh` (`target/q418-prof-*`). Three throwaway builds, none committed:
  - `dweller-exp`: `canvasChanged` returns at once (no DOM version bump from any canvas draw). Per 10 s: iterations 305, relayouts 355, dirty layouts 307; the before build: 308, 354, 310. Every record count of the whole run is the same within 1% (`ui_relayout` 438, `paint_build` 2688 → 2694, `restyle` 567 → 568, `layout_dirty` of the main page 394 → 391). The canvas bump does not start the relayouts: the canvas is in the `visual-intelligence` iframe, and the tab is laid out each frame anyway.
  - `dweller-dbg`: `restyleSubtrees` logs each root. Every frame restyles one element of the main page: `<p class="text-button-small … js-label">` (363 of 363 loop iterations).
  - `dweller-dbg2`: logs `textContent` writes that give an element the text it already has, and each `MutationObserver.observe`. `0%` is written to that `<p>` 358 times: the reading-progress widget of `_astro/layout…js` (`class Ad`, `update = () => { this.label.textContent = \`${e}%\` }`) runs each animation frame and writes the same `0%` at scroll 0. The page has five observers (three `childList` + `subtree` on `BODY`).
  - Per steady frame (frames 60 to 363, medians): loop 28.7 ms, `ui_raf` 28.4 (the timers 23.4, of them `canvas_draw` 8.0), `ui_relayout` 5.0 (mean 7.5). Inside `ui_relayout`: `paint_build` 4.1 ms (6 builds: the main page about 2.9 ms, the 5 iframes the rest), `images` 0.8, `paint_sig` 0.3. The style and layout work itself is small: `restyle` 0.04 ms, `layout_dirty` of the main page 0.09 ms, `script_layout` 0.15 ms.
- cause: the page's script replaces the text of one `<p>` with the same `0%` each frame. `nodeSetTextContent` removes the old Text node and appends a new one, the DOM version moves, and the window runs `relayout`: the restyle and the dirty layout of the one `<p>` are cheap (0.13 ms), but `buildList` then builds the display list of the whole tab again (`paint_build` of the page and of all 5 iframes, 4.1 ms) and re-signs it. The 7.3 ms "relayout + style" is a display-list rebuild after a one-text-node change.
- design: no code change.
  - The canvas fix is not the cause on mistral (`dweller-exp` above), so it is not made here.
  - Blink skips a `textContent` write when the element's only child is a Text node with the same non-empty data and the document has no mutation observers (`Node::setTextContent`, crbug.com/41095015). Mistral has observers on `BODY` with `childList` + `subtree`, so Chrome also replaces the node and queues records on this page; the same skip in Dweller would not apply here, and skipping it with observers present would drop records the spec requires.
  - The fix that would cut the 4.1 ms is to rebuild only the part of the display list whose boxes changed (Blink: `PaintController` reuses the cached display items of every layout object not marked for paint invalidation) or at least to keep the display lists of frames whose tree did not change. Neither is small; it is the next card.
- files: `docs/plans/cards/Q4.18.md` (new), `browser/engine/PERF.md` (a dated result).
- Chromium files read: `third_party/blink/renderer/core/html/canvas/html_canvas_element.cc` (`DidDraw`: `SetShouldCheckForPaintInvalidation` and `SetHasCanvasInvalidation`, no style or layout), `third_party/blink/renderer/core/layout/layout_html_canvas.cc` (`InvalidatePaint`, `SetNeedsLayout` only on a size change), `third_party/blink/renderer/core/dom/node.cc` (`setTextContent` same-text skip). Dweller takes: a canvas draw should only invalidate the canvas's paint (for a page whose only change is a canvas, see left), and the same-text skip only without observers.
