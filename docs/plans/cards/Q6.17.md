- cause fixed: the first row. A `ValidityState` flag says whether the control suffers from that condition, whether or not it is a candidate for constraint validation; being barred only keeps the control out of `checkValidity()`, `reportValidity()`, submission, `:valid`/`:invalid` and `validationMessage`.
- design:
  - `dom.validityOf` no longer returns early when `willValidate` is false. `valueMissing` of a text field (`textarea`, an `input` of a text, number or date type) needs the control to be mutable (not disabled, not `readonly`); a checkbox, radio button, file input or `select` is missing its value whether or not it is disabled (the expectations of `form-validation-validity-valueMissing.html`; Chromium's `TextFieldInputType::ValueMissing` and `HTMLTextAreaElement::ValueMissing` check `IsDisabledOrReadOnly`, the checkbox, file and select ones do not).
  - new `dom.failsValidation(doc, el)`: a candidate that does not satisfy its constraints. The three callers that relied on the early return use it: `engine.validate` (`checkValidity`, `reportValidity`, submission), the `:valid`/`:invalid` of a `form` or `fieldset` (`css/selector.aye`), and the invalid state of the accessibility tree (`agent/a11y.aye`). The `:valid`/`:invalid` of a control was already gated on `willValidate`.
  - `dom.validationMessage` is the empty string for a control that is not a candidate.
- references: https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#the-constraint-validation-api , `#check-validity-steps`, https://html.spec.whatwg.org/multipage/input.html#the-required-attribute ; chromium: `third_party/blink/renderer/core/html/forms/html_input_element.cc` (the flags call the input type with no `willValidate` check), `listed_element.cc` (`IsNotCandidateOrValid`), `text_field_input_type.cc`, `html_text_area_element.cc`, `checkbox_input_type.cc`, `file_input_type.cc`.
