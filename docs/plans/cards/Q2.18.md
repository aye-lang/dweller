# Q2.18: the window holds a renderer's fetch of an upgraded http image

- goal: in site mode the window never runs a renderer's fetch to the end on its own loop. On zol (live) it fetched the page's http images synchronously (`net.request` in `answer-fetch.aye` when `holdFetch` returned false): `ui_loop` froze for 0.4 to 2.9 s, every tab and the UI with it, the navigation document's held load could not move, and the first paint came late (W8 gap up to 1097 ms, P1.S8).
- source: the W8 report of P1.S8 (zol section): 10 `net_sync` "request" records in each sample, for `2[a-d].zol-img.com.cn/manu_photo/*`, inside the long `ui_loop` records.
- cause:
  - the page is https, and its 10 `manu_photo` images are `http://` (`<img src="http://2b.zol-img.com.cn/manu_photo/613.png">` in the archive's document; its other 1,079 images are `https://`). Mixed content upgrades an http image to https (`secureHref`).
  - `startLoadAs` refuses a URL that `secureHref` would change (`securedAsIs`), so that the cache key of the load is the key of the URL that net really fetches. It returned 0, `holdFetch` returned false, and `answerFetch` ran the upgraded request synchronously.
  - evidence: a temporary log in `holdFetch` on main, one live zol run (3 samples): every false return for an image that reached the network was `load == 0` for an `http://2[a-d].zol-img.com.cn` URL (20, 20 and 11 such returns in the 3 samples, the 10 images asked again; 10 `net_sync` "request" records in each sample). No `Failed` return. The `Done` returns were https URLs with a fresh cache entry (answered from memory, no network record). The candidates "a stale entry makes `cache.has` true" and "a failed load is joined" are not the cause: `has` is true only for a usable entry (`usableEntry`), and no load was `Failed`.
- fix:
  - new `net.startSecuredLoad` (`browser/net/start-secured-load.aye`): `startLoadAs` for the URL as net sends it (upgraded; 0 when mixed content blocks it). `holdFetch` uses it for a subresource GET. The held fetch is answered as before by `net.request` with the asked URL, which upgrades it and finds the load's response in the cache, so CORS, ORB, mixed content and cookies stay those of the synchronous path.
  - `holdFetch` answers at once only a load that is done (in the cache). A load that is `Failed` (an earlier load of the same URL that failed, or a transfer that failed at its start) is held too, and `finishHeld` answers `fetch_fail` without a retry on the loop, as the engine's rule for a failed held load says.
  - the checks of `answerFetch` (id, flags, doc, kind, method, top, referrer, headers) are unchanged and run before the hold.
  - `docs/process-model.md`: a paragraph "Upgraded subresources (Q2.18)".
- test: new `net::window_renderer_upgraded_images_held` (`browser/tests/hsts/upgraded-images.html`, `/slow.gif` of `hsts_server.py`, 2 s): an https page with three http images of its own TLS port, in `DWELLER_PROCESS=site` (set by the test, so it is the same in the single-mode run). The images load (`images: 3 loaded`); no `net_sync` request; every `ui_loop` under 100 ms; `ui_first_paint` under 2 s. On main's sources it fails: `longest ui_loop 6049 ms, first paint 6129 ms, 3 net_sync requests`. With the fix: `longest ui_loop 6 ms, first paint 75 ms, 0 net_sync requests`.
- numbers (macOS arm64, `browser/build.sh` safe build, `window_perf.py report --live --chrome --site zol` through P1.S8's wrapper that keeps each sample's log; one site at a time):

## Status: done, 2026-11-25

Left (the other `net.request` calls reachable from a renderer's messages in `browser/ui/`):
- `finishHeld` answers a held subresource with `net.request`, a cache hit. It reaches the network only when the entry is gone: a `no-store` response is kept once (`once`), so a second held fetch that joined the same load finds nothing and fetches again on the loop; an entry evicted in between does the same. Not seen on zol (0 `net_sync` requests after the fix). A fix keeps the response in the load for its users.
- `answerFetch` still answers synchronously what `liveRequest` refuses: `file:`, `data:` and other schemes (no network), a replayed archive (`DWELLER_REPLAY`, disk), and `DWELLER_RECORD`, where every request runs on the loop (a tool mode).
- single mode (`DWELLER_PROCESS=single`) still fetches an upgraded http image synchronously on the window's loop: the engine's `loadedInBackground` takes `startLoad`'s 0 as "loaded". Starting the load under the upgraded URL there needs the load to keep the page's URL for `loadHeld`, `loadOf`, `loadFailed` and `failedHref`, so it is not done here.
- a cold first sample can still have one long `ui_loop` with no network record in it: 594 ms (after run 1), and before the fix too (520 and 131 ms in P1.S8, 116 ms today). Each one comes as the renderer parses the document (`html` record), then sends its image fetches (about 1,090 on zol) in a burst. This is probably the window answering that burst in one iteration (each `startLoadAs` pumps the multi handle). It is not measured further; it needs a record around `pollTabProcesses`.
