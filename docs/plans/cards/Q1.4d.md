## #385 `window_renderer_popup_opener` (tab mode: "renderer gone crashed")

- CI (queue run 44987415404, macOS 1/3): the same-site popup's tab shows `renderer 21173 gone crashed`, `renderer-tabs 21173 21173`, no `renderer-frame`, stderr empty.
- reproduced: the test's first window (`DWELLER_PROCESS=tab`, `click:50,62`, the test server) run directly, 4 at a time: 5 of 400 (shared load), 0 of 400 (load about 10); the counts that decide, `main`'s build: 9 of 1200 (load 5 at the start, 12 busy loops, interleaved with the fixed build's runs).
- not a process crash. With logging in both processes: the renderer read end of file on the popup's socket (`fd 4`, the one `attach_tab` gave it) before it read anything there, while the browser's end (`fd 8`) was open; the browser then read end of file and called the tab crashed. The browser closed its copy of the renderer's end right after `sendmsg`, while the socket was still in transit in the opener's connection. XNU's garbage collector of in-flight descriptors (`unp_gc`, run when any process closes a Unix socket while descriptors are in transit) can take a socket whose only reference is such a message for garbage and flush it (`sorflush`): its receiver then sees end of file. Chromium works around the same kernel bug (`mojo/core/channel_posix.cc`, crbug.com/298276: the sender keeps the descriptors until `HANDLES_SENT_ACK`). A quick check first (shared load, 12 busy loops, interleaved): a build that never closed its copy 0 of 1200, the same build closing it 9 of 1200.
- fix: the renderer answers `attach_tab` with `attach_taken` (75, R→B, no fields) as soon as it holds the socket; the browser keeps each socket it sent (`TabProcess.attach_ends_sent`) until that answer and closes the rest when the opener's record ends (`ui/send-attaches.aye`, `ui/renderer-sent.aye`, `renderer/answer-all.aye`). A refused attach still ends with end of file on the popup's socket, as before.
- found on the way: every renderer that had served a popup crashed at exit (`EXC_BAD_ACCESS` at `0xdddd...`, 25 crash reports in 40 s): `endTab` destroyed the last tab and left `store_renderer` and the four other hooks' renderers pointing at it, and `serveOn`'s deferred `dropOpenedContexts` sent the popup's `sessionStorage` drop through it. Not seen by the tests (it comes after `--state`). `endTab` now clears them when no tab is left (`serveAs(null)`); 0 crash reports in the runs after.
- after (load 5 at the start, 12 busy loops): the window directly 0 of 1200; the test with `cargo test --exact` 20 of 20 under 8 busy loops (load 20 at the start, 150 at the end from other work on this Mac).

## #380 `window_frame_lists_reused` ("3 frames built the changing iframe")

- CI (queue run 44963994657, macOS 3/3, site mode): `[5, 2, 0, 4, 0, 4, 2, 2, 0, 4, 1, 1, ...]`: three window frames with the two lists of a tick of iframe `b` (5 wanted), three with four, each beside one with none.
- reproduced: the test's window (`frame_lists.html`, its environment and arguments) run directly, 6 at a time: 2 of 200 (shared load), there with the top's ticks crowded instead: `[..., 1, 1, 7, 2, 0, 1, ...]`, 12 frames of 1 (20 wanted).
- cause, in the test: it counted `paint_build` records per window frame (`ui_draw` ends one), and with a renderer the ticks are not the window's frames. The renderer runs a page's animation frame ticks on its own clock (`r.frame_ns`); a tick that paints nothing (the top writes the text it has) does not wait for the window to draw, so a loaded window frame holds several ticks or none, and the two processes' records reach stderr in arrival order. Counted per tick (from one `ui_raf` record to the next), the same 200 runs' stderr gives `[3, 2 x 10, 1 x 30]` in every one, the 2 failing ones too: the page's lists were built as the test wants each time. In one process a tick is a window frame, so there the count is the same as before (`[5, 2 x 9, 1 x 30, 0]`).
- fix: `window_frame_lists_reused` counts per tick (`builds_per_tick`), with the same bounds.
- after: `cargo test --exact paint::window_frame_lists_reused` 20 of 20 under 8 busy loops (load 18 at the start, 167 at the end from other work on this Mac).
