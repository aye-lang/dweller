# Q4.14b: the CSS animation hook runs once per rendering update in the window

- goal: in the window, CSS animation and transition discovery (`runAnimationHook`, the prelude's `cssAnimations.discover(); watchTransitions()`) runs once per rendering update, after the frame's layout, and not after every task. `dump`, `wpt` and the agent keep their point. Events, their order and computed values stay as before.
- cause: Q4.14 found that `afterTask` called the hook after every task that moved the layout version, the geometry or the started transitions, and each call forced style and layout (`akAnimatedElements` → `geometry`). The update-the-rendering steps of HTML update animations once per rendering opportunity, and Blink computes the CSS animation updates in the frame's style recalc.
- design (spec: https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering; Blink: `DocumentAnimations::UpdateAnimationTimingForAnimationFrame`, `PageAnimator::ServiceScriptedAnimations`, `CSSAnimations` updates in style recalc):
  - `afterTask` calls `runAnimationHook` only when the page is on the virtual clock (`!s.real`: `dump`, `wpt`, the agent). There, the point stays after each task, so the jsdom and dump goldens do not change.
  - On the real clock (the window), the only call is `afterLayout`, which the window's `relayout` calls after `layoutPage`. `afterLayout` now also visits the pages of the frames, which before had their hook called only from `afterTask`. A task, a rAF callback or an input event that changes styles moves `treeVersion`, so the window lays out (`afterScripts` → `relayout`) in the same loop iteration, and the hook runs after that layout and before the next iteration's rAF callbacks.
  - Forced style reads did not depend on the hook, and they still do not: `getComputedStyle` (`styleOf` in the prelude) already calls `cssAnimations.sync(el)` for the element it reads and `watchTransitions()`, and `computedStyle` starts transitions through `geometry` → `restyleTransitioning`.
  - The hook after the window's layout finds the geometry current (`layoutShared` laid out through it), so it does not lay out again.
- files: `browser/engine/script.aye` (`afterTask`), `browser/engine/after-layout.aye`, `docs/plans/cards/Q4.14b.md` (new)
- verify: `aye test browser` (165 passed), `aye check browser`, `cargo test --release --test browser -- anim transition window_ jsdom dump` → 0 with no golden changes (see Tests below), WPT `css/css-animations` and `css/css-transitions` do not drop, `check_taste.py` → 0.

Tests: the `anim transition window_ jsdom dump` run had 70 passed and 2 failed. `window_webgl` failed because ANGLE was not in this worktree (`fetch_angle.sh` fixed it). `window_spaces_watch` failed on its `loop_max_ms < 50` (77 ms, on a loaded machine). Finding: on Q4.14's head the hook's stamp already let through about one call per relayout (20 calls for 20 relayouts on youtube-search, not Q4.1's 60), so the number of calls does not drop much. What changes is the cost of a call: it ran after the task, before the window's layout, and so did that layout itself (52 ms per call on youtube-search). Now it runs after the layout and costs under 0.1 ms. The layout moved into `relayout` and is still done once per frame, so the idle CPU drops only 2 points on youtube-search (42% → 40%). What keeps youtube-search at 40% is 12–19 full layouts (`layout_full`) in 10 s idle, one per relayout; zol and mistral do dirty layouts each frame (93 and 200 in 10 s) from their own page scripts. The next step is to find what makes youtube-search lay out the whole document each frame.
