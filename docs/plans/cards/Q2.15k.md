# Q2.15k: the clipboard outside text fields

- goal: fourth item of the lane's second list [Q2.3f Left: "the clipboard works on text fields only"]. With no text field or editable in focus, Cmd/Ctrl+A and Cmd/Ctrl+C did nothing, in the window's process and in a renderer: the key was dropped when the document had no focused element, and `editHost` acted only on a `contenteditable` host.
- design: `engine.editHost` picks its target with `editTarget`: the focused editing host as before; a focused text field is left to the field code; otherwise `copy` and `selectall` go to the document element. The prelude's existing editing code does the rest: `selectall` selects the body's contents (`editing.js`), `copy` fires a `copy` event and writes the selection's text through the clipboard hook (`editing-clipboard.js`), which in a renderer is the `clipboard_write` message the browser already checks. Cut, paste, undo and redo still need an editable.
  - callers: the renderer's `editCommand` asks `editHost` before it looks for a focused field; the window's key handler passes a Cmd key with no focused element to `hostCmdKey`.
- no new message, no change to the browser's checks.
- spec read: https://w3c.github.io/clipboard-apis/#fire-a-clipboard-event (the target is the focused editable, else the body or document element); Chromium `third_party/blink/renderer/core/clipboard/clipboard_commands.cc` (`ExecuteCopy` works on any selection).
- files: `browser/engine/edit-host.aye`, new `browser/engine/edit-target.aye`; `browser/renderer/edit-command.aye`; `browser/ui/forms.aye` (six lines); new `browser/tests/ui/page-copy.html`; `tests/browser/window_renderer_limits.rs`.
- verify (2026-11-19, Linux x86_64): `window_renderer_limits_page_copy`, in the window's process, with `DWELLER_PROCESS=tab` and `=site`: Cmd+A, Cmd+C, a click into the field, Cmd+V: the page got `copy` (its title starts `Copy copy`) and the field holds `alpha beta`. Before the change nothing was copied. The whole suite and checks: below.
