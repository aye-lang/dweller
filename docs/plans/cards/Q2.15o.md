# Q2.15o: `MessagePort` transfer across renderers

- goal: readiness list for Q2.14, "Logins and popups", third bullet [Q2.11]: "No `MessagePort` transfer across processes". A `postMessage` to a window in another renderer (a cross-site frame, an opener or a popup) threw `DataCloneError` when its transfer list had a `MessagePort`. Sign-in widgets and embeds set up their channel exactly so. Now the port arrives as `event.ports[0]`, and the channel carries messages both ways between the two processes.
- design:
  - script (`engine/remote-windows.js`, `engine/workers/wire.js`): `remotePost` takes the ports of the transfer list (each must be open, still entangled in this page and not already remote, else `DataCloneError`), gives each a key from a counter of the renderer process (`newPortKey`), encodes a port inside the data as `{t:'P', i}` (its index in the list) and sends the keys with the message. The port that stays is bound to `(0, key)` ("the channel I own"), the moved one is closed. The receiver makes a `MessagePort` per key bound to `(sender's tab, key)`; these are `event.ports` and the ports inside the data (the same objects). A bound port's `postMessage` goes to the browser (`portSend` → `postPort`), and a message for it is delivered as a `message` event on the port (`MessagePort._deliver`, now shared with the in-page path). The wire's port encoding is used only when the host offers it, so worker messages reject ports as before.
  - IPC: `post_message` (51) and `message` (52) carry a trailing `ports` (decimal keys, comma separated). 93 `port_post{tab, key, data, buffers}` R→B and 94 `port_posted{tab, key, data, buffers}` B→R: `tab` is 0 on the owner's side and the owner's tab id on the holder's side.
  - browser: `openPorts` records a channel per key when it routes 51: `PortChannel { tab, key, owner, holder, holder_tab }` (the owner's tab id and process serial, the holder's). At most 16 ports per message (more, or a key that is not a number: `bad post_message`), at most 4096 channels (the oldest goes). `routePortMessage` forwards 93 only between the two ends of the named channel (`portPeer`: the sender must be the recorded owner, naming tab 0, or the recorded holder, naming the owner's tab); anything else is dropped. The ends are found by serial and tab, so a channel does not follow a tab into another process. `forgetPorts` drops a process's channels when it ends.
  - renderer: a received message's keys are noted on the target script at once (`notePorts`), before its task runs, so a channel message that arrives in the same read is not lost; `deliverPortMessage` finds the script that has the port (`scriptWithPort`, the root or a frame).
- decisions: a port travels one hop (a bound port cannot be transferred again: `DataCloneError`); messages on a channel carry data and ArrayBuffers but no further ports; closing or collecting a port does not tell the other side (Chromium closes the pipe). Each is in Left.
- Chromium read (over HTTPS from `main`): `third_party/blink/renderer/core/messaging/message_port.cc` (`Entangle`, `postMessage`, `Accept`), `third_party/blink/public/common/messaging/message_port_channel.h` (a transferred port is one end of a pipe handed to the other process). Taken: the port's identity is a handle the browser routes, and only its two holders can use it. Not taken: Mojo pipes with direct process-to-process delivery; here every message goes through the browser.
- found on the way: the tests build their own binary with `--leak-check`, and its leak report crashed with SIGSEGV instead of printing (a compiler-side bug in the report's format arguments; the leak was this card's channel list, now freed when it empties). Not reported upstream yet.

## Status: done, 2026-11-16

Left:

- A bound port cannot be transferred again, and a channel message cannot carry ports.
- A closed or collected port is not reported to the other process; its channel stays in the browser's table until either process ends or 4096 newer ones push it out.
- In one process, `window.postMessage` still clones by JSON and ignores the transfer list, so a port is not transferred there (the two modes differ; the default flips to `site` with Q2.14).
- Only tested between an opener and its popup; the same code path serves a cross-site frame and its parent (51 with a `key`), with no test of its own.
