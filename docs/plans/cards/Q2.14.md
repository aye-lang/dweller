# Q2.14: `DWELLER_PROCESS=site` becomes the default

- goal: with no `DWELLER_PROCESS` the browser runs each site's pages in a sandboxed renderer of their own, cross-site iframes too; the window's own process stays for debugging only, as Chromium's `--single-process`.
- source: row Q2.14 of `foundations.md`; the readiness list (Q2.15, Q2.16) and the suite's count (Q2.14h: 377 / 377 with the flag) are done.
- design:
  - `ui/process-mode.aye`: `processMode()` is `single` or `tab` when `DWELLER_PROCESS` says so, else `site`; `inRenderers()` is every mode but `single`. The four places that read the variable (`ui/window.aye` `tab_processes`, `ui/site-frames.aye`, `ui/start-tab-process.aye` `--site-frames`, `main.aye` for `agent` and `mcp`) ask these.
  - `--single-process`, anywhere among the arguments, sets `DWELLER_PROCESS=single` and is taken out of them (`ui/take-single-process-flag.aye`), so `dweller URL --single-process` and `dweller --single-process agent ...` both work.
  - tests: the arms that meant "the window's own process" by removing the variable now set `single` (`window_renderer_limits.rs`, `window_renderer_oopif_site.rs`); `paint.rs`'s caret check asks "not `single`". New `window_renderer::window_process_default_and_single_flag`: with no variable a `file:` page has a renderer of site `file:`; with `--single-process` there is no renderer line.
  - CI: the daily `site-mode` run (flip readiness) becomes `single-mode` (`.github/workflows/single-mode.yml`, `.github/scripts/mode-shard.sh`): the whole suite with `DWELLER_PROCESS=single` every day, so the debug mode stays whole (decision 9 of `docs/process-model.md`). `browser/tools/scoreboard.py` reads it. The required `browser` shards (Ubuntu and, in the queue, macOS) now run the default, site mode.
- Chromium read: `content/public/common/content_switches.cc` (`kSingleProcess`: "Runs the renderer and plugins in the same process as the browser"), `content/browser/renderer_host/render_process_host_impl.cc` (`run_renderer_in_process()`, for tests and debugging). Dweller takes: one switch, off by default, that keeps the same interfaces in one process.
- files: new `browser/ui/{process-mode,take-single-process-flag}.aye`; `browser/ui/{window,site-frames,start-tab-process}.aye`, `browser/main.aye`; `tests/browser/{paint,window_renderer,window_renderer_limits,window_renderer_oopif_site}.rs`; `.github/workflows/single-mode.yml` (was `site-mode.yml`), `.github/scripts/mode-shard.sh` (was `site-mode-shard.sh`), `browser/tools/scoreboard.py`; `docs/process-model.md` §3 and decision 9, `docs/browser.md`.
- verify (2026-11-21, Linux x86_64, 4 cores, on top of Q2.14h):
  - `aye check browser`, `check_taste.py`, `check_layers.py`: exit 0.
  - `cargo test --release --test browser` with no `DWELLER_PROCESS` (now site mode): 379 passed, 0 failed (`target/flip1.log`).
  - with `DWELLER_PROCESS=single`: 379 passed, 0 failed (`target/single1.log`).
  - the merge queue's macOS shards run site mode for the first time with this card.
