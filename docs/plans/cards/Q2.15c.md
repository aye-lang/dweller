# Q2.15c: tab and site mode check the initiator's sandbox flags

- goal: readiness list for Q2.14, "Security (X1)", third bullet [Q3.9]. Q3.9 and Q3.9b enforce the iframe `sandbox` flags in the in-process window and left "tab mode: the browser-side navigation must check the initiator's flags". This card states what is checked where in the renderer modes, adds the browser's checks where the browser knows the flags, and tests both.
- what was found:
  - a frame in its embedder's renderer (every frame in `tab` mode, a same-site frame in `site` mode): the engine's checks run in that renderer. A person's click on a link or form goes through `renderer/follow-frame-link.aye` and `submit-in-frame.aye`, which call `sandboxAllowsTarget` with activation (added after Q3.9b); scripts go through the engine's `Location` and `window.open` checks. The browser cannot check these: `begin_navigation` does not name a frame, and the renderer that would state the flags is the one the flags restrain. No test ran them in a renderer mode.
  - a cross-site frame in a renderer of its own (`site` mode): the browser knows its flags (the parent's `subframes` record, sent on in `frame_owner`, kept in `TabProcess.sandbox`). `proxy_navigate` was already checked against them (Q2.11, `proxyNavigationAllowed`) and `post_message` origins too (`targetOriginMatches`). Not checked: a POST navigation of the frame itself without `allow-forms`, and cookie and storage requests without `allow-same-origin` (the frame's origin is opaque, but its renderer is locked to its site, so the site-lock check passed them).
- design (`ui/child-sent.aye`, `ui/sandboxed-child.aye`): for a child renderer whose flags have the bit, `begin_navigation` with `post` kills it (`form in a sandboxed frame`); `cookie_get` and `cookie_set` kill it (`cookie in a sandboxed origin`); `storage` with an op on an area (0 to 5) kills it (`storage in a sandboxed origin`). The honest engine never sends these: `dispatchSubmit` and `submitForm` stop without `allow-forms`, `document.cookie` and Web Storage throw `SecurityError` without `allow-same-origin`. The flags are the ones of the last `frame_owner`, which are the ones the child's engine applies (`load-shared.aye`).
- decisions: popups of a child renderer are not checked, because the browser drops a child's `context` messages today (popups across renderers are the proc-spaces lane; `allow-popups` belongs with that work). `alert`, `confirm` and `prompt` do not cross to the browser in a renderer mode, so `allow-modals` has nothing to check. A GET form submission is not told from a link navigation of the frame itself, which the sandbox allows.
- test hooks (`renderer/send-sandbox-evil.aye`, with `DWELLER_TEST=1`, only in a renderer that has a frame owner): `DWELLER_TEST_EVIL=sandbox-form` (a `begin_navigation` with `post`), `sandbox-cookie` (`cookie_get`), `sandbox-storage` (`storage` op 0), each after the frame's load.
- Chromium read: `content/browser/renderer_host/render_frame_host_impl.cc` (`BeginNavigation`: the browser's `IsSandboxed` checks on the frame's active flags, not on what the renderer says), `third_party/blink/renderer/core/loader/form_submission.cc` (the renderer's `kForms` check), `services/network/restricted_cookie_manager.cc` (an opaque origin gets no cookie access).
- files: `browser/ui/child-sent.aye`, new `browser/ui/sandboxed-child.aye`; `browser/renderer/load.aye`, new `browser/renderer/send-sandbox-evil.aye`; new `browser/tests/ui/{oopif-sandbox,oopif-sandbox-child}.html`; `tests/browser/window_renderer_oopif_site.rs`.
- verify (2026-11-16, Linux x86_64):
  - `cargo test --release --test browser -- window_renderer_oopif window_sandbox_targets aye_unit_tests window_renderer_storage`: 19 passed, 0 failed.
    - `window_renderer_oopif_site_sandbox`, with `DWELLER_PROCESS=tab` and `=site`: the four clicks of `sandbox_targets.html` end as in the in-process window (`_top` link without a flag: stays; with `allow-top-navigation-by-user-activation`: `other.html`; `_top` form with `allow-forms` only: stays; with `allow-top-navigation`: `other.html?`), empty stderr.
    - with `DWELLER_PROCESS=site`: `oopif-sandbox.html` (`sandbox="allow-scripts"` on a `localhost` frame in a `127.0.0.1` page; the child reads `document.cookie` and `localStorage` and submits a POST form by script): one child, title `Sandboxed cookie SecurityError storage SecurityError`, not `?posted`, empty stderr. With each hook: `renderer-child PID http://localhost gone REASON`, stderr `error: bad message: REASON PID`, the parent still `title Parent`.

## Status: done, 2026-11-16

Left:

That is the proc-tests lane's automatic waits, not a sandbox fault.
- `allow-popups` and `allow-popups-to-escape-sandbox` for a child renderer, once popups cross renderers (proc-spaces lane).
- a sandboxed same-site frame runs in its embedder's renderer (process-model §3), so a compromised renderer is not held to that frame's flags; Chromium isolates sandboxed frames since M127 (process-model §9, open question 8).
- the flags are those sent when the child was last navigated by the browser; a `sandbox` attribute changed later applies at the frame's next navigation by its parent, as in the engine.
