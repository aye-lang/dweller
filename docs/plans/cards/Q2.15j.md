# Q2.15j: find in frames

- goal: third item of the lane's second list ("find in frames", not needed for the flip). With `DWELLER_PROCESS=site` the find bar searched only the tab's own renderer: text in a cross-site frame was not counted or highlighted, and a frame's renderer that answered would have been killed (`find_reply` was "unexpected in a frame").
- design (the existing `find` 62 and `find_reply` 63, two more command values, no new kind):
  - browser: `askFind` sends the query to every live frame renderer of the tab in tree order (`findFrames`: the top, then each child and its children). The top gets the command as before; the others get 5 "passive" (highlight, no active match). `findCounts` adds the counts up, and the active match's number is the counts of the frames before the frame that holds it plus that frame's own (`TabProcess.find_frame`).
  - Enter and Shift+Enter (`stepFind`): inside the frame that holds the active match the renderer steps as before; at that frame's last (first) match the active one moves to the next (previous) frame with matches: the old frame is told 5, the new one 0 "first" or 6 "last". With one frame it wraps in place.
  - a page with no match of its own: once every answer is in, the first frame with matches gets the active one (`settleFindFrame`, each poll of the shown tab).
  - renderer: 5 clears the active mark (`find_passive`, `find-marks.aye`), 6 makes the last match active and scrolls to it (`step-match.aye`); `find` accepts commands up to 6.
  - checks: a child's `find_reply` goes through `takeFindReply` as a tab's (id asked, count and active in range, else `bad find_reply`).
  - `--state --processes` prints `renderer-find COUNT active N` for a tab with child frames once a find ran; `renderer:find` waits for the children's answers too.
- Chromium read: `content/browser/find_request_manager.cc` (`Find` to each frame, `OnFindReply` sums `number_of_matches_`, `Traverse` to the next frame in the search order when a frame is past its last match, `active_match_ordinal` from the frames before).
- files: new `browser/ui/{add-find-counts,find-frames,send-find,step-find,active-find-frame,next-find-frame,settle-find-frame,find-waits,write-find-state}.aye`; `browser/ui/{ask-find,find-counts,tab-process,child-sent,poll-tab-slot,renderer-waits,write-tab-process}.aye`; `browser/renderer/{answer-all,take-find,find-marks,step-match,tab-renderer}.aye`; new `browser/tests/ui/{oopif-find,oopif-find-child}.html`; `tests/browser/window_renderer_limits.rs`.
- verify (2026-11-19, Linux x86_64): `window_renderer_limits_find_in_frames`, `oopif-find.html` ("needle" once in a `127.0.0.1` page, twice in its `localhost` frame): the query gives `matches 3`, `renderer-find 3 active 0`; Enter 1, 2, then 0 again; Shift+Enter from the start 2; Enter then Shift+Enter 0. `?only` (no match in the page): `matches 2`, active 0, Enter 1. Escape: `matches 0`. `window_renderer_edit::window_renderer_find` (one renderer, pixels against in-process) passes unchanged. 
  - on the tree with the wave branch at 492db3e: `cargo test --release --test browser` 329 passed, 0 failed; `check_layers.py`, `gen_property_ids.py --check`, `aye check browser` exit 0; `check_taste.py` 1 on that run (two functions in `find-counts.aye`), then 0 after `add-find-counts.aye` took one, with `aye check` 0 and the two find tests passing again.
