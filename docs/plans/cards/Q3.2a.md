# Q3.2a: CORS is enforced in net, not in page JS

- goal: a page cannot read the response of a cross-origin `fetch` (mode `cors`) or XHR unless the server allows it. The check runs in `net/` (Aye), keyed on the request's initiator (`net.Initiator`, Q3.1c), its mode and its credentials, so it moves into the browser process with net (Q2.4, `docs/process-model.md` sections 2 and 4). Page JS only types and filters the response (basic, cors, opaque; exposed headers).
- cause: the CORS check lived only in `engine/fetch-api.js` (`corsOk`, used by `fetch`). XHR only filtered the headers of a cross-origin response: the body of a cross-origin XHR without `Access-Control-Allow-Origin` was readable.
- design:
  - `net.Mode` (`NoCors`, the default, and `Cors`) on `net.Request`. `fetch` passes `req.mode` (`no-cors` stays `NoCors`, any other mode is `Cors`); XHR is always `Cors`. `ak.fetch`/`ak.fetchStart` take the mode as argument 5 (the callback moves to 6).
  - `corsOrigin`: CORS applies when the mode is `Cors`, the URL is http(s), and the initiator's origin differs from the URL's (Chromium `ShouldCheckCors`). The initiator's serialized origin, `null` for an opaque one (`hrefOrigin`). The browser and `data:`/`file:` targets are not checked.
  - `corsCheck` (Chromium `CheckAccess`) on the response at its final URL: `Access-Control-Allow-Origin` must be `*` (not for `credentials: include`) or equal the origin; a credentialed request also needs `Access-Control-Allow-Credentials: true`. A failed check is `FetchError.Network`: `fetch` rejects with TypeError; XHR ends with status 0, `error`, `loadend`, no body.
  - Both paths: `net.request` (synchronous XHR, archive replay) through `corsChecked`; the background loader (`finishRequest`) fails the request. The archive still records the real response. `Ask` keeps the initiator's URL (the origin page's, not the referrer's), so an `about:blank` frame is checked with its parent's origin.
  - No preflight (Q3.2b). A cross-origin `Cors` request that would need one (`corsSafelisted`: a method other than GET, HEAD, POST, or a header other than Accept, Accept-Language, Content-Language and a safelisted Content-Type, or a value over 128 bytes) is not sent: `corsSendable` fails it as a network error. `Range` is not treated as safelisted.
  - `fetch-api.js`: `corsOk` and its throw are removed; `corsFiltered` and the response types stay.
  - `net/permissive-cors.aye` is unchanged: it still synthesizes headers for an archived response without recorded headers.
- not done: the CORS check on each redirect hop and the tainted (`null`) origin after a cross-origin redirect; preflight and its cache (Q3.2b).
- files: `browser/net/{mode,href-origin,cors-origin,cors-check,cors-checked,cors-sendable,cors-safelisted,safelisted-header}.aye` (new), `browser/net/net.aye`, `browser/net/loader.aye`, `browser/engine/window_api.aye`, `browser/engine/prelude.aye`, `browser/engine/fetch-api.js`, `browser/tests/net/cors.{html,txt}` (new), `tests/browser.rs` (`cors_in_net`), `docs/browser.md`.
- verify: `cors_in_net` (from `127.0.0.1` to `localhost` of one port: XHR and fetch without ACAO get no body, with ACAO `*` or the origin they do, credentialed with `*` fails, `no-cors` is opaque, a POST with `x-test` is not sent); the fetch, xhr, jsdom, samesite and cors tests in one run; WPT `fetch/api` and `xhr`; `aye check browser`; `check_taste.py`.
