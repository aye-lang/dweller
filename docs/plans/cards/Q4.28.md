# Q4.28: Reflect.construct reads its argument list natively, so core-js's Array.from no longer recurses to the stack limit

- goal: on mistral (archive `target/sites/mistral`) the renderer ran one timer task of 10–16 s in Google Tag Manager's `gtag/js` (W7 notes, 2026-11-24). Find what the task does and why it is slow in the JS VM, and fix the slow path.
- method: `browser/build.sh` (safe) at 2aeff8d2 and the same plus the fix, this Mac (M2 Pro, load 2–4). `window_perf.py scroll` (the W7 scroll: 3 `frame`, then 40 `wheel:-3 frame`) with `DWELLER_REPLAY`, `DWELLER_PROCESS=single`, `SDL_VIDEODRIVER=dummy`, `--log`; once without and once with `DWELLER_JS_VM_STATS=t DWELLER_JS_NATIVES=1` (Q4.16a's counters; they add ~22 ns an instruction, so the task grew to 32.9 s). The live page: the same scroll without `DWELLER_REPLAY`, `--frames 80`, `DWELLER_PROFILE` a temp dir. Script bodies from the archive's `.response` files. Logs: `target/q428-*` in the worktree.

- live (base build, live network): the same functions (`Array.from` 769M instructions, `__engine.construct` 10.7M calls) and a 5304 ms timer task. So this is not a replay or virtual-clock artefact: the task does not wait on a clock, it recurses.

## Cause

- The prelude's `Reflect.construct(C, args, NT)` built its argument list with `Array.from(args)`, the page's global.
- axept's core-js replaces `Array.from`. It fails core-js's `check-correctness-of-iteration` test: Dweller's `Array.from` does not call the iterator's `return` when `mapfn` throws (`SAFE_CLOSING` false; node: true).
- core-js's `Array.from` calls `isConstructor(this)`, and that calls `Reflect.construct(Object, [], Array)` in a `try`. So `Array.from` → `isConstructor` → `Reflect.construct` → `Array.from([])` → ... until the stack overflows. The deepest `isConstructor` catches the RangeError, and the stack unwinds. One top-level `Array.from` costs a full stack of recursion: 3333 levels in `dweller js` (20 calls became 66660), about 4.7 ms.
- gtag calls `Array.from` (`Array.from(new Uint8Array(a))`, `Array.from(d.searchParams)`, `Array.from(a.classList, …)`), and so does the prelude (`new Uint8Array(array)`, `Promise.all`, `drawImage`). On mistral that was 12.25M calls, about 1840 top-level calls times a stack each.
- In the window without `--frames` the budget killed it (`Script terminated: it ran too long`, twice). Then the page's later scripts and its animation never ran.

## Fix

- `Reflect.construct` no longer calls `Array.from`. `__engine.construct` (`engineConstruct`, `browser/js/coroutine.aye`) reads the list itself with `pushArrayLike`, the CreateListFromArrayLike that `Function.prototype.apply` uses. It first checks the target and new.target, then throws a TypeError for a non-object list, as the spec orders it (https://tc39.es/ecma262/#sec-reflect.construct). `browser/js/lib.aye` passes `args` through.
- This also fixes three spec gaps: a string or number list now throws, the list's `Symbol.iterator` is not used, and the list is not read when new.target is not a constructor.
- fixture: `browser/tests/js/298_reflect_construct_array_like.{js,out}` (`.out` from node 22). It has a core-js-shaped `Array.from` and `isConstructor`. 20 calls print `calls 20` (before: 66660), plus array-like, hole, `arguments` and iterator-override lists, the four non-object lists, the read order, and new.target.

## Found, not in this step

- `Array.from` does not close the iterator when `mapfn` throws, and it drains the whole iterator before it maps (`arrayFrom`, `browser/js/builtins_array.aye`). This is why core-js replaces it on mistral. A spec `Array.from` (step, map, IfAbruptCloseIterator; `this` as the constructor) would let the native one stay.
- The prelude calls the page's `Array.from` inside built-ins: `Promise.all`/`allSettled`/`any`, `AggregateError`, the typed-array constructors, `Intl.ListFormat`, `Segmenter`, and the canvas `drawImage`, `setLineDash` and `isPointIn*`. A page's polyfill then runs inside them. Capturing the intrinsic once would close this.
