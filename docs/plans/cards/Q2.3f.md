# Q2.3f: clipboard, find, link and form targets, arrow keys and frame clicks with the renderer

- goal: with `DWELLER_PROCESS=tab` the rest of the window's page features that Q2.3e listed as not running work through the tab's renderer: Cmd/Ctrl+A/C/X/V in a text field, find (Cmd/Ctrl+F, the find bar, next, previous, the highlight of the matches), links and forms with `target=_blank` or a name (another tab, GET and POST), arrow keys on a focused `select`, range and number input, clicks and hovers in the (same-site, in-process) frames of a page. Without the flag nothing changes.
- design:
  - IPC messages added (type codes from 60; Q2.4e takes 50 and up): 60 `edit{seq, command, typed}` B→R (0 select all, 1 copy, 2 cut, 3 paste with the text; an input like `key`: it has a `seq` and is acked); 61 `clipboard{copied}` R→B (the text a copy or cut put on the clipboard); 62 `find{id, command, query}` B→R (0 find and jump to the first match at or below the top of the view, 1 find again without jumping, 2 next, 3 previous, 4 stop); 63 `find_reply{id, count, active}` R→B; 64 `context{ask, context, href, post, content_type, body}` R→B (ask 0 open a tab for the renderer's context id, 1 navigate the tab opened for it; the engine's `ContextRequest`).
  - clipboard: the window owns the system clipboard. Cmd/Ctrl+C or X sends `edit` and the renderer answers `clipboard` with the field's selected text before it acks the input (nothing for an empty selection or a password field); the window writes it with SDL. Cmd/Ctrl+V reads the clipboard in the window, on the gesture, and sends it in `edit`; the renderer takes it as typed input (`beforeinput`, insert, `input`; the same `textInput`). The renderer never reads the clipboard. Cmd+A selects the field's text. Only the focused frame's renderer gets the edit (`focusedFrame`).
  - find: the find bar (query field, "n of m", Enter, Shift+Enter, Esc) stays in the window; it sends `find` on every change and key, and shows the last `find_reply`. The renderer keeps the query, finds the text over its laid-out page (`engine.findText`) on each frame it paints, picks the active match (first at or below the scroll offset after a find, the next or previous after those), scrolls to it when it is out of the view (a third from the top, as the window), paints the matches as marks (yellow, the active one orange: the caret's mechanism) and sends `find_reply` when the count or the active one changed or a `find` was run. A `find` waits for the next frame, after the window's resize for the shorter view the find bar makes. A closed find bar (`stop`) clears the marks.
  - targets: with the window as tab host (`engine.setTabHost(true)` while the renderer handles a mouse, key, text or edit input, so that scripts of a load or a timer still open their popups in memory as before), the engine's context requests of a click (link, form, `window.open` in a handler) are sent as `context`. The browser opens a tab (shown unless the opener's tab is an agent's; that tab is the agent's too), pushes the URL to its history and lets its renderer navigate (`queueNavigate`, with the POST body kept on the `TabSlot` until sent); a later request for the same context id (a name, `window.open(url, name)` again) navigates that tab without showing it, or opens a new one when it was closed. The tab has no opener (no `window.opener`, `postMessage` or `window.close()` across tabs).
  - arrow keys: `renderer/step-key.aye` and `step-option.aye` port the window's `pageKey`: Up and Down step a number or range input (Left and Right the range), Up and Down select the previous or next enabled option of a select, each firing `input` and `change`. The activation `Changed` now lays the page out after it restyles it (a Space released over a checkbox left a stale layout for the next Tab).
  - frames: `engine.frameAt` routes a click in a frame to `click-frame.aye` (the click event, a link to its own frame, the frame its target names or the tab, a form button, as the window's `clickFrame`), and a hover to `frame-hover.aye` (the status line shows the link resolved in the frame).
  - the browser's checks (`rendererSent`, `childSent`; a failure logs `bad message: REASON PID` and kills): `clipboard` only while a copy or cut it sent is unacked and answered at most once (`tp.copy_seq`), at most 512 KiB, no NUL byte (`bad clipboard`; the reference: the renderer may write the clipboard only for a gesture it was asked for); `find_reply` with an id not older than the last reply and not newer than the last `find` sent, `active` under `count` (`bad find_reply`); `context` with ask over 1, post over 1 or a URL over 2 MiB (`bad context`); a `context` without an unacked input in flight, or a second one for the same input, is dropped with `popup blocked: no user gesture` (a popup needs a gesture); the URL then passes the navigation checks of `begin_navigation` (`initiatorMayLoad` from the committed URL, no top-level `data:`) before any tab opens. A `context` from an out-of-process frame is dropped. Nothing in these messages names a site or a document: the URL is checked as a request, not claimed (Q2.7).
- Chromium read (idea only): `content/browser/renderer_host/render_widget_host_impl.cc` (the browser keeps the clipboard shortcuts and hands the paste to the focused frame; the cursor and `TakeFocus` pattern of Q2.3e), `content/browser/find_request_manager.cc` and `third_party/blink/renderer/core/editing/finder/text_finder.cc` (the browser sends the query with a request id and the renderer answers with the match count and the active match; the renderer scrolls to it and paints the markers), `content/browser/renderer_host/clipboard_host_impl.cc` (a renderer writes the clipboard only on a gesture and reads it only on a paste), `content/browser/renderer_host/render_view_host_impl.cc` / `render_frame_host_impl.cc` (`CreateNewWindow`: the browser opens the popup and checks the request). Dweller takes: the browser owns the clipboard and the find bar; the renderer finds, paints the highlight and serves the selection; a popup is a checked request that needs an input in flight.
- files: `browser/ipc/{message,decode,put-payload,from-renderer}.aye`, new `browser/ipc/edit_test.aye`; `browser/renderer/{answer-all,tab-renderer,serve-on,paint-frame,focus-key,run-act,click-at,hover-report}.aye`, new `browser/renderer/{edit-command,copy-selection,take-find,run-find,step-match,show-match,first-match-below,find-marks,send-contexts,drives-input,step-key,step-option,click-frame,follow-frame-link,submit-in-frame,frame-hover}.aye`; `browser/engine/drop-opened-contexts.aye` (frees the popup contexts the renderer keeps for names when it exits); `browser/ui/{window,chrome,script,agents,tab-process,start-tab-process,end-tab-process,tabs,queue-navigate,forward-tab,renderer-sent,child-sent,poll-tab-processes,renderer-waits}.aye`, new `browser/ui/{forward-edit,edit-command-of,paste-clipboard,take-clipboard,ask-find,take-find-reply,find-counts,take-context,serve-open-requests,open-target,opened-slot,opened,end-slot}.aye`; `browser/tests/ui/renderer_targets.html`; `tests/browser.rs`, new `tests/browser/window_renderer_edit.rs` (`window_renderer_{clipboard,find,arrow_keys,frame_click,targets}`). ## Status: done, 2026-11-09

Left:
- `wait` (the window command that waits in real time for a selector or the timers) still reads the window's page, null under the flag: it needs a renderer-side wait answered later (the `agent_reply` of a pending request).
- the agent's highlight (the outline with the ref and the `agent: click ...` status line; `agentActs` is a no-op in `RendererHost`): needs a message that carries the target's rect and label to the browser.
- popups keep no relation to their opener: no `window.opener`, `postMessage` or `window.close()` across tabs; a named target finds only the tabs this renderer opened (not one the person opened or another renderer's); `context` requests of out-of-process frames (`DWELLER_PROCESS=site`) are dropped; a page's `window.open` with no input in flight still opens its popup in the renderer's memory, as before; a reload of a tab that a POST form opened sends a GET.
- Escape on an open remote dropdown, then arrow keys, differs from the in-process window (the dropdown's close and the select's focus); the arrow keys on a select reached by Tab or click-less focus match.
- the clipboard works on text fields only (the page has no text selection outside them); copy then paste in the same input burst races the renderer's answer (the paste reads the clipboard before it arrives; a person's gestures are not that fast); no rich clipboard.
- find covers the top document only (as the window: not frames, not out-of-process frames) and sends no match rects to the browser (no tick marks); the scroll to the active match is clamped by the last frame's maximum, so right after a resize it can stop a few px short.
- hovering a frame's link is not pixel-identical to the in-process window (the frame's `:hover` styles are not run).
