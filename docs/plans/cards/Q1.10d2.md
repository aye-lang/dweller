# Q1.10d2: a cap on the memory one image decode may use

- goal: a tiny image file cannot make the browser allocate hundreds of MB (left by Q1.10d: the `image` fuzz target peaked at 705 MB on files that claim a size just under the old 40-million-pixel limit).
- cause: `checkSize` let any image up to 40 million pixels through (160 MB of RGBA), and the JPEG decoder allocated its sample planes and, for a progressive file, its coefficients (2 bytes per sample per component) at the frame header, before reading any scan data. A 150-byte progressive JPEG claiming 6324 x 6324 with an empty scan ended at a marker (the reader yields zeros there) decoded to a full bitmap: max RSS 652 MB.
- reference read: `third_party/blink/renderer/platform/image-decoders/image_decoder.cc` (`SetSize` refuses a size whose `width * height * 4` overflows; `max_decoded_bytes_`), `content/child/blink_platform_impl.cc` `MaxDecodedImageBytes` (desktop: no limit; Android: physical memory / 25, "16M pixels on a 2GB device, 4K*4K is a relatively common texture size"), `jpeg/jpeg_image_decoder.cc` `DesiredScaleNumerator` (a JPEG over the limit decodes at `scale_num / 8`; 0 fails the decode).
- cap: `MAX_DECODED_BYTES` = 256 MiB (64M pixels, 8192 x 8192), the size of Q4.10's decoded-image budget (`DECODED_BUDGET`), so one image never outgrows the budget it is held under. The reference's desktop default is no limit. `MAX_PIXELS` is gone.
- design:
  - `image.aye` `checkSize` = `check-side.aye` `checkSide` (zero: `Invalid`; a side over 16384: `Unsupported`) plus `width * height * 4 > MAX_DECODED_BYTES` (`Unsupported`). Every decoder calls it on its header before allocating; `headerSize` (`checkedSize`) returns null, so the page shows a broken image. PNG, GIF, WebP and ICO cannot downscale, so over the cap they are refused; none of the 1,175 PNG/GIF/WebP/ICO files under WPT is.
  - JPEG: `jpegFrame` checks only the sides, lays out the components at full size, then `jpeg-scale.aye` `jpegScale` picks the smallest of 1, 2, 4, 8 at which the decode's buffers (bitmap and upsampled planes, `4 + ncomp` bytes per output pixel, the sample planes / s², and a progressive file's full-size coefficients, 128 bytes per block) fit the cap; none fits: `Unsupported`. Powers of two only (Dweller's IDCT is 8-point; the reference takes any n / 8). Offsets and strides are divided by the scale; `jpeg-store-scaled.aye` writes each 8 x 8 IDCT block as (8 / s)² box averages (`jpeg-box.aye`); `jpegOutput` and `jpegUpsample` work at the scaled size. Scale 1 takes the old path, so no decode output changes.
  - Natural size: `image.Bitmap` gains `natural_width` / `natural_height` (0: the pixel size) and `naturalWidth()` / `naturalHeight()`. The JPEG decoder sets them to the header size (swapped by EXIF orientation in `jpegOrient`); `jpeg-frame-size.aye` reports the header size. Readers of the natural size use them: `layout/controls.aye` `naturalSize` and `urlSize`, `paint/background.aye` (tile size), `paint/paint.aye` (`object-fit`), `engine/image_api.aye` (`naturalWidth`, `img.width`), `engine/canvas_api.aye` (`drawImage` source scale). Paint draws the smaller bitmap into the natural-size box. `engine/take-pixels.aye` lands a decode when its natural size matches the header-sized bitmap, and takes its pixel size.
  - WebP: an animated file whose first frame is the whole canvas returns the frame instead of copying it; a partial frame whose frame plus canvas pass the cap is refused.
- files: `browser/image/image.aye`, `jpeg.aye`, `jpeg-frame-size.aye`, `webp.aye`, `browser/engine/take-pixels.aye`, `image_api.aye`, `canvas_api.aye`, `browser/layout/controls.aye`, `browser/paint/background.aye`, `paint.aye`, `tests/browser.rs` (changed); `browser/image/check-side.aye`, `jpeg-scale.aye`, `jpeg-store-scaled.aye`, `jpeg-box.aye`, `decode-cap_test.aye`, `browser/engine/downscaled-decode_test.aye` (new); fixtures `browser/tests/image/cap_wide.png` (69 bytes, 8193 x 8192), `cap_progressive.jpg` (16384² progressive), `cap_large.jpg` (6324² baseline), `cap_natural.html`; seeds `browser/tests/fuzz/image/bomb_progressive.jpg`, `bomb_wide.png`. Contains Q1.10d (PR #340).

## Status: done, 2026-11-08

- left:
  - The 120 s fuzz peak (1,122 MB) is higher than Q1.10d's 705 MB: the cap only bounds a JPEG decode's whole working set; PNG, GIF, WebP and ICO bound the bitmap, and their own buffers (VP8 planes, the VP8L ARGB buffer, GIF's index buffer) come on top. Counting those against the cap per decoder, as `jpegScale` does, is the next step; the input behind the peak is not isolated.
