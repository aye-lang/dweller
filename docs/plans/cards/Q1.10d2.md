# Q1.10d2: a cap on the memory one image decode may use

- goal: a tiny image file cannot make the browser allocate hundreds of MB (left by Q1.10d: the `image` fuzz target peaked at 705 MB on files that claim a size just under the old 40-million-pixel limit).
- cause: `checkSize` let any image up to 40 million pixels through (160 MB of RGBA), and the JPEG decoder allocated its sample planes and, for a progressive file, its coefficients (2 bytes per sample per component) at the frame header, before reading any scan data. A 150-byte progressive JPEG claiming 6324 x 6324 with an empty scan ended at a marker (the reader yields zeros there) decoded to a full bitmap: max RSS 652 MB.
- reference read: `third_party/blink/renderer/platform/image-decoders/image_decoder.cc` (`SetSize` refuses a size whose `width * height * 4` overflows; `max_decoded_bytes_`), `content/child/blink_platform_impl.cc` `MaxDecodedImageBytes` (desktop: no limit; Android: physical memory / 25, "16M pixels on a 2GB device, 4K*4K is a relatively common texture size"), `jpeg/jpeg_image_decoder.cc` `DesiredScaleNumerator` (a JPEG over the limit decodes at `scale_num / 8`; 0 fails the decode).
- cap: `MAX_DECODED_BYTES` = 64 MiB (4096 x 4096 RGBA). The desktop default is no limit, so it cannot bound a bomb; the value is the reference's own figure for a capped device (16M pixels). `MAX_PIXELS` is gone (the cap is lower).
- design:
  - `image.aye` `checkSize` refuses `width * height * 4 > MAX_DECODED_BYTES` as `Unsupported`. Every decoder calls it on its header before allocating, and `headerSize` (through `checkedSize`) returns null for it, so the page shows a broken image.
  - JPEG: `jpeg-scale.aye` `jpegScale` picks the smallest of 1, 2, 4, 8 at which the scaled size passes `checkSize` (powers of two only: Dweller's IDCT is 8-point; the reference takes any n / 8). The planes are allocated at the scaled size; `jpeg-store-scaled.aye` writes each 8 x 8 IDCT block as (8 / s)² box averages (`jpeg-box.aye`); `jpegOutput` and `jpegUpsample` work at the scaled size. Scale 1 takes the old path unchanged, so no decode output changes. `jpeg-frame-size.aye` reports the scaled size, so the window's header-sized bitmap matches the decode (`takePixels`).
  - Intermediate buffers: a progressive JPEG whose coefficient buffer (64 x 2 bytes per block, full size) passes the cap is refused before allocation. PNG's inflate output is already bounded by deflate's 1032x ratio and fails before the bitmap; WebP/VP8 planes and the GIF canvas are under the cap once the header passes it.
- files: `browser/image/image.aye`, `jpeg.aye`, `jpeg-frame-size.aye` (changed); `jpeg-scale.aye`, `jpeg-store-scaled.aye`, `jpeg-box.aye`, `decode-cap_test.aye` (new); fixtures `browser/tests/image/cap_wide.png` (69 bytes, 4097 x 4096), `cap_progressive.jpg`, `cap_large.jpg` (150 bytes each, 6324² progressive, 6000 x 4000 baseline); seeds `browser/tests/fuzz/image/bomb_progressive.jpg`, `bomb_wide.png`. Contains Q1.10d (PR #340).
