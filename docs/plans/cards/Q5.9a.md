# Q5.9a: `<video>` and `<audio>` 1: progressive playback, with controls

- goal: media elements that load, report and play as the HTML standard says ("Media elements"), for MP4 (H.264, AAC), WebM (VP9, Opus), MP3 and WAV, with controls; decoding of the compressed formats by the system decoders in a utility process. Row Q5.9a of `foundations.md` (F1, Chromium `media/`, `third_party/blink/renderer/core/html/media/`). Assigned to lane feat-net by the integrator on 2026-11-17 with a suggested cut, taken below.
- facts found first (2026-11-17):
  - `HTMLMediaElement` exists as an interface with stubs (`prelude.aye`: "Media elements play nothing"): `play()` rejects with `NotSupportedError`, `canPlayType()` is `""`, `paused`, `currentTime`, `duration`, `volume`, `muted`, `readyState`, `ended` are plain settable values, no event ever fires. The content attributes are reflected (`reflection-table.js`: `src`, `preload`, `autoplay`, `loop`, `controls`, `muted`, `poster`, `playsInline`). `Audio(src)` makes an element.
  - Layout knows `video` as a replaced element with a 2:1 default ratio (`layout/block.aye`), `audio` is not displayed; nothing paints either.
  - `audio/` renders Web Audio graphs to an SDL device (`out.aye`, float32 stereo, queued about 30 ms ahead) and reads and writes WAV (`wav.aye`). Without a device it renders by the page clock.
  - Network: responses arrive whole (Q5.8's card); there are no Range requests; a body is capped at 16 MiB for a subresource. The browser process owns the network; a renderer gets bytes over IPC (`FetchBody`).
  - No container parser (MP4, WebM, MP3) and no decoder exists. Code-taste rule 6 allows MIT, BSD and Apache libraries only: no ffmpeg, no GStreamer. The cloud machines have no system decoder, so compressed audio and video cannot be decoded or verified here.
  - WPT `html/semantics/embedded-content/media-elements` is not in the checkout; its files need `/media/` and `/common/media.js`.

- decisions (nobody to ask; the plan's defaults and the integrator's note):
  - No LGPL or GPL decoder. Without a platform decoder (Linux, the cloud) `canPlayType` answers `""` for the compressed codecs and their sources fail with `MEDIA_ERR_SRC_NOT_SUPPORTED`, as a browser without the codec does; WAV plays everywhere.
  - The media clock is the page's clock scaled by `playbackRate`; with an audio device the audio clock corrects it (slice 4).
  - IPC kinds for the decoder: 149 to 159, the rest of this lane's range.
- references: https://html.spec.whatwg.org/multipage/media.html ; Chromium `third_party/blink/renderer/core/html/media/html_media_element.cc` (the state machine and the event order), `media/base/pipeline_impl.cc`, `media/filters/` (demuxers), `media/formats/mp4/`, `media/formats/webm/`; ISO/IEC 14496-12; the Matroska specification (RFC 9559).

- slice 1, as built (2026-11-17):
  - `engine/media-types.js` (`TimeRanges`, `MediaError`, the range union, `canPlayType`'s table: WAV with codec `1`), `engine/media-element.js` (the state per element, the load and resource selection algorithms, `play()`/`pause()` with their promise lists, the media clock, seeking, the IDL attributes and constants), `engine/ak-media-probe.aye` (`ak.mediaProbe(bytes)`: duration, channels, rate, width, height of a WAV through `audio.parseWav`; the one interface the later demuxers answer). Both scripts run right after the prelude, so their events are trusted.
  - The resource is fetched whole with `ak.fetchStart` (no-cors, or cors with `crossorigin`), so it works in a renderer through the browser's network already; `buffered` and `seekable` are the whole duration once loaded (slice 2 makes them real).
  - The clock: position = the position at the last start plus the page's clock times `playbackRate`; a timer every 250 ms (or at the end) fires `timeupdate`, then `ended`, or seeks to 0 with `loop`. As in Chromium `paused` stays false after `ended`. On the virtual clock a file plays in no real time.
  - Autoplay policy (Chromium's document-user-activation rule): `play()` and `autoplay` need the element muted (or volume 0) or a user activation of the page, else `NotAllowedError`. A video without an audio track is not yet excepted (no video yet).
  - An element starts its resource selection when a script first touches it, at the page's first task after the prelude for the elements the parser made, and from then on a `MutationObserver` on the document follows `src` and inserted media and `source` elements. The observer is made with the first media element, so a page without media pays nothing; a media element inserted later into a page that had none starts when a script touches it (Left).

- slice 2, as built (2026-11-19):
  - `engine/media-load.js` (split from `media-element.js`, which keeps the state, the clock and the API; the three scripts share one parts object that the last one removes): the resource is asked in 64 KiB `Range` requests through `ak.fetchStart`, so through the browser's network in every process mode. A 206 with a matching `Content-Range` adds its byte range and tells the total; a 200 is the whole resource; anything else fails the source (before metadata: the next `<source>`, or `MEDIA_ERR_SRC_NOT_SUPPORTED`; after: `MEDIA_ERR_NETWORK`).
  - `buffered` is the byte ranges in time; the ready state follows the range under the playback position (`HAVE_METADATA` outside any range, `HAVE_CURRENT_DATA` at its end, `HAVE_FUTURE_DATA` inside it, `HAVE_ENOUGH_DATA` with 10 s ahead or to the end), with `canplay`, `playing`, `canplaythrough`, and `waiting` when playback reaches the buffered edge; the clock stops there and goes on when data comes.
  - `preload`: `metadata` (the default) and `none` ask the first range and suspend (`networkState` idle, `suspend`); `auto`, `autoplay`, `play()` and a seek ask on. A seek outside the buffered ranges drops the range in flight and asks from the seek's byte; `seeked` waits for it.
  - `ak.mediaProbe(bytes, total)` and `media.probe(alloc, bytes, total)`: a WAV's duration is from its data chunk's declared size against the resource's total, so the first range is enough.
  - `load()` removes the element's queued event tasks, as the standard says (a `volumechange` queued before `src` is set no longer fires: the golden's line changed for that reason). A `src` set on an element outside the document is noticed at its next media property read.

- slice 4b, as built (2026-11-19): the decoder process, and video frames.

IPC 149 `DecoderOpen`, 150 `DecoderData`, 151 `DecoderOutput`, 152 `DecoderClose`, samples and outputs in chunks of 256 KiB; in `docs/process-model.md` §1 and §2. When the child ends, every stream gets one output with `seq` 0xffffffff and the element fails with `MEDIA_ERR_DECODE`; the next `open` starts a new child.
