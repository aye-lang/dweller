# Q2.15a: the process of a frame is chosen after redirects

- goal: readiness list for Q2.14, "Security (X1)", first bullet [Q2.9]. With `DWELLER_PROCESS=site` a frame whose URL is of its parent's site was fetched for the parent's renderer, and the response went there also when redirects had led to another site. Now the browser decides on the URL after redirects: a frame document of another site never reaches the renderer that asked for it; it commits in a renderer locked to its own site.
- design:
  - browser (`ui/frame-leaves.aye`): a renderer's document fetch for a frame (`kind` Document, not its own navigation, a claimed `top`) whose final URL is an http(s) URL of another site than the asker's lock "leaves". This is checked for every such response, redirected or not, so a renderer that asks for a cross-site document as a frame's gets no byte of it either. Both paths: the answered-at-once one (`answerFetch`) and the held one (`finishHeld`, `HeldFetch.framed`).
  - `keepFrame`: the response is checked against `X-Frame-Options` and `frame-ancestors` with the asker and its embedders as ancestors (`framingRefusedBy`; `framingRefused` is now that from `tp.embedder`). Refused: the asker gets `FetchFail` `AccessDenied` and no renderer starts. Else the response is kept (`TabProcess.kept`, `KeptFrame` {the URL asked, the final URL, the response}; at most 16, the oldest goes) and the asker gets the new B→R `FetchRemote{id}` (IPC kind 100), which carries nothing else: not the final URL, not a header.
  - renderer: `FetchRemote` ends the fetch with `Response.remote` (`net/net.aye`, default false). `engine.pageOf` makes the remote placeholder for it (`remotePageAt`, the body of the former `remotePage`) at the URL that was asked. So every way a frame gets a document (`framedDocument` and its background prefetch, `navigateFrame`, a form into the frame, the frame's history) lands on the placeholder, and the next `subframes` names it with the URL asked.
  - browser (`placeChild`): a new key whose URL has a kept response (`takeKept`, by the URL asked) is accepted although that URL is of the sender's site; any other same-site URL is still `bad subframes`. The `ChildFrame` gets `href` (the final URL) and `primed` (the response); `startFrameChild` starts the renderer with that response primed and locked to the final URL's site, and it is navigated to `childHref` (as `swapChild` does). No second request is made.
  - found on the way: `swapChild` replaced `ChildFrame.src` by the URL the child left for, and `placeChild` kills the parent (`bad subframes`) when a key's URL changes, so the parent's next changed `subframes` after a child's own cross-site navigation would have killed the parent. `swapChild` now sets `href` and `src` stays what the parent reports. (Read from the code; the old binary was not run against the new test.)
- decisions: the parent's renderer is not told the final URL (Chromium does not tell the embedder a cross-site frame's URL after redirects either). A refused document shows the network error page in the parent's own frame, as Q2.9's refused remote frame does.
- Chromium read: `content/browser/renderer_host/render_frame_host_manager.cc` (`GetFrameHostForNavigation`: the SiteInstance is computed for the navigation's current URL, again after each redirect), `content/browser/renderer_host/navigation_request.cc` (`OnRequestRedirected`, `OnResponseStarted`: the response is committed in the process chosen then, never passed through the initiator), `content/browser/renderer_host/ancestor_throttle.cc`.
