# Q5.5: `<input type=file>`: the picker and a multipart upload with files

- goal: a file input opens a picker, holds the chosen files (`files`, `value`, `input`, `change`, `cancel`), and a form or `FormData` sends them as `multipart/form-data` with their names, types and bytes, in all three process modes. Row Q5.5 of `foundations.md` (F1; Chromium `core/html/forms/file_input_type.cc`, `core/fileapi/`, `content/browser/web_contents/file_chooser_impl.cc`).
- facts found first (2026-11-16):
  - A file input is laid out as a button that says "No file chosen" (`layout/controls.aye`), its value is always "", `files` is an empty `FileList` (`engine/control-members.js`), and a submission sends one empty file (`engine/forms.aye` `multipartBody`).
  - `Blob`, `File`, `FileReader` and `FormData` exist in the prelude; a `Blob` keeps its bytes as a latin-1 string (`_bytes`), and `fetch` and XHR already serialize a `FormData` with `File` values.
  - SDL2 has no file dialog (SDL3 has). The window has no native code of its own on macOS (no Objective-C).
  - A sandboxed renderer opens no file (`docs/process-model.md` §6): the browser must read what the person chose.
- slices (each with its verify):
  1. The chosen files of a control, in the document (`dom/`): name, type (from the extension, `net.typeOfPath`), bytes, time; `value` is `C:\fakepath\NAME`, setting it to "" and a form reset empty the list; the control's label is the name or "N files". The engine: a click (or Enter, Space, `label`, an agent's click) on a file input records a request in its document, `engine.takeFileRequest` hands it to the host, `engine.chooseFiles` stores the answer and fires `input` and `change` (or `cancel` for none); `input.files` (`FileList` of `File`s with the bytes), `FormData(form)`, and the form's own submission (multipart with the file parts; urlencoded and text/plain send the names). Verify: slice 2's window tests.
  2. The picker, one process: the window starts a picker process and reads the chosen paths from its pipe without waiting for it (`ui/`): `DWELLER_PICKER` names the command (the test hook, and a person's own choice), else `osascript` (`choose file`, the system's open panel) on macOS and `zenity` on Linux; no picker in a headless window. Verify: `tests/browser/window_file.rs` with `DWELLER_PICKER` printing paths: the page sees the files (names, sizes, types, text and binary content through `FileReader` and `file.text()`), `change` and `cancel`, `multiple`, a form submission and a `fetch` of a `FormData` echoed by the test server byte for byte.
  3. `DWELLER_PROCESS=tab|site`: IPC kinds 190 `ChooseFiles{multiple, accept}` (R→B), 191 `ChosenFile{name, mime, modified}`, 192 `ChosenBytes{chunk}`, 193 `ChosenEnd{count}` (B→R). The browser reads the files and sends their bytes; the renderer never sees a path. Verify: the same tests with `DWELLER_PROCESS=site`, and a file input in a cross-site frame.
- decisions (nobody to ask; the plan's defaults):
  - The picker is a process, not an in-process panel: `osascript -e 'choose file'` shows the system's own open panel and needs no Objective-C in the browser; the window's loop never blocks on it. It is not a sheet of the window.
  - Bytes, not file descriptors, cross to the renderer (the process model's note said fds): no `fstat` or `lseek` joins the seccomp list, and a `Blob` is bytes in memory anyway. A selection over 256 MiB is refused (the picker's answer counts as cancel).
  - One picker per window at a time; a second request while one is open is canceled (Chromium shows one chooser per frame).
  - A renderer's request needs no proof of a user gesture: the person still has to choose a file in the picker; the browser sends only what they chose, by base name.
  - `accept` is passed to the picker as a hint (a `DWELLER_PICKER` command gets `single` or `multiple` as `$1` and the attribute as `$2`; `osascript` gets extensions and the four `type/*` groups as uniform types, `zenity` extensions; anything else drops the filter), never enforced: the standard says a hint.
- references: HTML "File Upload state (type=file)" (https://html.spec.whatwg.org/multipage/input.html#file-upload-state-(type=file)), "multipart/form-data encoding algorithm"; Chromium `core/html/forms/file_input_type.cc` (`SetFiles`, the events, `C:\fakepath\`), `content/browser/web_contents/file_chooser_impl.cc`.

## Status: done, 2026-11-16

Done note. Built whole for the three process modes.
- The document (`dom/`, 7 files): `Controls.files` (name, fake path, type, bytes, time per file and control), `file_request` and `file_pending`; `valueOf` gives `C:\fakepath\NAME`, `setValue("")` and `resetForm` empty the list; `layout/file-label.aye` names the file or counts them ("Many files" over 10: the label is a borrowed string).
- The engine (10 files): `activate` records the request, `takeFileRequest` (the page and its same-process frames, one pending per tab), `chooseFiles` (`input`, `change`, or `cancel`), `_fileCount`, `_fileInfo`, `_fileBytes`, `_fileStamp` behind `input.files` (`control-members.js`: one `FileList` until the selection changes), `FormData(form)` with the `File`s, `addFileEntries` and `filePart` for the form's own multipart body.
- The window (16 files): `startPicker` spawns the command with its output on a pipe, `pollPicker` reads it without blocking and reaps it, `readPicked` reads the files (256 MiB a selection), `deliverPicked` hands them to the page or sends them (`sendPicked`); `picker` is a new `--events` word (the words after it wait for the picker), and a window with a picker open is not idle.
- `DWELLER_PROCESS=tab|site`: kinds 190–193 as planned; `TabProcess.file_ask`; the renderer side is `renderer/ask-files.aye`, `take-chosen.aye`, `land-chosen.aye`. `docs/process-model.md` §2 says what was built.
