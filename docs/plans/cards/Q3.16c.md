# Q3.16c: a `javascript:` URL aimed at another frame needs the frame's origin

- goal: a `javascript:` URL aimed at another frame (`window.open` into its name, a link whose `target` is its name, its `location` set by another page) runs in that frame only when the source is of the origin of the frame's document, with one process, with a renderer per tab and with one per site (the default). Otherwise it is dropped: no script, no navigation. This is slice (b) of Q3.16b's Left, for frames.
- the hole (Q3.16b): with one process and with a renderer per tab, `window.open('javascript:...', name)` where `name` is a frame of another origin ran the script in that frame, and its string result replaced the frame's document. `openWindow` set the frame's navigation (`setNavigation`), and `followFrameNavigation` ran it with the frame as its own source (`runFrameJavascript(c, c, ...)`: the frame's CSP and the frame's origin). The same for `frames[name].location = 'javascript:...'` (`akWinNavigate`) and for a top-level page that another page sent to a `javascript:` URL (`_top`, `top.location`: the window's `afterScripts` and `pumpContexts` ran it with the page as its own source). With a renderer per site, the frame of another origin is remote: `window.open` did nothing, but `location` went to the browser in `proxy_navigate`, and the browser sent the frame a `navigate` to the `javascript:` URL: the frame's document was gone. A link with a target other than `_self` ran nothing.
- the rule (Blink `LocalFrame::CanNavigate`, `third_party/blink/renderer/core/frame/local_frame.cc`; the CSP is the source window's, `FrameLoader::StartNavigation` in `core/loader/frame_loader.cc`; the browser never loads one for a remote frame, `RenderFrameProxyHost::OpenURL` → `VerifyOpenURLParams` → `FilterURL`): a `javascript:` navigation of a frame other than the source's own runs only if the source is same-origin with the target's current document. Else the source gets the console error "The frame attempting navigation must be same-origin with the target if navigating to a javascript: url", and nothing else happens.

## As built

- `queueJavascriptUrl(source, target, href)` (`engine/queue-javascript-url.aye`): the source's CSP (`javascriptUrlRefused`), then `sameOrigin(source, target)` or the console error (`JAVASCRIPT_TARGET_ERROR`), then `queueJavascriptTask` (`engine/queue-javascript-task.aye`: the task of Q3.16 slice 2, which runs the URL in the target's script and makes a string result the target's document). A remote page has no script: nothing is queued.
- its callers: `openWindow` into a frame, `_self`, `_parent` or `_top` (`engine/open-window.aye`); `akWinNavigate`, the `location` of another window (`engine/windows.aye`); `followJavascriptLink` (`engine/follow-javascript-link.aye`): a link whose target is a frame (`targetFrame`), after the sandbox rule (`sandboxAllowsNavigation`); and, with the source as target, a page's own `location` and links (`akNavigate`, as before).
- `navigateRemote` (`engine/navigate-remote.aye`): a `javascript:` URL for a remote frame or tab is not sent; the console error.
- the browser (`ui/navigate-proxy.aye`): a `javascript:` URL in `proxy_navigate` is dropped (`navigation refused` in the log); it is never sent as a `navigate`. Test hook `DWELLER_TEST_EVIL=javascript-url` (`renderer/windows-through.aye`): the renderer sends a `javascript:` URL in place of the URL of each `proxy_navigate`. `docs/process-model.md` §4 (the `proxy_*` row) says so. No IPC kind.
- gone: `followJavascriptNavigation`, `initiatorHref`, and the `javascript:` branches of `followFrameNavigation`, `pumpContexts` and the window's `afterScripts`. No navigation that a script asks for (`setNavigation`) holds a `javascript:` URL now, and these branches ran it with the target as its own source.
- `browser/tests/sandbox/javascript_url_targets.html` (Q3.16b, no test used it): removed; `javascript_url_into_frames.html` has its frame cases and also checks that the frame's document stays.

## Tests

`sandbox::javascript_url_into_frames_needs_same_origin` (`browser/tests/sandbox/javascript_url_into_frames.html`, `javascript_url_probe.html`): six frames, three of the page's origin and three of `localhost`. `window.open`, a link (`a.click()`) and `location` each aim `javascript:parent.postMessage('ran in ' + name, '*'); '<p>written</p>'` at one frame of each origin.
- same origin: `ran in open-same` (and `link-same`, `location-same`): the script ran in the frame, and the frame shows `written`;
- other origin: no `ran in`, and the frame's own script still answers `open-other: probe` (and `link-other`, `location-other`): no script ran and its document stayed;
- in the window with `DWELLER_PROCESS` `single`, `tab` and `site`, and once more in `site` with `DWELLER_TEST_EVIL=javascript-url`: the page sets the cross-origin frame's `location` to `blank.html`, its renderer sends a `javascript:` URL instead, the browser logs `navigation refused: javascript:...`, and the frame answers `probe` (the test checks both).

Before the fix:
- the test on `main` 7725655c (the engine, ui and renderer of `main`, this test): fails in `single` with `ran in location-other`, `ran in open-other`, no `open-other: probe` and no `location-other: probe` (both documents replaced by `written`), and `link-same: probe` (a link into a frame ran nothing). A build of `main` 9fc3fb84 printed the same in `tab`; in `site` it printed no `location-other: probe` (the frame was sent to the `javascript:` URL).
- a build of this branch without the browser's check (`navigate-proxy.aye` as on `main`): the evil run has no `location-other: probe`.
