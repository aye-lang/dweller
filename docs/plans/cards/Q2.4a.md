# Q2.4a: a renderer's loads go through the browser's net

- goal: with `DWELLER_PROCESS=tab`, every `net.request` a renderer makes (the document of a navigation, frames' documents, scripts, module scripts, styles, images, fonts, fetch/XHR, a worker's `fetch`) is a request message to the browser; the browser runs it through its one `net` session (its jar, cache, connections, HSTS, mixed content, CORS, ORB, PNA) with an initiator it sets itself, and streams the response back. The renderer has no `net` session of its own (`net.setRemote` stops it), so its background loader is off and every load takes the synchronous `request` path, which the remote hook answers. Cookies stay in the browser: `Set-Cookie` lines are taken out of the headers the renderer gets.
- design:
  - IPC messages added (type codes in order): 26 R→B `fetch{id, doc, nav, kind, credentials, mode, method, url, referrer, top, headers, content_type, has_body, body}`; 27 B→R `fetch_head{id, doc, status, tainted, mime, charset, url, headers}` (after net's CORS/ORB checks, without `Set-Cookie`); 28 B→R `fetch_body{id, chunk}` (256 KiB chunks, so a body of any size stays under the 1 MiB payload limit); 29 B→R `fetch_end{id}`; 30 B→R `fetch_fail{id, code}` (`net.fetchErrorCode` / `fetchErrorOf`). Kind, credentials and mode go as codes (`net.requestCode` / `codedRequest`).
  - the initiator is the browser's: the renderer never sends an origin or URL for it, only `doc`, a number the browser gave it. `doc` 0 is the tab's committed document (`tp.committed`); a document response for a frame gets the next number, with its final URL kept in `tp.docs`. A top-level navigation (`nav` 1, a Document with no `top`) gets `Initiator.Browser` only when the browser is waiting for one: it started the navigation (`tp.loading` and the URL matches the commit, `commitMatches`) or an acting agent request is outstanding (`agentCommitAllowed`); it then becomes the committed URL (its final URL after redirects) and the frame list starts again. Any other request gets `Initiator.Page` with the URL the browser holds for that `doc`.
  - the browser's checks (`answerFetch`, from `rendererSent` and the `dweller agent` relay's `askRenderer`; a failure logs `bad message: bad fetch PID` and kills the renderer): `fetch` on another frame id than the tab's (window), an id that is not the last one + 1, `nav`/`has_body` not 0 or 1, a `doc` the browser never gave, a kind/credentials/mode code out of range.
  - renderer: `fetchThrough` installs `fetchRemote` as net's remote hook. It sends `fetch` (finding the `doc` whose origin is the claimed initiator's in its list of frame documents, else 0) and reads the socket until the reply ends; other messages read meanwhile stay in `r.inbox`, which the loop (`serveOn`, `answerAll`) now handles one message at a time (each copied to `r.current` first, so the hook may append to the inbox while a message is handled).
  - window: `--until-idle` also waits for the tab's renderer (hello, no navigation loading, input acked: `rendererSettled`); `--text` under the flag asks the renderer (agent `wait` then `eval` of `document.documentElement.textContent`, `rendererText`); the `url` line of `--state` is the committed URL (`slotUrl`). `askRenderer` no longer drops what the outbox holds (fetch replies still to send).
  - test hook: `DWELLER_TEST_EVIL=initiator` (the renderer names doc 4096 for every page-initiated request).
- Chromium read: `services/network/url_loader.cc`, `services/network/public/mojom/url_loader_factory.mojom` and `network_context.mojom` (`URLLoaderFactoryParams.request_initiator_origin_lock`: a factory per frame with a fixed initiator lock; a request whose initiator does not match is refused and reported as a bad message), `content/browser/renderer_host/render_frame_host_impl.cc` (`CreateNetworkServiceDefaultFactoryAndObserve`: the browser makes the factory with the frame's committed origin). Dweller takes: the initiator comes from what the browser committed for that renderer (here a document number, not a factory per frame), and a request naming a document the renderer does not have kills it.
- files: `browser/ipc/{message,decode,put-payload,from-renderer,message_test}.aye`; `browser/net/net.aye`, new `browser/net/{set-remote,request-code,coded-request,coded-request_test,fetch-error-code,fetch-error-of}.aye`; `browser/renderer/{tab-renderer,serve-on,answer-all,load}.aye`, new `browser/renderer/{fetch-through,ask-fetch,await-fetch,take-fetched,fetched,fetched-response,doc-of}.aye`; `browser/ui/{tab-process,start-tab-process,end-tab-process,renderer-sent,ask-renderer,page-settled,script,window}.aye`, new `browser/ui/{answer-fetch,send-fetched,fetch-initiator,fetch-navigates,doc-count,headers-without-cookies,headers-without-cookies_test,renderer-settled,renderer-text}.aye`; `tests/browser.rs` (`window_login` split into `window_login_in`; new `window_login_in_renderer`, `window_renderer_net`; `login_window_with`).

## Status: done, 2026-11-08

Left:
- cancellation: a load is synchronous in the renderer (one outstanding request, the browser answers it at once), so nothing cancels yet; a `fetch_cancel` comes with asynchronous loads over IPC (the renderer's background loader, prefetch, `startRequest`), which are off under the flag: every load waits for its answer, and the window's loop runs the request while it answers.
- workers' module and classic scripts (`fetchLocal`, file: and data: only) still read in the renderer; a worker thread cannot use the tab's socket.
- the browser trusts the renderer's `referrer`, `top` (the site for cookies of a frame's requests), method and headers (forbidden headers are dropped in the page's JS, not in the browser); request bodies are bounded by the 1 MiB payload limit.
- `noteNavigation` (the Referer of a link's navigation) and `noteFrame` (a frame's top-level page for its subresources) live in the renderer's net, which has no session now: those requests go without them.
- `document.cookie`, `localStorage`, `sessionStorage`, IndexedDB: Q2.4b. The proof that a renderer opens no profile file: Q2.4c. Process swap: Q2.6.
