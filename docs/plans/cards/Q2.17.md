# Q2.17: a module's import may have the module's URL as its referrer in site mode

- goal: in site mode (the default) github's agent task fails 3 runs of 3: the browser refuses a renderer's `fetch` (`bad message: bad fetch`) and ends the session; in `DWELLER_PROCESS=single` it passes. Find the check, decide whether the request is legitimate, fix the right side, and make the refusal say which check fired.
- source: step Q2.16 of the queue (P1.S3 W2 notes, github row: the refusal is in `browser/ui/answer-fetch.aye`, reported by `relay-agent-main.aye:53`, which check is not logged). The id Q2.16 is the done row "Speed with the flag" (slices Q2.16a to Q2.16d), so this card is Q2.17.
- cause:
  - with each check named, the log says `bad fetch referrer`. The request: `https://github.githubassets.com/assets/xg-….js`, a script in CORS mode (an `import()`), asked by the document `https://github.com/rust-lang/rust` with the referrer `https://github.githubassets.com/assets/wp-runtime-….js`, the webpack runtime module that imports it.
  - the renderer is right: an import's referrer is the base URL of the module that imports it (HTML "fetch the descendants of a module script"; Blink `ModuleTreeLinker` passes `module_script->BaseUrl()`), and a style sheet's `@import` has the sheet's URL. On github that module is on another site than the page.
  - the browser's `referrerAllowed` (Q2.4d) let a referrer through only when it was of the asking document's origin, and killed the renderer otherwise. In one process there is no such check, so single mode passed.
  - the check is there because net used the referrer as the initiator in three places: a script's request (`hopRequest`) took its `Origin`, `Sec-Fetch-Site` and same-origin credentials from it, and every hop took the SameSite initiator (`Hop.from`, `http.aye`) from it. So letting a cross-origin referrer through alone would let a compromised renderer that loaded one script of a site send requests that look same-origin with that site.
- Chromium's rule: the network service takes `ResourceRequest::referrer` from the renderer as it is and only cuts it by the referrer policy (`services/network/url_loader_util.cc`: `url_request.SetReferrer(request.referrer.GetAsReferrer().spec())`; `net/url_request/url_request_job.cc` `ComputeReferrerForPolicy`). `CorsURLLoaderFactory::IsValidRequest` has no referrer check. What a compromised renderer must not forge is `request_initiator`, which is checked against `request_initiator_origin_lock` (`VerifyRequestInitiatorLock`); `Origin`, `Sec-Fetch-Site`, SameSite and CORS all come from it.
- fix:
  - `answer-fetch.aye`: each refusal names its check: `bad fetch id`, `flags`, `doc`, `kind`, `method`, `top`, `referrer`, `headers`.
  - the referrer may also be of the origin of a script or style sheet that the browser gave this renderer: `sendFetched` notes the origin of the final URL of every script and style sheet response (`note-referrer-origin.aye`, `TabProcess.referrer_origins`, one origin a line, kept for the renderer's life as its lock is) and `referrerAllowed` looks the referrer's origin up there. A referrer of any other origin still kills, as `DWELLER_TEST_EVIL=referrer` checks.
  - net takes the initiator from the request's initiator, the browser's record of the document, and the referrer only when the request names none (`requestOrigin`): `hop-request.aye`, `start-load-job.aye`, the two `Hop` of `loader.aye`, the SameSite initiator of `http.aye`. The referrer is now only the `Referer` header, as in Chromium. The site lock and the initiator check (`bad fetch doc`) are unchanged.
- tests:
  - new `window_renderer_loads::window_renderer_loads_import_referrer` (`browser/tests/net/import-referrer.html`): a module of the other test origin with a static and a dynamic import, a style sheet of the other origin with an `@import`, then a `fetch()` to the other origin that shows the `Origin` and `Sec-Fetch-Site` the server got. The same text in single mode, in site mode, and in site mode with the new hook `DWELLER_TEST_EVIL=script-referrer` (the renderer names the fetch's own URL, of the module's origin, as its referrer).
  - before the fix the site arm fails: `error: bad message: bad fetch PID`. With the check loosened but without the net part, the hook arm fails: `fetch origin is the page: false`, `fetch sec-fetch-site: same-origin`.
  - `window_renderer_net` and `window_renderer_site_lock` now expect the named reasons (`bad fetch doc`, `top`, `referrer`, `method`); `referrer-allowed_test.aye` adds the origins that were given.
- files: new `browser/ui/{note-referrer-origin,has-line}.aye`; `browser/ui/{answer-fetch,referrer-allowed,referrer-allowed_test,send-fetched,send-navigation,send-primed,finish-held,tab-process,new-tab-process,end-tab-process}.aye`; `browser/net/{hop-request,start-load-job,loader,http}.aye`; `browser/renderer/ask-fetch.aye` (the hook); `browser/tests/net/import-referrer.html` and `import-referrer/`; `tests/browser/{window_renderer,window_renderer_loads}.rs`; `docs/process-model.md` §4.
