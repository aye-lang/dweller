# Q3.4b: proceed past a certificate error per host, never on HSTS hosts

- goal: the certificate interstitial of Q3.4 gets "Advanced", then "Proceed to HOST (unsafe)", except on HSTS hosts (a stored `Strict-Transport-Security` header or the preload list), which have no bypass at all. Proceeding records a per-host, per-error-kind exception in the process's net session (not written to disk, like Chromium's in-memory exceptions per profile); later loads to that host with the same kind of error succeed; another process or profile asks again. The bypass covers the top-level navigation's host and subresources whose top-level page is on that same host. The expired page shows a wrong-clock hint when the clock check says so.
- design:
  - the action is browser chrome, not the page: the interstitial is still the engine's HTML page (`not-private.html`, no link or script), and `Page.cert` (`?net.CertKind`), set only by `notPrivatePage`, marks it. The window draws a bar under the toolbar (`ui/cert-bar.aye`, `draw-cert-bar.aye`, `cert-label.aye`) while `certPage` finds the tab's page with a `cert` on a host that `net.certBypassable` allows (not a Space). Its button says "Advanced"; a click (`cert-click.aye`, before the page gets the click) makes it "Proceed to HOST (unsafe)" (`Ui.cert_advanced`, reset by `navigated` and `showEarly`); a second click calls `net.allowCert(host, kind)` and reloads. Page scripts cannot reach the window's click handler or `allowCert`; a page that only looks like the interstitial has no `Page.cert`. `--state` prints `cert LABEL` while the bar is shown.
  - store: `net/cert-exceptions.aye` `CertExceptions` (a list of `CertException`: host, `CertKind`) in `Session.certs`. `allow-cert.aye` `allowCert` refuses HSTS hosts (`cert-bypassable.aye`, which uses `hstsKnown`) and works only with a session; `add-cert.aye` adds once; `cert-allowed.aye` looks up host and kind. `CertKind` (`cert-kind.aye`: Expired, Untrusted, WrongHost, Invalid) comes from a `FetchError` by `cert-kind-of.aye` and goes back by `cert-error.aye`. `TlsVersion` has no kind: no bypass, like Chromium's `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`.
  - applying it: `prepare` (http.aye) sets `Sink.cert_host` by `bypass-host.aye` `bypassHost`: the request's host when the session has exceptions, the host is not HSTS, and the request is a top-level navigation or its top-level page (`req.top`, else `frameTop` of the referrer, else the referrer) is on that host; else "". Every request is still verified strictly first. When it fails with CURLcode 51 or 60, `relax-tls.aye` `relaxTls` takes the kind (`tlsError`), and when `(cert_host, kind)` is allowed it turns off only that check (`CURLOPT_SSL_VERIFYHOST` 0 for WrongHost, `CURLOPT_SSL_VERIFYPEER` 0 for the others), at most twice per request (a self-signed cert for another host needs both), and the transfer runs again: `transfer` loops on `performShared`, the loader's `harvest` re-adds the handle to the multi handle (`retry-relaxed.aye`). An exception for one kind lets no other kind through, because the kind comes from the strict attempt.
  - why strict first: with `VERIFYPEER` 0 libcurl loads no CA store, so `CURLINFO_SSL_VERIFYRESULT` is 20 (no local issuer) for every CA-signed certificate (measured with curl 8.7.1: expired, wrong-host and valid servers all give 20 under `-k`). The kind cannot be checked on a relaxed connection, so the relaxed attempt only follows a strict one that showed the allowed kind. (A first try with `CURLOPT_PREREQFUNCTION` checking the verify result let an expired certificate through an Untrusted exception for that reason.)
  - wrong clock: `engine/clock-wrong.aye` `clockWrong(now_ms, built_ms)`: the clock is before the build time of the binary, or more than a year after it (Chromium's `GetClockState`). `build-time-ms.aye` takes the build time from the mtime of the executable (`argv[0]`); none (a bare name on the PATH) means no hint. `notPrivatePage` puts the hint (`<p id=clock>`, at `{clock}` in `not-private.html`) on an Expired page when `clockWrong(std.time.now(), buildTimeMs())`. The notBefore check is not needed here: a certificate whose notBefore is after the clock is reported as not yet valid (X509 error 9, `CertInvalid`), never as expired.
- files: new `browser/net/{cert-kind,cert-kind-of,cert-error,cert-exception,cert-exceptions,cert-allowed,add-cert,allow-cert,cert-bypassable,bypass-host,relax-tls,retry-relaxed,verify-kind}.aye`, `browser/net/cert-allowed_test.aye`, `browser/engine/{clock-wrong,build-time-ms}.aye`, `browser/engine/clock-wrong_test.aye`, `browser/ui/{cert-page,cert-label,cert-bar,draw-cert-bar,cert-click}.aye`; changed `browser/net/{http,loader,session,tls-error}.aye` (`verifyKind` moved out of `tlsError`), `browser/engine/{engine,not-private-page}.aye`, `browser/engine/not-private.html`, `browser/ui/{window,script,show-early}.aye`, `tests/browser.rs` (`cert_bypass`).
- Chromium files read:
  - `components/security_interstitials/content/stateful_ssl_host_state_delegate.cc` (`AllowCert`, `QueryPolicy`; the card named `chrome/browser/ssl/`, which now holds only its factory) and `components/security_interstitials/core/ssl_error_ui.cc` (`PopulateOverridableStrings`, `PopulateNonOverridableStrings`, `HandleCommand`, `hard_override_enabled_`): Dweller takes exceptions per host and error, in memory per profile, proceed as a browser command and no proceed on HSTS hosts.
  - `components/ssl_errors/error_classification.cc` (`GetClockState`: before the build time less 2 days is the past, after it plus 365 days the future): Dweller takes the build-time check without the 2 days (the card asked for "before the build time") and without the network time.

After that, the expired and the wrong-host servers on the same host still show the interstitial (another kind). Another process with another profile asks again. A page on the valid server whose script fetches the self-signed host gets `TypeError`, and no bar, with the same clicks. On `site.test` (HSTS from `hsts_server.py` stored in the profile, its certificate untrusted under the Q3.4 CA) the interstitial has no bar and the same two clicks change nothing; with a fresh profile the same clicks proceed to its page.
- left:
  - the exception is per host and kind, not per certificate (Chromium keys it by the certificate's fingerprint too): another certificate with the same kind of error on that host passes. Binding it needs the certificate (`CURLINFO_CERTINFO`) and `CURLOPT_PINNEDPUBLICKEY` with its SPKI hash.
  - the relaxed retry is a second handshake; a server that changes its certificate between the two is not checked again.
  - an HSTS header received over a bypassed connection is stored (Chromium ignores it there); it only makes the host stricter.
  - the bar is not keyboard-reachable (Tab), and the page body does not repeat "Advanced"; the interstitial shows no "HSTS: you cannot visit HOST right now" line.
  - no window test across hosts (the test servers are all 127.0.0.1); `bypassHost` decides it.
