# Q5.7: WebSocket through the browser's network

- goal: `WebSocket` as in the WebSockets standard (https://websockets.spec.whatwg.org/) over RFC 6455, with the connection in the browser process in all three process modes. Row Q5.7 of `foundations.md` (F1, Chromium `modules/websockets/`, `services/network/websocket.cc`).
- facts found first (2026-11-16):
  - No `WebSocket` anywhere in `browser/` (grep of the preludes). CSP `connect-src` has no WebSocket request to gate (Q3.8 Left), `Sec-Fetch-*` has no `websocket` mode (Q3.14 Left).
  - libcurl's own WebSocket API is not usable: the Linux system libcurl (8.5.0, Ubuntu 24.04) is built without the `ws`/`wss` protocols (`curl --version`: not in the list), and the header's `curl_ws_*` functions fail on it. So, by code-taste rule 6 (std, then the linked C libraries): libcurl makes the connection (`CURLOPT_CONNECT_ONLY`, on the loader's multi handle, so DNS, TLS, the test CA, `DWELLER_RESOLVE`, the proxy environment and the partition's share are the ones every request has), and the opening handshake and the frames go through `curl_easy_send`/`curl_easy_recv`; SHA-1, base64 and the random key and masks are `std.crypto` and `std.encoding`.
  - No script API delivers anything before a response ends (Q5.8's card): a socket needs its own events from net to the page. Workers are the precedent for work that is open-ended without a queued task (`engine/wait-workers.aye`).
  - With `DWELLER_PROCESS=tab|site` the renderer has no socket (`docs/process-model.md` §1): it asks over IPC, as fetch does (`renderer/start-remote.aye`, `ui/answer-fetch.aye`).
- slices (each with its verify; one commit each):
  1. The protocol, pure (`net/`): the handshake request and the check of its response (`Sec-WebSocket-Accept`, the chosen subprotocol), the frame writer (masked) and the incremental frame reader (fragments, control frames inside a fragmented message, close code and reason, the protocol errors of RFC 6455 §5 and §7.4). Verify: Aye unit tests (`aye test browser`).
  2. The connection in net and the API in one process: `net.socketOpen/Send/Close/Next/Release` on the loader's multi handle; `ak.socketOpen/Send/Close`, `engine/websocket.js` (`WebSocket`, `CloseEvent`; `MessageEvent` exists), events delivered as tasks, the headless loops wait while a socket is alive. Cookies and `Origin` as for a request; `Set-Cookie` of the handshake stored. Verify: a `/ws-echo` route of `browser/tests/server.py`, `dump` golden `net/websocket.{html,txt}` (text, binary, subprotocol, close code and reason, a refused handshake, a cookie sent).
  3. `DWELLER_PROCESS=tab|site`: IPC kinds 140 `SocketOpen`, 141 `SocketSend`, 142 `SocketClose` (R→B), 143 `SocketOpened`, 144 `SocketMessage`, 145 `SocketClosed` (B→R); the browser checks the URL scheme, the claimed document and the site lock as `answerFetch` does, and ends a renderer's sockets with it. Verify: slice 2's page in the window with `DWELLER_PROCESS=site` and `tab`, the same lines.
  4. The gates and the WPT area: CSP `connect-src` (with `ws:`/`wss:` and `'self'` matching as CSP3 says), mixed content (`ws:` from an `https:` page is a `SecurityError`), `Sec-Fetch-Mode: websocket`; area `websockets` in `wpt_areas.json` (upstream server, fixed `ws`/`wss` ports in `wpt_upstream`), its score and the largest clusters. Verify: `wpt.py run websockets`, the floor set at the measured score.
  5. (if 4 leaves room) `WebSocket` in dedicated workers (`engine/workers/`), `bufferedAmount` from the bytes net has not written, `permessage-deflate` (zlib is linked).
- decisions (nobody to ask; the plan's defaults):
  - No `permessage-deflate` offered in slices 1 to 4: `extensions` is `""`, as the standard allows a client without it. Chromium offers it; a server never requires it.
  - A message larger than 16 MiB (the subresource limit of `net/http.aye`) fails the connection with 1009.
  - A socket does not keep `dump` alive forever: the headless loop waits for sockets as for workers, at most 5 s without any socket event.
  - Redirects of the handshake are not followed (the standard: redirect mode "error").
- references: RFC 6455; the WebSockets standard; Chromium `net/websockets/websocket_frame_parser.cc`, `websocket_channel.cc` (the close handshake and the failure codes), `third_party/blink/renderer/modules/websockets/dom_websocket.cc` (the API's argument checks and the event order).

- design as built:
  - Protocol, pure (`net/`): `socket-key`, `socket-accept`, `socket-request`, `socket-response` (the handshake), `frame`, `read-frame`, `put-frame`, `assembly`, `take-frame`, `close-of`, `close-code-valid` (the frames). Tests `read-frame_test.aye`, `socket-response_test.aye`.
  - Connection (`net/socket*.aye`, `pump-sockets`, `connect-socket`, `harvest-sockets`, ...): a socket is a `Job` of `multi.aye` (so `prepare` gives it the request's cookies, `Authorization`, TLS settings, `DWELLER_RESOLVE` and the partition's share, and `secureHref` its HSTS and mixed-content rules) with `CURLOPT_CONNECT_ONLY` and HTTP/1.1, on a multi handle of its own (255 connections; the loader's has 6 per host, which 25 sockets to one host exceed). One handshake at a time per host and port (Chromium `websocket_endpoint_lock_manager.cc`): the others stay `Queued`. `pumpLoads` pumps the sockets first. Events are `SocketNote`s (opened, text, binary, closed) that `socketNext` hands out. `Origin` is always sent; `Accept`, `Referer` and `Sec-Fetch-*` are not (as Chromium); URL credentials become `Authorization: Basic`; Fetch's bad ports fail.
  - Page (`engine/`): `ak.socketOpen/Send/Close/Buffered`, `websocket.js` right after the prelude (trusted events). `pumpPageSockets` turns notes into tasks; `waitSockets` is the workers' hook for the headless loops (5 s without a note ends the wait; the virtual clock moves by the time waited, so a test that measures a server's delay sees it); `socketWait` caps the window's wait at `LOAD_POLL_MS` while a page has a socket; `ui/page-settled.aye` counts live sockets, so `--until-idle` waits for them.
  - Renderer modes: IPC 140 `SocketOpen{id, doc, url, protocols}`, 141 `SocketSend{id, binary, more, data}`, 142 `SocketClose{id, code, reason}` (R→B), 143 `SocketNote{id, kind, clean, code, more, data}` (B→R; one kind for opened, messages and closed instead of the three planned). Messages over 256 KiB go in chunks (`more`). The browser (`ui/*tab-socket*.aye`, `answer-sockets.aye`) checks the id, the document, the scheme, the fragment, the subprotocol tokens, the close code and the reason's length (`bad socket` kills the renderer), takes the referrer and top from its own record, allows 255 sockets per renderer and ends them with it. Written into `docs/process-model.md` §2.
  - Gates: CSP `connect-src` in `akSocketOpen` (a refused socket fails as a network error: `error` then `close` 1006). Mixed content is `secureHref`'s: `ws:` from an `https:` page fails the same way (the Fetch standard; Chromium throws `SecurityError` in the constructor: Left).
  - Tools: `browser/tests/server.py` `/ws/` (echo with test commands); `wpt_upstream.py` gives `wpt serve` fixed `ws`/`wss` ports (8666, 8667), resolves them and `www.not-web-platform.test`, and waits for them at start (the first tests of a run failed to connect before the WebSocket server listened); area `websockets` in `wpt_areas.json`.

- 2026-11-19, a race found by a whole-suite run of Q5.9a (`websocket_echo_in_renderers` printed `close while connecting: clean=true code=1005` once): with a renderer, the browser could finish the handshake before the page's `close()` reached it, and then closed cleanly. The standard fails a connection that is closed before it is established, whatever the network did meanwhile: `websocket.js` now remembers that `close()` came while connecting and reports `error` and `close` 1006.
