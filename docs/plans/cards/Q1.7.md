# Q1.7: stop a runaway script

- goal: a page with `while(1){}` no longer freezes the window for good. After 5 s in one script task the window shows a bar "This page is not responding" with Wait and Stop. Wait gives the script 5 s more. Stop ends the script, and the tab keeps working.
- cause: P11.24b decided that the window gives a page task no budget. A task over 10 s showed "A page task ran for N s" only after it ended, so a task without end never gave control back.
- design:
  - The check was already in the VM: `Interp.tick` runs on every `JumpLoop` (loop back-edge) and every call. Every 1024 ticks it calls `checkBudget`, which calls the `goes_on` hook. This is V8's interrupt budget in `JumpLoop`. The hot path does not change: no new instruction in `tick` or in `vmLoop`.
  - No watchdog thread. The brief asked for a flag that another thread sets. But the flag is read only at the same tick points, so a thread would stop a script no sooner than reading the clock there does. A thread would add a start and a stop for each task, and atomics. `pageGoesOn` (`engine/page-goes-on.aye`) reads `time.monotonicMs()` once per 1024 ticks.
  - `engine.Script` gets `hang_at`. `enter` sets it to the task start + 5 s for a window page (`s.real`). A window page's `Interp` gets `goes_on = pageGoesOn` when it is made. Past `hang_at`, inside a task (`depth > 0`), `pageGoesOn` calls the hook that the window set (`engine.setHangHook`). It then sets `hang_at` to now + 5 s (Wait) or returns false (Stop). False makes `checkBudget` set `terminated` and throw `JsError.Terminated`.
  - The hook is `ui/ask-stuck.aye`, a small event pump on the window thread while the script waits on the stack. It sets `ui.stuck`, draws the window once with the bar (`draw-stuck-bar.aye`, rects in `stuck-bar.aye`), then reads the scripted words (`resumeScript`) and SDL events until there is an answer. While `ui.stuck` is set, `Ui.handle` sends every event to `stuckInput` (`stuck-input.aye`): a click on Wait or Stop answers, the window's close answers Stop and quits, and other input is dropped. No timer, layout or page event runs in the pump. After the answer it draws the window again without the bar. `--state` prints `unresponsive N` (the bar was shown N times).
  - Termination semantics, the same as V8's `TerminateExecution`: `vmUnwind` gives no `catch` and no `finally` handler a `Terminated` (V8: `Isolate::UnwindAndFindHandler`, `if (!catchable_by_js) break;` for each JS frame, and a `finally` is a catch handler in bytecode). `terminated` stays set until the outermost call returns, so the other listeners of the same dispatch end at once. The next task's `startBudget` clears it. The console gets "Script terminated: it ran too long", as for the other budgets.
  - Workers and agent `run` realms are not changed: they have their own `Interp` and budget (`run-in-realm.aye` sets its own `goes_on`). `dump` and the agent (the virtual clock) keep the step budget.
- files: `browser/engine/{page-goes-on,set-hang-hook}.aye` (new), `browser/engine/script.aye`, `browser/ui/{ask-stuck,stuck-bar,draw-stuck-bar,stuck-input}.aye` (new), `browser/ui/window.aye`, `browser/ui/script.aye`, `browser/tests/ui/stuck.html` (new), `tests/browser.rs` (`window_stuck_script`)
- verify: `window_stuck_script`: a click starts `try { while (1) {} } catch { log } finally { log }`. Wait at 5 s, Stop at 10 s. `--state` has `unresponsive 2`. The log is `start hang after`: no `caught` and no `finally`, and the click on the second button ran. `cargo test --release --test browser -- window_ js_conformance`, `aye test browser`, `aye check browser` and `check_taste.py` pass. jsbench is within 2% (see Status).
- limits: native work that does not tick (a long regexp or one huge `sort`) is not interrupted. That is the same as before, and a watchdog thread would not interrupt it either. The pump reads `--events` words with `resumeScript`, which goes on until a `frame` word. So a test puts `frame` after the Wait or Stop click. Without it, the next click goes to the page while the stopped script is still on the stack.

## Status: done, 2026-11-04

- `window_ js_conformance`: 66 passed. `aye test browser`: 157 passed. `aye check browser` and `check_taste.py`: exit 0.
- jsbench, fast build, 5 runs interleaved with the build of origin/main (`BENCH_BASELINE`): geometric mean speedup 1.003. `dom` read 0.96 in that run; again with 9 runs it read 1.00 (2.669 s before, 2.671 s after). It runs `dump`, which this change does not touch. The other benchmarks run `dweller js`, which has no `Script` and no hook.
- The bar was checked by eye: a PNG of the window while the pump waits shows the bar under the toolbar, with the text on the left and Wait and Stop on the right.
