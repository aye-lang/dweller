# Q4.10: image decode off the main thread, decoded-image budget

- goal: the window does not decode images on its main thread, the decoded pixels come back as a task, and decoded pixels are held under a size budget (foundations.md, Q4 table, row Q4.10).
- cause: `fetchImage` (`browser/engine/images.aye`) decoded every image (`image.decode`) on the thread that fetched it, inside layout's image pass, and the decoded pixels of every image stayed in `ImageCache` for the life of the page, with no bound.
- design:
  - Only a window's page decodes later (`decodesLater`: the top page's `ImageCache.background`, so frames follow their window). `dump`, `shot` and tests stay synchronous, so goldens do not change.
  - Sizes first: `image.headerSize` reads width and height from the PNG, GIF, JPEG (SOF marker) and WebP (VP8, VP8L, VP8X) header. The cache entry gets a `Bitmap` of that size with no pixels, layout runs with the right box, and the encoded bytes are kept in `CachedImage.encoded`. A format without a readable header decodes synchronously as before.
  - Decode pool: two threads (`DECODE_THREADS`), started on first use (`decodePoolOf`), fed by one `Channel(*mut DecodeJob)`. A job decodes into its own `std.heap.General`, so the decode threads never touch the page allocator; it sets `done` when finished. `stopDecoding` closes the channel and joins the threads at exit.
  - The task back: `landDecodes` runs on the main thread from `imagesIn` (the window's image pass) and before the last frame of `--save`. It copies a finished job's pixels into the cache's bitmap (`takePixels`, only when the size matches the header), bumps `version` so paint uploads it again, and sets `landed`; the view relists and repaints. `decodesPending` keeps the page from settling and keeps the loop's poll at `LOAD_POLL_MS` while decodes are out. Canvas `drawImage` waits for its source's decode (`waitDecode`).
  - Budget: 256 MB of decoded pixels per `ImageCache` (`DECODED_BUDGET`). After decodes land, `evictDecoded` frees the least recently used bitmap (`CachedImage.used`, set by `touchImage` on every `bitmapOf`) until the total is under the budget. An image is not evicted when it has no encoded bytes to decode again, is being decoded, or is still mapped from an element or a CSS URL in `layout.Images` (`usesBitmap`). An evicted image keeps its size; the next `bitmapOf` starts its decode again.
  - Cancel: `ImageCache.deinit` marks its jobs cancelled and waits for them, so a job never writes into a freed bitmap.

- Chromium files read:
  - `third_party/blink/renderer/platform/graphics/image_decoding_store.cc`: one store of decoded images with a byte limit, `Prune` walks the LRU list from the least recently used and skips entries in use; Dweller takes the LRU walk and the in-use skip (its "in use" is mapped in `layout.Images` or being decoded).
  - `cc/tiles/software_image_decode_cache.cc`, `gpu_image_decode_cache.h`, `tile_task_manager.h`: decodes run as tasks on worker threads and the result is handed back to the compositor; Dweller takes the worker-thread decode and the main-thread landing, not the per-tile scheduling.
