# Q5.6: Downloads (`Content-Disposition`, the `download` attribute, a downloads list)

- goal: a response that is an attachment, and a link with a `download` attribute, are saved to the downloads directory instead of replacing the page, in all three process modes; the browser keeps a list. Row Q5.6 of `foundations.md` (F1, Chromium `components/download/`, `chrome/browser/download/`).
- facts found first (2026-11-16):
  - Nothing about downloads existed. A top-level response of any MIME type was decoded as text and parsed as HTML (`engine.aye` `pageOf`, `documentOf`): a zip showed as garbage.
  - `HTMLAnchorElement.download` is reflected already (`reflection-table.js`); `allow-downloads` is parsed into `SB_DOWNLOADS` and nothing reads it.
  - No navigation could end without a new page: `fetchPage` always returns a `Page`, and with a renderer the browser has announced the new history entry before the response (`beginNavigation`, `Ui.go`). No 204 handling either.
  - There is no internal page scheme (`about:` is "not supported"), no history file; the profile holds `cookies`, `hsts`, `storage/`, `session`.
  - WPT has no download tests in the checkout (`html/semantics/links/downloading-resources` needs testdriver and a download directory).
- slices:
  1. (done) The header and the name, pure (`net/`): `dispositionAttaches`, `dispositionName` (RFC 6266: `filename*` of RFC 8187 in UTF-8 or ISO-8859-1 before `filename`, quoted strings with escapes), `downloadName` (the header, then the attribute, then the URL's last segment, then `download`), `safeFileName` (no path separators, control characters or leading and trailing dots and spaces). Verify: `net/download-name_test.aye`.
  2. (done) The store and the interception (`net/`): `takeDownload` in `net.request` for a document request whose response is an attachment or was noted by `noteDownload` (status under 400): the body goes to `DWELLER_DOWNLOADS` or `$HOME/Downloads` under a free name (`name (1).ext`), the entry to `<profile>/downloads` (state, size, path, URL per line), and the request ends with `FetchError.Downloaded` (code 19). `about:downloads` (asked by the browser, not by a page) lists the entries, newest first. `--state` prints `downloads N`.
  3. (done) The page stays (`engine/`, `ui/`, `renderer/`): `fetchPage` answers `Downloaded` with a marked placeholder page that `Tab.navigate`, `navigateEarly` and the renderer's `load` drop, keeping the document, its history and (in the renderer) the shared session history it had. `activate` notes the download of a same-origin `http(s)` link with `download` (IPC 144 `DownloadHint{url, name}` from a renderer; the browser checks the scheme, the name's length and the site lock). With a renderer the browser saves the file when the navigation's response arrives (`sendNavigation`, or `net.request` in `answerFetch`), answers the renderer's fetch with `FetchFail{19}` and takes the navigation back (`keepAfterDownload`: `loading`, `committed`, the entry `Ui.go` pushed for a typed URL, the session history it had announced).
  4. (left) `blob:` and `data:` links with `download` (what scripts use to save generated files): the bytes are the renderer's, so they go to the browser over IPC in chunks.
  5. (left) A body streamed to the file as it arrives, with progress and cancel: today the body is in memory, so a download is limited as a document is (32 MiB, `MAX_DOCUMENT`) and ends in 30 s (`TIMEOUT_MS`).
  6. (left) A place in the window's chrome (a button or a shelf) that opens `about:downloads`; today it is a URL to type.
- decisions (nobody to ask; the plan's defaults):
  - The header's file name wins over the attribute's, also when the type is `inline` (Chromium). A cross-origin link with `download` navigates as a plain link (Chromium ignores the attribute's name there and downloads only an attachment).
  - No prompt and no dangerous-file check: every download is saved at once, as Chromium does for a user-started download of a safe type. A script can start one without a gesture (Chromium asks before the second automatic download): Left.
  - A status of 400 or more is not a download: the error page shows.
  - `IPC`: one kind, 144.
