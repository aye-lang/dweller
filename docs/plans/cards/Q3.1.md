# Q3.1: a web page cannot read or show a local file

- goal: an http, https, data:, blob: or about: page can never read or show a `file:` URL. fetch rejects with TypeError, XHR fires `error`, img, script, link and iframe fail as network errors, and `location`, `window.open` and a link click to `file:` show no byte of the file. A `file:` page still loads `file:` subresources, and a `file:` URL the browser is given (address bar, command line, agent `navigate`, history) still opens.
- cause: `requestLive` (net/net.aye) read `file:` for any request; `fetchWith` (engine/window_api.aye) only refused methods other than GET and HEAD. An http page could read a local file with XHR, run it with `<script>`, apply it with `<link>`, frame it, and navigate to it with `location`, `window.open` or a link.
- design:
  - `net.Request.initiator`: the URL of the document that asks; `""` for the browser. `net/initiator-may-load.aye` `initiatorMayLoad(initiator, target)`: a `file:` target only for the browser or a `file:` initiator (Chromium `CanRequestURL`: `file:` is not a web-safe scheme). `net.request` checks it first and fails with `FetchError.Network`; `net.fetchLocal` (the workers' `file:` and `data:` loads, which do not go through `request`) checks it too. Every other renderer load is http(s) only (`startLoad`, `startRequest`, redirects), so these two are the only ways to a `file:` read.
  - `engine/initiator-of.aye` `initiatorOf(page)`: the URL of the page's origin page (`about:blank` and `about:srcdoc` take their parent's, as `sameOrigin` does).
  - Subresources (fetch, XHR, script, module, sheet, image, font, worker fetch) set `initiator`. Navigations carry it: `fetchPage`, `loadWith`, `loadParsed`, `navigateFrame`, `Tab.navigate`, `Tab.navigateEarly`, `navigateTo`, `ui.go`, the agent's `goTo` and `loadInFrame` take it, and `ContextRequest` keeps it (owned) for window.open and links to other tabs. Browser-initiated loads pass `""`.
  - A refused navigation commits the usual network-error page at the `file:` URL (as Chromium's browser-side check commits `about:blank#blocked`); it shows why the load failed, never the file. Not starting the navigation at all (Blink's renderer-side `CanDisplay`) is not done.
  - `freeContextRequest` moved to `engine/free-context-request.aye` (it grew past 5 lines).
- files: `browser/net/{net,fetch-local,initiator-may-load}.aye`, `browser/engine/{initiator-of,free-context-request,engine,tab,frames,forms,contexts,windows,window_api,inserted,script,images,fonts,sheets,wk-fetch,traverse-early,submit-form-into-frame}.aye`, `browser/engine/workers/{load-bytes,worker-module-response}.aye`, `browser/js/module-response.aye`, `browser/ui/{window,forms}.aye`, `browser/agent/{actions,scripts}.aye`, `browser/tests/no-file/`, `tests/browser.rs`
- verify: `scripts/capped.sh cargo test --release --test browser -- no_file_from_web` passes; it failed before the fix (the http page read the file by XHR, ran it as a script, applied it as a sheet, framed it, and every navigation showed it). Near tests in one run (`fixtures worker_ window_login http fetch xhr frame form scripts history web_font_files data_urls errors agent_sessions storage_between_tabs`): 57 of 58 pass; `worker_canvas` needs ANGLE, which this worktree does not have (`browser/gpu/fetch_angle.sh`). `aye check browser` and `python3 browser/tools/check_taste.py` pass.
