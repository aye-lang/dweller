- goal: `navigator.serviceWorker.register`, `getRegistration(s)`,
  `ready`, `controller`; `ServiceWorkerRegistration` (`installing`,
  `waiting`, `active`, `update`, `unregister`, `updatefound`);
  `ServiceWorker` (`state`, `statechange`, `postMessage`); in the

- verify: WPT `service-workers/service-worker` (upstream server), 0

## Design

Chromium keeps registrations, versions and their states in the browser
(`content/browser/service_worker/service_worker_registry.cc`,
`service_worker_version.cc`, `service_worker_controllee_request_handler.cc`)
and runs the worker's script in a renderer
(`third_party/blink/renderer/modules/service_worker/`). Dweller:

- `browser/serviceworker/` (browser process): per storage key the
  registrations (scope, script URL), each with up to three versions
  (installing, waiting, active: id, script text, state), the clients
  (pages) and which version controls each, and the rules that move a
  version on: installed -> activating when no client is controlled by
  the active version or after `skipWaiting`; `claim` moves the matching
  clients to the version. One text call (`ak.sw(request) -> reply`) and
  event lines per client, as IndexedDB (`cards/Q5.11a.md`).
- The worker's script runs in a hidden page of the client's renderer
  (`Page.worker_page`), not in a worker thread: the dedicated-worker
  scope has no `Request`, `Response`, `Headers` or events and its
  `fetch` blocks its page, while a page has all of them. A page that
  registers a worker hosts the instance that gets `install` and
  `activate`; a controlled page hosts an instance of its controller,
  started without those events (as a worker restarted after it was
  stopped). So one version may run in several pages at once: a worker
  must not rely on its globals between events (the specification lets
  the browser stop it between any two), so only code that counts
  instances can tell. `document` and `window` stay visible in the
  worker's global (Left).
- Interception is one hook in `net.request` (and the three background
  starts of `net/loader.aye`), before the renderer's remote hook, so it
  works the same in every process mode: a request whose initiator is a
  controlled page, or a navigation into a scope with an active worker,
  is handed to the instance; the engine runs that hidden page's tasks
  (timers, microtasks, its own loads) until `respondWith` settles; no
  `respondWith` falls through to the network. The instance's own
  requests are not intercepted.
- IPC: none new. The call and its events ride the IndexedDB channel
  (160 `Idb`, 161 `IdbReply`, 162 `IdbEvent`): a request whose first
  line is `sw` goes to the registry, and its event lines start with
  `sw`. The storage key comes from the committed document; scope and
  script URL must be of that origin (checked in the browser).

## Slices

1. The registry (`browser/serviceworker/`): register, versions and
   states, activation rule, unregister, match by scope, clients,
   control, claim. Verify: unit tests.
2. Page API: `ak.sw`, events; `ServiceWorkerContainer`,
   `ServiceWorkerRegistration`, `ServiceWorker`. Verify:
   `serviceworker_register` (states reach `activated`, `ready`
   resolves, `unregister`).
3. The instance: the hidden page, the worker global (`install`,
   `activate`, `waitUntil`, `skipWaiting`, `registration`,
   `importScripts`). Part of slice 2's verify.
4. Fetch: the net hook, `FetchEvent`, `respondWith`, fallback, the
   controller of a navigation. Verify: `serviceworker_fetch`.
5. Messages and clients: `postMessage` both ways, `clients.matchAll`,
   `claim`, `controllerchange`. Verify: `serviceworker_clients`.
6. Processes and the profile: the `sw` requests over 160-162, checks, the saved
   registrations. Verify: `window_renderer_serviceworker` (`tab`,
   `site`), `serviceworker_profile`.
7. WPT: the area's score, the largest clusters, the baseline.
