# Q4.29: a renderer's socket holds 512 KiB, so a response no longer reaches the page 8 KiB a window iteration (youtube-search's 9 s timer task)

- goal: on youtube-search (archive `target/sites/youtube-search`) the renderer ran one `timers` task of about 9.0 s on the results page in site mode (W7 notes, 2026-11-24). With `DWELLER_PROCESS=single` the same page's `ui_timers` is about 824 ms. Find why site mode is about 11 times slower and fix the cause.
- method: `browser/build.sh` (safe) at 888e5c91 plus PR #432/#433 (`origin/n23-Q4.28b`, not yet on main), and the same plus the fix. This Mac (M2 Pro, load 2–6). `window_perf.py report --replay --site youtube-search` (the brief's `page_load.py report` is this command), with `--process site` or with `DWELLER_PROCESS=single`. For the profile: `window_perf.py scroll` with the report's renderer step and `--log`, `DWELLER_REPLAY`, `DWELLER_PROCESS=site`; a macOS `sample` of the renderer and of the window for 12 s during it; a build with three temporary timing records (the window's writes to the renderer's socket, each answered fetch with its body size, each renderer `fetchRemote`), not committed. Logs: `target/q429-*` in the worktree.

## Profile (base build)

- The hypotheses first. (a) is not it: the renderer runs due timers as the window does, `runDueTimersUntil(p, now + 50 ms)` in both (`TIMER_TASK_MS` and `TASK_BUDGET_MS` are 50), and the task is one callback of 3.7 s, not many short ones. (c) is not it: the JS VM is at the top of the stack in about 0.5 s of the 12 s sample.
- (b) is it. The renderer's main thread in the 12 s sample: 7241 ms in `runTimers`, of it 5691 ms in `__recvmsg`: a timer → JS → `scriptRun` (`akScriptRun`, `engine/inserted.aye`) → `net.request` → `fetchRemote` → `awaitFetch` → `ipc.recvFds`. The script asked for its source at once and waited for the browser's answer.
- Why the script fetches in the task: YouTube inserts `www.google.com/js/th/….js` (64 KB). Under replay `net.liveRequest` is false, so `scriptFetch` starts no background load and `scriptRun` fetches it in the task. In the window's own process that is a read of the archive.
- Why the answer takes seconds. With the timing records, that fetch took 9702 ms in a 9799 ms task. Meanwhile the window ran 2526 loop iterations (2.3 ms of work each on average; the rest of the time it waits in `SDL_WaitEventTimeout`, as the window's sample shows: 4325 of 8900 samples) and wrote the renderer's socket 2525 times. `serviceTabProcess` writes the outbox once an iteration, as much as the socket takes. A macOS AF_UNIX socket holds 8 KiB (`net.local.stream.sendspace` and `recvspace` 8192), so each iteration moved about 8 KiB: about 4 MB/s. The page's answers are one ordered stream: the 64 KB script waited behind the bodies asked for before it. In a second run the window queued seven 2.9 MB YouTube Sans fonts (20 MB) just before the script's answer, and the fetch took 3649 ms.
- The load task waits the same way: 5.9 s of the renderer's 9.2 s sample was `finishStaged` → `pumpRemote` → `poll` for the load's responses, 10.9 MB (`kevlar_base` script), 3.8 MB (its CSS) and 1.7 MB (the page) among them.
- The slow socket also made the renderer ask again: the same scripts 2 or 3 times (`kevlar_base` 10.9 MB twice, its CSS twice), 83 answers and 55.3 MB of bodies in the run. With the fix: 69 answers, 43.8 MB, none twice.
- An experiment with the existing test hook (`DWELLER_TEST=1 DWELLER_TEST_SOCKET_BUFFER=N`, both ends): 512 KiB: renderer task 1984 ms (the load), the `js/th` fetch 69 ms, 410 writes in the run; 2 MiB: 1950 ms, 15 ms, 376 writes.

## Cause

- The browser hands a renderer every response over the renderer's socket, writes it once a window loop iteration, and macOS gives the socket 8 KiB. So a renderer gets its responses at about 4 MB/s, and a task that fetches synchronously waits for every body before its own. Site mode only: in one process the page reads the cache or archive directly.

## Fix

- The window gives each renderer socket send and receive buffers of 512 KiB at both ends (`sizeRendererChannel`, `ui/size-renderer-channel.aye`) when it makes it (`startTabProcess`, and `attachTabProcess` for a popup in its opener's renderer). 512 KiB is Chromium's default response body data pipe (`services/network/public/cpp/loading_params.cc`, `kDefaultDataPipeAllocationSize`). The setsockopt loop of the test hook moved to `setSocketBuffers` (`ui/set-socket-buffers.aye`), which both use; the hook still sets its size after, so tests that shrink the buffers keep working. Linux caps the request at `net.core.wmem_max`, by default the 208 KiB it gave before.
- `docs/process-model.md` §2 (Transport) says so.
- test: `window_renderer_perf_large_body` (`tests/browser/window_renderer_perf.rs`, page `browser/tests/perf/large_body.html`, server `/big?16`): a page fetches a 16 MiB body and must have it in under 2 s, in the run's `DWELLER_PROCESS`. Base: 4629 ms, fails. Fix: 159 ms (default, site mode), 100 ms (`DWELLER_PROCESS=single`).

## Left

- The longest renderer task on youtube-search is the replay load, 2.0 s. Under replay `stageLoad` finishes a load in one task (`finishStaged`, as for every load that `net.liveRequest` refuses), so its scripts run back to back; a live load runs one script a task (Q4.25d). Stepping it would still leave `kevlar_base`'s own 1.5 s (parse 0.7 s). Done in Q0.3f: the replayed load steps, and the longest task is now `kevlar_base` (1.6 s).
- Wheel p95 468–477 ms and idle 85% still fail Q4.25's criterion. They are the page's own timers (0.2–0.8 s tasks with forced layout), as in single mode (scroll p95 425 ms, idle 99.7%).
- The decoder process's socket (`startDecoderProcess`) still has 8 KiB buffers and is written once a loop iteration too. Not measured here.
- The window still writes a renderer's socket only once a loop iteration (Chromium writes on its IO thread). With 512 KiB the 16 MiB test body takes 159 ms against 100 ms in one process, so this is no longer what a page waits for.
