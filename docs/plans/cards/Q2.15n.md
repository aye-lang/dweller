# Q2.15n: `opener`, the window name and the popup's reference across renderers

- goal: readiness list for Q2.14, "Logins and popups", second bullet [Q2.3f, Q2.11, Q2.12]: "`opener`, named targets and popup openers across renderers". A popup that keeps its opener and is of another site (the usual sign-in window) ran in a renderer of its own with `opener` null and no name, so the page it ends on could not hand the result back. Now both ends have a proxy of the other across processes, and the way back to the opener's site ends in the opener's process.
- slices (all done):
  1. A cross-site popup has a home too (`AttachFrom.home`, set by `attachSource` whenever the opener is kept): when it navigates to its opener's site, Q2.15m's `rejoinHome` commits it in the opener's process, in the context the opener made, so `opener`, the name and synchronous scripting are there.
  2. The name and the opener reach a popup's own renderer: `context` (64) carries the context's `name`; the browser keeps the opener's tab id and the name on the slot (`TabSlot.opener`, `name`) and, before each navigation of a process that is not the home process, sends 91 `opener_info{frame, name}` (`tellOpener`). The renderer gives the tab's new context that name and a remote opener (`BrowsingContext.remote_opener`); `window.opener` is then the remote window of that tab (`remoteWindowValue`, the proxy Q2.11 made for frames).
  3. Messages and navigation between the two. The opener's renderer learns which tab shows a context it opened (92 `context_tab{context, frame}`, `BrowsingContext.remote_tab`); while that context has no page in this process, its window object routes like a remote window (`routeOf`): `postMessage` becomes 51 and `location.href = ...` becomes 55, addressed to the popup's tab. The browser (`postTarget` → `relatedTab`) accepts a top-level target outside the sender's tab only when one is the opener of the other (`TabProcess.opener_tab`, from the browser's own record), in the same partition, live, and not a speculative process; everything else is dropped as before. The receiver's `event.source` is its own reference: in the popup the same object as `window.opener`, in the opener the object `window.open` returned (`remoteSource` → `contextOfTab`).
- decisions: no new routing message; 51 and 55 keep their checks (source origin hosted by the sender, target origin against the target's committed origin, `allow-top-navigation` for a sandboxed sender, `initiatorMayLoad`). The relation is checked on the browser's records only; a renderer names a tab id and gets nothing unless that tab is its opener or its popup. A popup at home gets no `opener_info` (its opener is a local context).
- Chromium read (over HTTPS from `main`): `content/browser/renderer_host/render_frame_host_manager.cc` (`CreateOpenerProxies`: before a frame commits in a process, that process gets proxies of its opener chain), `content/browser/renderer_host/render_frame_proxy_host.cc` (`RouteMessageEvent`, `OpenURL`: a proxy forwards `postMessage` and navigations to the browser, which checks and routes them), `third_party/blink/renderer/core/frame/remote_dom_window.cc`. Taken: a proxy of the opener in the popup's process and of the popup in the opener's, `postMessage` and navigation through the browser, the replicated name. Not taken: proxies for the rest of the browsing context group (only the opener and its direct popups), `closed` and `focus()` of a remote opener, the replicated origin for `targetOrigin` errors.
- IPC: 91 `opener_info{frame, name}` B→R; 92 `context_tab{context, frame}` B→R; `context` (64) gained the trailing field `name` (at most 4096 bytes, else `bad context`).
- files: new `browser/ui/{tell-opener,tell-context-tab,related-tab}.aye`, `browser/engine/{set-context-tab,set-remote-opener,context-of-tab}.aye`; changed `browser/ipc/{message,decode,put-payload,from-renderer,edit_test,context-closed_test}.aye`, `browser/engine/{contexts,windows,route-of,remote-source}.aye`, `browser/renderer/{send-contexts,answer-all,load,tab-renderer,new-tab-renderer}.aye`, `browser/ui/{open-ask,attach-from,attach-source,attach-slot,opened-slot,serve-open-requests,take-context,tabs,end-slot,tab-process,queue-navigate,navigate-speculative,start-speculative,service-speculative,post-target}.aye`; tests `tests/browser/window_renderer_popup.rs`, pages `browser/tests/ui/popup_{opener,child}.html`.

## Status: done, 2026-11-16

Left:
- Only an opener and its direct popups know each other across processes: a named target is found from the opener (its context table) but not from a sibling popup or from the popup's own renderer (`window.open('', 'opener-name')`).
- A remote opener's `closed` is always false and `focus()`, `blur()` and `close()` on it do nothing; a popup does not learn that its opener's tab closed.
- An opener that leaves its process and returns gets a fresh context, so its popups' proxies of it keep pointing at its tab (messages still arrive) but a popup at home loses `opener` (Q2.15m's Left).
- `window.name` set by the popup's page later is not sent back to the opener's process; a popup that returns home gets the name the opener gave.
- `MessagePort` transfer in these messages: Q2.15o.
