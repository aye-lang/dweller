# Q2.14j: the paint tests with a renderer per site

- goal: the `paint::` tests of the suite pass with `DWELLER_PROCESS=site`. At the start 13 of 22 failed: they count relayouts, display-list builds, composited frames, damage and window pixels, and compare `--state` after wheels.
- source: the integrator's list of 2026-11-19 for lane proc-speed (Q2.14, the flip; Q2.14h and the other failures are lane proc-tests').
- rows (cause → change):
  1. `window_frame_lists_reused`, `window_transform_composite`, `window_css_animation`, `window_css_transition`: the renderer built one flat list per frame with `paint.build`. → It now uses the window's page-view code: `TabRenderer.lists` is a `pageview.PageView` (its `tab` is a `Tab` made by `newViewTab`, with no browsing context, that only carries the page and the scroll). `keepList` keeps the list (Q2.16c's conditions; a scroll that moved fixed or sticky boxes keeps it when `paint.followPinned` can), else `pageview.noteAnimated` and `pageview.composite` (the changed boxes are patched as layers: record `ui_composite`), else `pageview.buildList` (`paint.buildPromoted` with the cached lists of the frames: record `ui_relayout`); then `engine.markPainted` and `engine.afterLayout`, which the renderer never called. `composite` and `noteAnimated` are now `pub`. `drawDamage` rasters with a `paint.RasterCache` (`TabRenderer.layers`, cleared with the buffers and the page) and writes `ui_layers KEPT DRAWN`.
  2. `window_css_animation`, `window_css_transition`, and `scripts::window_raf_vsync`, `scripts::window_hidden_raf`: the renderer ran animation-frame callbacks as 16 ms timers. → `runAnimationFrame` (from `runTimers`) is the window's step: `engine.runAnimationFrames` once per 16.67 ms frame while one is requested, record `ui_raf`; `frameWait` gives `timerWait` the time to the next frame.
  3. `window_canvas_raf_no_relayout`: the renderer wrote `ui_relayout` for every frame. → only when the list was built (`notePaintStep`).
  4. `window_relayout_floats`, `window_relayout_attr`, `window_width_animation`: a staged load (Q2.16a) showed a local file before its scripts ran, so the page's full layout came after its first frame. → `stageLoad` finishes the load at once when the document is not fetched from the network (`!net.liveRequest`: a file, a replayed archive), as the window's own process does. In the tests, "after the first frame" is now the first `ui_draw` after the page's first layout (`page_first_draw`): the window draws its toolbar before the renderer's first frame; in the window's own process that is the same frame as before.
  5. `window_damage_rect_only`: `scroll_info` (Q4.25e), `settled` and `pong` marked the window dirty, so it composed all of itself for a renderer frame of 1344 px. → `changesChrome`: those and `frame`, `input_ack` do not. `takeScrollInfo` no longer damages the whole tab when nothing was shifted. With a renderer the caret is the renderer's, so the window has no overlay and presents the page's texture (no `ui_window_px` record): the test checks in that mode that the last frame that drew pixels drew the 1344 px alone.
  6. `window_idle_no_raster`: the script word `painted` passed before the renderer's first frame, and the `frame` words after it were used up while the page loaded. → `painted` also waits while the tab's renderer has shown no frame of the loaded page (`rendererUnpainted`).
  7. `window_framesets`, `window_scroll_positions`: with the event script's automatic waits, a `move` after a `wheel` ran before the wheel was sent, so the wheel went to the new pointer position (the menu frame; the fixed link was hovered at the old scroll). → the script sends a pending wheel before its next input word (`script.aye`), then waits for its ack as for any input.
- not fixed: `window_fractional_scroll` (one row): it wants a scroll to draw only the strip that came into view (the window's own process moves the old pixels, P4.36). The renderer draws its whole buffer on a scroll and the window copies all of it. That is Q4.25e's next slice (the taller buffer and the scroll by offset); the test stays red in site mode until then.
