# Q6.10: WPT `html/semantics/forms` to its floor

- goal: the area reaches its floor of 60 plus 2 points (54.3 in the table; 2936/5413, 54.2%, measured at the start of this card).
- causes, largest first (subtests are of the area's 5413):
  - an input's value was sanitized for `color` and `range` only, and only when set; changing `type` did nothing to the value (`type-change-state` 214, `-weekmonth` 66, and the validity, `number`, `time`, `week`, `datetime-local`, `valueMode` files).
  - `showPicker()` did not exist (`show-picker-*`: 133).
- design:
  - `input.value = v` from script runs the value sanitization algorithm of the input's type (`engine/sanitized-input.aye`, `is-scalar-input.aye`): newlines are stripped, `email` and `url` are trimmed, and `number`, `date`, `time`, `datetime-local`, `month`, `week` become the empty string when `dom.scalar` cannot parse them. Typing is not changed: the edit path calls `dom.setValue` directly, so a half-typed number stays.
  - in the default and default/on modes (`hidden`, `submit`, `image`, `reset`, `button`, `checkbox`, `radio`) the setter writes the `value` attribute and clears the dirty flag (`engine/default-mode-input.aye`, `controlSetValue` in `dom_api.aye`).
  - the `type` setter (prelude.aye, after the reflected accessor) follows "input type change": from a value-mode type to a default-mode one, a non-empty value becomes the `value` attribute; from a default-mode type to a value-mode one, the value is the attribute's; between value-mode types a dirty value is sanitized again and a clean one stays clean (`ak.valueDirty`, `engine/ak-value-dirty.aye`); the selection is kept when the value did not change and reset to the start otherwise.
  - `HTMLInputElement.prototype.showPicker` and `HTMLSelectElement.prototype.showPicker`: `InvalidStateError` when the control is disabled or read-only (where `readonly` applies), `NotAllowedError` without transient activation, which the call consumes. No picker opens.
- two fixtures asserted the old behaviour and were changed, with their goldens blessed after reading the diff (only the line of script text echoed in the tree changed; the result lines are the same):
  - `browser/tests/jsdom/forms_html5.html`: `date.value = '2023-02-29'` was expected to stay and be invalid. By the sanitization algorithm it is the empty string and the control is valid; the assertion is now `date.value === '' && date.checkValidity()`.
  - `browser/tests/jsdom/forms_types.html`: six values that do not parse (`1900-02-29`, `2024-13-01`, `24:00`, `2024-02-30T12:30`, `2024-00`, `2021-W53`) go through a new helper `cleared()` with the same assertion. The step and range cases of that fixture are untouched.
  - This is what WPT checks (`form-validation-validity-valueMissing`, `number.html`, `time-2.html`), and it means a script can no longer see `badInput`-like state by assigning a bad string; a user typing one still can.
