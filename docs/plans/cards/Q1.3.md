# Q1.3: window tests count the page's ticks, not frames

- goal: no test that runs the window with `--frames` depends on how many frames fit in wall time. A page that animates stops its loop after a fixed number of ticks, and its test runs `--frames <cap> --until-idle` (TC3k). A failure must not bounce a PR out of the merge queue because the runner was slow.
- cause: twice on 11-04 a `window_*` test failed on the slower Ubuntu runner because it needed a count of rAF ticks inside a fixed `--frames N`, and the load and a slow machine take frames from it: `window_container_queries` (60 ticks in 90 frames, fixed in #267) and `window_relayout_floats` (30 relayouts in 40 frames, fixed on #268). rAF runs at most once a loop iteration and at most once a display period (`run-animation-frame.aye`), so ticks per drawn frame fall when iterations get slow. The opposite does not hold: an idle iteration waits up to 10 ms (8 ms while the page loads), so N frames are at least N × 8 ms of wall time, and a slower machine only adds time. A test that needs one timer tick or one held load inside a large N is safe.
- design: every test in `tests/browser.rs` that passes `--frames` (by `grep`), directly or through `window_log`, `console_of` or `login_window`, classified:
  - (a) safe: the assertion does not need page work to finish within N frames, or N gives several times the wall time it needs.
  - (b) at risk: the assertion needs a count of rAF ticks, composites or relayouts within N frames, or a wall-clock CSS animation's frames, or HTTP loads within a small N (30-40 frames, at least 0.24 s).
  - (b) changed: the page loop stops after a fixed number of ticks (it already did in most), and the test runs `--frames <cap> --until-idle`. The two CSS tests are the exception, see below.

- why the CSS tests keep a fixed N: a CSS animation or transition runs on the wall clock, and the assertion needs 50 idle frames after its end (to show that no more animation frames run). `--until-idle` ends the run 3 iterations after the end, so it cannot keep that assertion. Instead the durations are doubled, so the frames counted during the animation fit at up to 80 ms (animation) or 60 ms (transition) a frame. The cap is 300, so 50 idle frames still come after the end at 10 ms a frame. The thresholds (15 composites, 10 damaged frames, 50 idle frames) are unchanged.
