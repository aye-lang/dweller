# Q2.13c: the renderer gives freed memory back at idle moments (a no-op on this Mac's malloc)

## Status: done, 2026-11-26

- goal: Q2.13a and Q2.13b cut live data, but the renderer's macOS footprint rose, because malloc keeps freed pages dirty and they count (Q2.13a: the malloc large cache held 400 to 500 MB of youtube-search; Q2.13b: youtube-search 1733 → 2277 MB, small-block dirty pages 632–743 → 956–988 MB). Give freed memory back to the OS at the right moments, never inside a frame or task, then decide #448 (Q2.13a) with numbers.

## Design

- `engine.releaseFreeMemory` (`engine/release-free-memory.aye`): macOS `malloc_zone_pressure_relief(NULL, 0)`, Linux (glibc) `malloc_trim(0)`, elsewhere nothing.
- what asks for a release (`wantRelease`): the window's load event (`fireWindowLoad`), a style rebuild that dropped sheets (`dropStyling`; a parsed source that leaves the cache, `dropParsed`), a page that turns hidden (`setHidden`).
- when it runs (`engine.releaseWhenIdle(wait)`, `engine/release-when-idle.aye`): the loop calls it with the time it is about to wait, just before it blocks: the renderer in `pollTabs` (no message waiting, so between two `r_task`s), the window's loop (single mode) before `SDL_WaitEventTimeout`. It releases only when asked, when the wait is not 0 (a due timer, frame, staged load or message makes it 0), and at most once in 2 s; inside the 2 s it shortens the wait to their end, so that a release asked for is not lost while the loop sleeps; after a release it shortens the wait by the call's time. A `release_free_memory` record (`DWELLER_TIMING`) times each call. As PartitionAlloc's reclaimer (`memory_reclaimer.cc`), on the main thread, outside tasks.

## What this Mac's malloc does

- this Mac (arm64, macOS 26.5): the default zone is xzone malloc (zone version 16, `free` is `xzm_malloc_zone_free`), and its `pressure_relief` is `malloc_zone_pressure_relief_fallback`, which frees nothing and returns 0.
- a C test (session scratchpad, `q213c/relief.c`): 40 blocks of 12 MB written and freed: footprint 481.8 MB, `vmmap` `MALLOC_LARGE (empty)` 480 MB in 40 regions; then `malloc_zone_pressure_relief(NULL, 0)`: 0 B in 1 µs, still 481.8 MB. The same with the zone's own function, with `malloc_memory_event_handler` and every memorystatus bit, and with `MallocXzoneHugeCacheSize=0`, `MallocXzoneDeferLarge=0`/`1`, `MallocXzoneDeferSmall=0` or `MallocSecureAllocator=0` at start. Only `MallocLargeCache=0` at start gives them back (1.0 MB after the frees). Small blocks (1500 B, 1 in 64 kept) go back without a call (1112 → 138 MB).
- in the renderer: 0 B a call (a scratch build that logged the result).
- youtube and youtube-search never reach an idle moment in the load + 10 s: their renderer runs tasks for 12.2 to 12.7 s of it (`r_task`), and its wait is 0 at every `pollTabs`, so no release runs there (by the design above).

## Cost per call

- 36 calls in the branch runs below (and branch + #448): 0 µs 30 times, 1 µs 3 times, 4 µs 3 times (the record's clock has 1 µs steps). Each call is outside a task: `pollTabs` runs between two `r_task`s.
- W7 (`window_perf.py report --replay --process site --site youtube-search`, one run each): base loop 13 ms, wheel-to-frame p50/p95 122.9/440.2 ms, idle 86.2%, longest task 1506 ms; branch 13 ms, 122.4/418.4 ms, 86.3%, 1531 ms. No frame worse (FAIL on p95 in both, as on main).

## #448

- **merge #448 after Q2.13c** (with the `Sheet.parts` fix above): on top of this branch it lowers every one of the 5 sites: youtube-search 2284–2314 → 2090, youtube 1689–1736 → 1452, mistral 1698–1711 → 1601, zol 558–569 → 545, github 1204–1224 → 1088 MB; and with the large cache off, 1384 → 1267. Q2.13a's rise (1625–1782 → 2063–2113 on youtube-search) came with 22 parses of `kevlar_base` a load, each leaving its freed list buffers in the large cache; since #450 there are 3.

## Tests

- `perf::free_memory_released_after_load_at_most_every_two_seconds` (new): after its load event a page swaps a `style` element's text 35 times, every 100 ms, reading `getComputedStyle` each time, then sets its title. The window and its renderer must log at least one `release_free_memory` and at most 1 + (run ms / 2000), with `DWELLER_PROCESS=single` and in site mode. Passes; with the 2 s limit taken out it fails (`single: 35 releases in 4189 ms`).
