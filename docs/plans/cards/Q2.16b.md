# Q2.16b: the window is woken by libcurl's and the renderers' sockets, not by a 2 ms poll

- goal: with `DWELLER_PROCESS=tab` or `site`, the browser's window loop no longer wakes every 2 ms while a renderer's fetch is held (Q2.4e and Q2.12b left: `HELD_POLL_MS`). It sleeps in SDL and is woken when a socket of libcurl or of a renderer is ready.
- source: the readiness list of Q2, "Speed with the flag", second bullet; `docs/process-model.md` §2 "Rules" (an IO thread polls the renderer sockets and pushes an SDL user event).
- design:
  - net: `waitsOfLoads()` gives what the loader waits for (`LoadWaits`: up to 32 sockets from `curl_multi_fdset`, whether each waits to write, and libcurl's timeout from `curl_multi_timeout`, at most 1 s, 50 ms when libcurl has work without a socket). `waitLoadsOr(fd, ms)` is `curl_multi_poll` with one more descriptor, for a loop that blocks outside SDL.
  - ui: `IoWaker` (one, `io_waker`; started by the first `armWaker` of a window with the flag): a thread (`runWaker`) polls a pipe and the set the main thread gave it; when a descriptor of the set is ready or the timeout passed it pushes an SDL user event (`WAKE_EVENT`, 0x8000; `SDL_PushEvent` is thread-safe) and then waits on the pipe alone until it is armed again. `armWaker` (before each `SDL_WaitEventTimeout`) collects the set (`wakerFds`: the socket of every live renderer of `tab_processes`, children and popups included, for reading, and for writing while its out buffer is not empty; libcurl's sockets) and tells the thread only when the thread fired, the set changed or libcurl's deadline moved earlier (`sameWakerSet`, 2 ms slack), under `IoWaker.lock`, with one byte on the pipe (`told` keeps it to one). `handle` ignores the wake event. `stopWaker` (before `SDL_Quit`) stops and joins the thread and frees the waker.
  - `tabProcessTimeout` no longer returns `HELD_POLL_MS` when the waker runs. The fallback waits stay (15 ms while a renderer is busy), so a missed wake costs at most what it cost before.
  - the agent relay's blocking loop (`askRenderer`) waits with `net.waitLoadsOr(tp.fd, 100)` instead of 2 ms reads.
  - the thread touches no page state and no allocator: it reads its set under the lock and calls `poll`, `read` and `SDL_PushEvent`.
- Chromium read: `content/browser/browser_thread_impl.cc` and `content/browser/browser_main_loop.cc` (the IO thread owns the channel and network sockets and posts tasks to the UI thread), `net/socket/socket_posix.cc` (`ReadIfReady`/`WriteIfReady`: a watcher on the fd instead of a timer). Dweller takes: one thread that only watches descriptors and wakes the main loop, which still does all the work.
- files: new `browser/net/{load-waits,waits-of-loads,wait-loads-or}.aye`; new `browser/ui/{io-waker,start-waker,run-waker,take-waker-set,arm-waker,same-waker-set,waker-fds,stop-waker}.aye`, `browser/ui/{window,sdl,tab-process-timeout,ask-renderer}.aye`; `tests/browser/window_renderer_loads.rs` (new `window_renderer_loads_held_not_polled`), `tests/browser/window_renderer_oopif_input.rs` (below).

## Status: done, 2026-11-16

Left:
- the fallback waits stay: 15 ms while a renderer loads, shows no frame yet, has unacked input or an open ping (`tabProcessTimeout`), 15 ms while an agent socket listens. With the waker they could be seconds; each needs its own check that nothing else relies on the poll (hang timeouts, `--events` words).
- the waker is for windows with the flag. The window's own process still polls its loads at 8 ms (`LOAD_POLL_MS`), and a Space process waits in `waitInSpace`.
- at most 96 descriptors and 32 libcurl sockets are watched; the rest are seen at the fallback waits. A descriptor above 1023 is not in libcurl's `fd_set`.
- the agent sockets (`pollAgents`) are not in the set.
- macOS: `fd_set` is read as a bitmap of 1024 bits, the same layout there; not run on a Mac.
