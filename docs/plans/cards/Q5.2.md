# Q5.2: `prefers-color-scheme: dark`, a dark UA sheet, and `color-scheme`

- goal: a page sees the preferred color scheme (`prefers-color-scheme`, `matchMedia`), opts in with `color-scheme` or `<meta name="color-scheme">`, and then the canvas, the default text and link colors, the system colors, `light-dark()` and the form controls are dark, as in Chromium. Row Q5.2 of `foundations.md`. Measured by the WPT area `css/css-color-adjust` (added by this card) and by tests of `browser/tests/` in one process and with `DWELLER_PROCESS=site`.
- facts found first (2026-11-16):
  - `css/media.aye` answers `prefers-color-scheme` with `light` always. `light-dark(a, b)` parses to `a` and the system colors to their light values, both at parse time (`values.aye` `colorValue`, `systemColor`), as `Value.Rgba`.
  - There is no `color-scheme` property and no `<meta name="color-scheme">` handling. The UA sheet (`css/ua.aye`) writes the control colors as literals (`color: black`, `background-color: white`, `#efefef`, `#767676`); the initial `color` is black; the canvas is white under the root's and body's background (`paint.aye` `canvasBackground`, `WHITE`).
  - SDL2 (the window's library) has no call for the system's appearance (SDL3 has `SDL_GetSystemTheme`). So the preference comes from a setting of the process; following macOS needs `AppleInterfaceStyle` and is for the Mac queue.
  - Chromium: `core/css/media_query_evaluator.cc` (`PreferredColorScheme`), `core/css/resolver/style_adjuster.cc` and `style_resolver` (the used color scheme from `color-scheme`, the page's supported schemes from the meta tag), `core/layout/layout_theme.cc` `DefaultSystemColor` (the dark values: Canvas #121212, CanvasText #ffffff, LinkText #9e9eff, VisitedText #d0adf0, ButtonFace #6b6b6b, ButtonBorder #6b6b6b, ButtonText #ffffff, Field #3b3b3b, FieldText #ffffff, GrayText #808080), `core/html/resources/html.css` (controls written with `light-dark()` and system colors; that is the "dark UA sheet": there is no second sheet).
- slices:
  1. The preferred color scheme. `DWELLER_COLOR_SCHEME=dark|light` sets it for the process (a renderer inherits the environment, so no IPC); `prefers-color-scheme` and `matchMedia` answer by it. Verify: a unit test of the media query, a page of `browser/tests/` dumped with both settings, and in the window with `DWELLER_PROCESS=site`.
  2. `color-scheme` as a property (inherited; `normal | [light | dark | <custom-ident>]+ && only?`), `<meta name="color-scheme">`, and the used color scheme of an element (the preferred one when the element supports it, else the first supported of light and dark, else light). Verify: `css/css-color-adjust/parsing`, `getComputedStyle`, the page of slice 1.
  3. Colors by the used scheme: system colors and `light-dark()` in color properties resolve when the style is computed; the initial `color` is CanvasText; the canvas under a dark root is Canvas; the UA sheet's controls and links use system colors. Verify: the WPT area's reftests, a window screenshot test with the dark setting.
  4. What paint draws itself in a dark scheme: scrollbars, check boxes, radio buttons, the select arrow, the caret. Verify: a screenshot test.
  5. Frames: an iframe's canvas is opaque when its used scheme differs from its owner's. Verify: the WPT area's `rendering/dark-color-scheme` frame tests.
- defaults taken (nobody to ask): the preference is light unless `DWELLER_COLOR_SCHEME=dark`; no setting in the browser's own UI and no live change while pages run (both need a way to tell renderers, IPC range 130–139, and a UI decision); the browser's own UI stays light.

## Done (slices 1 to 4, 2026-11-16)

- slice 1: `css.setPrefersDark` (`css/preferred-scheme.aye`), set once in `main` from `DWELLER_COLOR_SCHEME` (every process kind starts there, a renderer inherits the environment); `media.aye` answers `prefers-color-scheme` by it, and `matchMedia` with it.
- slice 2: the property `color-scheme` (`css/color-scheme-value.aye`: the grammar of the spec, `only` serialized last, `normal`/`default`/CSS-wide keywords refused in a list; also checked for an inline style), `css.metaColorScheme` (the first `<meta name="color-scheme">` before `body` whose content has no comma), `css.usedDark(list, page)`: dark when the list (or, for `normal`, the page's) has `dark` and either the preference is dark or the list has no `light`. `print-color-adjust` and `forced-color-adjust` exist as inherited keyword properties with no effect (the area's inheritance and parsing tests).
- slice 3: a color that depends on the scheme is a new specified value, `Value.Schemed { light, dark }` (two packed RGBA, so `Value` does not grow): a system color with a dark value (`dark-system-color.aye`, Chromium's `DefaultSystemColor`) or `light-dark(a, b)` of two plain colors, made by `schemeColorValue` for color longhands and the `border` shorthand. `computeValues` finds the element's used scheme first and resolves it (`scheme-resolved.aye`); a computed style never holds `Schemed`. The initial `color` is CanvasText of the used scheme (`initial-of.aye`: the root without a declaration, `initial`, `unset`). The canvas under the root is #121212 when the root's used scheme is dark (`paint/canvas-base.aye`). The UA sheet's controls use `fieldtext`, `field`, `buttonface`, `light-dark(#767676, #858585)` and links `linktext`: the light values are the old literals.
- slice 4 (part): check boxes and radio buttons are filled with the dark Field and edged #858585 in a dark used scheme (`paint/control-dark.aye`).
- decisions: colors inside shadows, gradients, SVG paint and other shorthands keep the light value of `light-dark()` and of system colors (they are parsed by `colorValue`, which stays light); a keyframe's scheme color is not interpolated. The preference is one per process.
- shared numbers: CSS properties appended at the end: `color-scheme`, `print-color-adjust`, `forced-color-adjust` (the integrator renumbers at the merge; `gen_property_ids.py` run). No IPC kind, no host object tag. `wpt_areas.json`: the area `css/css-color-adjust` (floor 0.0, the integrator's to set).

## Slice 5, frames: what stays of the first attempt (2026-11-19)

- kept (verified with the whole suite on the merged tree, 315/315): the preference can be per document. `css.Media.dark` and `css.Styles.dark` (null: the process's preference, `css.prefersDarkOf`), `css.usedDarkBy(list, page, prefers)`; `prefers-color-scheme`, the cascade's used scheme, the canvas and the controls read it; `Page.prefers_dark` goes into every `css.Media` the engine builds for a page; `engine/same-dark.aye` in two reuse checks. Nothing sets `Page.prefers_dark` yet, so behaviour is unchanged.
- taken out: giving a frame its `iframe` element's used scheme at the frame's layout (`note-frame-scheme.aye`), and its test page. A test page served over http showed why it is the wrong place: a frame's `load` scripts run before the embedder first lays it out, so they still saw the process's preference. (The earlier "contentDocument is null" was the test page: frames from `file:` are cross-origin.)
- to do: set `Page.prefers_dark` when the frame's page is created (`engine/frames.aye` `placeFrame`/`framedDocument`), from the embedder's style of the element (the embedder may have no styling yet at that point: compute the element's style on demand), and again with a restyle of the frame when the element's used scheme changes; then the canvas rule and out-of-process frames.
