# Q1.8: a JS heap limit in bytes; out of memory ends the page, not the browser

- goal: a page that allocates without end no longer takes the machine's memory or the window with it. When its JS heap is over the limit after a full collection, its scripts end with the uncatchable termination of Q1.7, and the tab shows "This page ran out of memory" with a Reload link. The window and the other tabs live. With `DWELLER_PROCESS=tab` the renderer does the same and tells the browser (no crash).
- cause: `js/gc.aye` paced collections only by the count of values (`threshold`, twice the live count). Nothing counted bytes, so a loop of big strings or ArrayBuffers grew until the process was killed.
- design:
  - Byte count, two parts. `Heap.live_bytes` is exact: `sweep` sums `objBytes` / `strBytes` / `envBytes` (`js/live-bytes.aye`) over the cells it keeps. This is the memory the GC owns: each cell, its property and element slabs, a Map/Set key index, an ArrayBuffer's own store (not an external WebAssembly memory), a string's owned bytes, an environment's slots (a closure is an object plus its environment). `Heap.bytes_since_gc` is the cheap part on the allocation path: one add in `newObj`, `cell`, `concat`, `flatten`, `newEnv`, the growth of props and elements, and `ArrayBuffer`. It counts what was taken, not what was given back. The next sweep sets it to 0.
  - The value-count pacing does not change (perf). `Interp.maybeGc` also collects when `live_bytes + bytes_since_gc` passes `limit_bytes`. That collection is the last-chance full GC (V8: `NearHeapLimitCallback`, then `FatalProcessOutOfMemory("Ineffective mark-compacts near heap limit")` in `heap.cc`). If `live_bytes` is still over the limit after it, the sweep sets `Heap.out_of_memory` (it stays set) and `Interp.terminated`. The next `tick` throws `JsError.Terminated`, so no `catch` or `finally` runs. `startBudget` starts every later task as terminated, so the page's timers and events end at once until the page is replaced.
  - Limit: a fixed 4 GB per tab. This is V8's old-generation ceiling on 64-bit (the 4 GB pointer-compression cage, `Heap::AllocatorLimitOnMaxOldGenerationSize`), and Chrome's desktop renderers reach that ceiling on any machine with 16 GB or more. A fraction of RAM would need a RAM query for each OS and would give the same number on today's machines. `DWELLER_JS_HEAP_LIMIT=<bytes>` overrides it (`js/heap-limit.aye`), for tests.
  - The console says "Script terminated: out of memory" (`engine/terminated-why.aye`). `engine.outOfMemoryPage` is a failure page with the same URL: `<h1>This page ran out of memory</h1>` and a Reload link to the URL. The window (`ui/show-out-of-memory.aye`, once in each loop iteration after `showLongTask`) calls `engine.endOutOfMemory(tab)`. If the shown page's heap is out of memory, it puts that page in its place (`Tab.show` destroys the old page and frees its heap) and lays it out (`navigated(true)`). The history is not changed.
  - Renderer: `reportPage` (after each load, input batch and timer run) calls `endOutOfMemory` (`renderer/end-out-of-memory.aye`). It adopts the same page, paints it, and sends the new IPC message `OutOfMemory` (kind 42, no payload). The browser keeps the renderer and shows the title "Out of memory" (`renderer-sent.aye`).
- Chromium files: `gin/v8_initializer.cc`, `v8/src/heap/heap.cc` (`InvokeNearHeapLimitCallback`, `FatalProcessOutOfMemory`, `AllocatorLimitOnMaxOldGenerationSize`), `chrome/browser/ui/sad_tab.cc` (`IDS_SAD_TAB_OOM_TITLE`). What Dweller takes: V8's 4 GB limit and its one last full GC near the limit. Where Chrome kills the renderer and the browser shows a sad tab, Dweller ends only the scripts, because its heap belongs to the page and not to the process.
- files: `browser/js/{heap-limit,live-bytes,live-bytes_test}.aye` (new), `browser/js/{heap,gc,interp,typed}.aye`, `browser/engine/{page-out-of-memory,out-of-memory-page,end-out-of-memory,terminated-why}.aye` (new), `browser/engine/script.aye`, `browser/ipc/{message,decode,put-payload,from-renderer,message_test}.aye`, `browser/renderer/end-out-of-memory.aye` (new), `browser/renderer/report-page.aye`, `browser/ui/show-out-of-memory.aye` (new), `browser/ui/{window,renderer-sent}.aye`, `browser/tests/ui/{out-of-memory,allocate-and-free}.html` (new), `tests/browser.rs` (`window_out_of_memory`, `window_renderer_out_of_memory`)
- verify: `live-bytes_test.aye`: a 100 kB string, a 50000-element array and a 200 kB ArrayBuffer add at least their bytes to `live_bytes` and less than twice that. After they are dropped and collected, the bytes are gone. A loop that makes 100 MB of garbage strings under a 4 MB limit does not run out. A loop that keeps strings ends with `Terminated` and `out_of_memory`. `window_out_of_memory` (64 MB limit): the console has the termination, a second tab runs `allocate-and-free.html` to "freed 40000", and the first tab shows the error page. `window_renderer_out_of_memory`: the renderer line is `title Out of memory`, not `gone`.

- left:
  - Only the top page's heap is checked. A frame or a worker that runs out of memory ends its own scripts (the same flag and termination) but gets no error page.
  - A background tab that runs out of memory gets its error page only when it is shown. Its scripts end at once until then.
  - Near the limit, a page that keeps its heap just under the limit while it makes garbage collects often (every `limit - live` bytes). V8 ends such a page ("ineffective mark-compacts"). Dweller does not.
  - Native memory that is not in the JS heap (DOM nodes, layout, images, canvas) does not count toward the limit.
