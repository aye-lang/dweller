# Q3.4: TLS policy set explicitly, bad certificates get an interstitial

- goal: every request verifies the peer and the host name, refuses TLS older than 1.2 and uses a known CA store, whatever the linked libcurl defaults to. A top-level navigation to a host with a bad certificate shows "Your connection is not private" with the host and the reason, and no bypass. Frames, subresources, fetch and XHR fail as network errors. The agent's navigate result says why.
- cause: no TLS option was set anywhere (`grep -rn 'SSL_VERIFY\|CAINFO\|SSLVERSION' browser` found nothing), so verification and the minimum version were what each platform's libcurl build chose. Every TLS failure was one `FetchError.Tls` ("the secure connection failed (TLS)"), shown on the generic error page.
- what the linked libcurl uses (found 2026-11-04):
  - macOS: `/usr/lib/libcurl.4.dylib`, curl 8.7.1, MultiSSL with SecureTransport and LibreSSL 3.3.6. LibreSSL is the backend in use (`curl -V` puts the unused one, SecureTransport, in parentheses; the error texts are LibreSSL's). `curl_version_info` and `CURLINFO_CAINFO` give the built-in CA file `/etc/ssl/cert.pem` (Apple's bundle), no CA path. `curl-config --ca` prints nothing. The system keychain is not consulted (that happens only with SecureTransport, selected by `CURL_SSL_BACKEND=secure-transport`).
  - Ubuntu 24.04 (CI, `libcurl4-openssl-dev`): curl 8.5.0 with OpenSSL 3.0. Debian builds it with `--with-ca-bundle=/etc/ssl/certs/ca-certificates.crt` and `--with-ca-path=/etc/ssl/certs`. Not checked by running it here; the `tls_errors` test on CI shows that verification and the reasons work there.
  - Both have a built-in CA store, so `CURLOPT_CAINFO`/`CAPATH` are not set (an explicit path would only copy the default and break on another distribution).
- design:
  - `net/set-tls.aye` `setTls`, called by `prepare` (http.aye), which both the synchronous path (`transfer`) and the loader (`multi.aye` `startJob`) use: `CURLOPT_SSL_VERIFYPEER` 1, `CURLOPT_SSL_VERIFYHOST` 2, `CURLOPT_SSLVERSION` `CURL_SSLVERSION_TLSv1_2`, and `CURLOPT_ERRORBUFFER` into the new `Sink.error_text`. `DWELLER_TEST_CA` (a PEM file), when set, becomes `CURLOPT_CAINFO`; only the test sets it.
  - `net/tls-error.aye` `tlsError`, from `curlError` for CURLcodes 35, 51 and 60: "subject name" in libcurl's message is `CertWrongHost`; "protocol version", "unsupported protocol" or "wrong version number" is `TlsVersion`; another 35 stays `Tls`. A plain HTTP server on an https URL is `TlsVersion` too: LibreSSL reports its answer as "tlsv1 alert protocol version", OpenSSL 3 as "wrong version number", so the two cannot be told apart from the message; `net_http` expects that reason now. For 51 and 60, `CURLINFO_SSL_VERIFYRESULT` (the X509 verify result): 10 is `CertExpired`; 2, 18, 19, 20 and 21 are `CertUntrusted`; 62 is `CertWrongHost`; any other is `CertInvalid`. These are the kinds of Chromium's `net/cert/cert_status_flags.h` (DATE_INVALID, AUTHORITY_INVALID, COMMON_NAME_INVALID, INVALID) and `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`.
  - `FetchError` gets the five kinds; `describe` gives the reason ("the certificate has expired", "the certificate is self-signed or from an unknown issuer", "the certificate is for another host", "the certificate is not valid", "the server does not support TLS 1.2 or later"); the archive's error list has them too.
  - engine `fetchPage`: one of the five on a top-level fetch (`top` empty) gives `notPrivatePage` (`engine/not-private-page.aye`, HTML in `engine/not-private.html` by `@embedFile`, after Chromium's `ssl_error_ui.cc`): title "Privacy error", "Your connection is not private", the host and "Why: REASON". Its `failure` is the reason, so the agent's navigate fails with "cannot fetch URL: REASON" and the tab stays (as for every failed fetch), and `dump` prints the same on stderr. Frames keep the generic error page. `engine/failure-page.aye` holds the tail that the error page and the interstitial share.
- files: `browser/net/set-tls.aye`, `browser/net/tls-error.aye`, `browser/net/http.aye`, `browser/net/multi.aye`, `browser/net/loader.aye`, `browser/net/net.aye`, `browser/net/archive.aye`, `browser/engine/engine.aye`, `browser/engine/failure-page.aye`, `browser/engine/not-private-page.aye`, `browser/engine/not-private.html`, `browser/tests/tls_server.py`, `browser/tests/tls/` (test CA, four certificates with keys, `fetch.html`), `tests/browser.rs` (`tls_errors`), `docs/browser.md`.
- test certificates: P-256 keys, made once with OpenSSL 3.6 and checked in. `ca.pem` (the test CA, 100 years); `valid.pem` (IP 127.0.0.1, by the CA, 100 years); `expired.pem` (by the CA, 2020-01-01 to 2021-01-01); `wrong-host.pem` (DNS wrong.example, by the CA); `self-signed.pem` (IP 127.0.0.1, its own issuer). The CA key is not kept: new certificates need a new CA.
- verify: `tls_errors`: `tls_server.py` serves each certificate on its own port of 127.0.0.1, and `valid.pem` once more with TLS 1.1 only (`@SECLEVEL=0`) when this OpenSSL can still connect with 1.1, else port 0 and the case is skipped with a message. With `DWELLER_TEST_CA`: the valid server's page loads, and its `fetch.html` fetching itself gets 200 by fetch and XHR (the positive control); without it, the valid server is untrusted (the default store is used). For each bad server: `dump` fails with the reason, a page on the valid server gets `TypeError` from fetch and `error` status 0 from XHR, the window (`--frames 1 --text`, when SDL is there) shows the interstitial with host and reason, and the agent's `navigate` answers `ok:false` with the reason. By hand: an iframe to the expired server gets the generic "Cannot load this page" with the reason.
- follow-ups:
  - a bypass ("Proceed to HOST (unsafe)") needs a per-host exception store, and no bypass for HSTS hosts (Q3.5): not in this step.
  - the expired page could say how long ago it expired and check the clock (Chromium's bad-clock interstitial).
  - `CURL_SSL_BACKEND=secure-transport` on macOS would switch to the keychain, where `CURLINFO_SSL_VERIFYRESULT` and the messages differ; the reasons would then fall back to `CertInvalid` or `Tls`.
