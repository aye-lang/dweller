# Q5.1: zoom (Cmd +/−/0), per site, remembered

- goal: page zoom as in Chromium (`chrome/browser/ui/zoom/`, `components/zoom/`, `content/browser/host_zoom_map_impl.cc`): Cmd/Ctrl with `+` or `=` zooms in, with `-` out, with `0` back to 100%; the level belongs to the page's host and is kept in the profile; all three process modes. Row Q5.1 of `foundations.md` (F1).
- facts found first (2026-11-16):
  - No zoom anywhere in `browser/`. The window paints the page and the chrome at one `Ui.scale` (device px per CSS px); in one process the page's viewport is `win_w` x `layoutHeight()` CSS px (`pageview.resize`), with `DWELLER_PROCESS=tab|site` the renderer gets `Resize{width, height, scale}` in device px and divides by the scale (`renderer/lay-out.aye`).
  - A renderer never set `css.setDevicePixelRatio`: `devicePixelRatio` and the `resolution` media features were 1 there on any screen.
  - `giveBuffers` sends `Resize` only when the size in device px changed, so a new scale alone never reached a renderer.
- how it works (Chromium's page zoom, not a visual pinch zoom): the zoom factor multiplies the page's scale and divides its viewport: at 200% a 400 px window lays the page out 200 CSS px wide and `devicePixelRatio` doubles. The chrome keeps the window's scale.
- slices (each with its verify; one commit for the card, the slices are small):
  1. `browser/zoom/`: Chromium's preset factors (`components/zoom/page_zoom_constants.cc`: 25 33 50 67 75 80 90 100 110 125 150 175 200 250 300 400 500), the next and previous level, the key of a URL (its host; the URL without its fragment when it has none, as `net::GetHostOrSpecFromURL`), the map and its file `<profile>/zoom` (written atomically, only by the process that holds the profile lock). Verify: Aye unit tests (`aye test browser/zoom`).
  2. One process: `Ui.page_zoom` follows the shown tab's URL (`syncZoom`, once per loop iteration), the page view gets the divided viewport and the multiplied scale, the mouse points are divided on their way to the page, the keys, a percent chip at the right end of the address bar while the level is not 100% (a click on it resets), `zoom N` in `--state`. Verify: window tests in `tests/browser/window_zoom.rs` (`innerWidth` and `devicePixelRatio` seen by the page, a click that lands on the zoomed element, the PNG's pixels twice as large, the level kept for the host across a navigation and across two runs with one profile).
  3. `DWELLER_PROCESS=tab|site`: no new IPC kind. `Resize` carries `scale * zoom` and is sent again when only the scale changed; the renderer sets its device pixel ratio from it; a child frame's renderer inherits the tab's zoom; mouse and wheel points, the bubbled scroll and the `select` popup's bounds use the page's scale. Verify: the same tests with `DWELLER_PROCESS=site` (and `tab` for the pixels).
- decisions (nobody to ask; the plan's defaults):
  - The key is the host, as Chromium (`a.example` and `b.example` zoom apart, ports and schemes together), not the registrable domain: "per site" of the row is Chromium's "per-site zoom", which is per host.
  - A level of 100% is not stored (Chromium: the default level erases the entry).
  - A window without a profile (the tests, Spaces) keeps the levels in memory until it ends.
  - A hosted Space's tabs stay at 100%: an agent's viewport must not depend on what the person zoomed.
  - Wheel and key scroll steps stay 40 CSS px of the page, so they grow with the zoom (Chromium scrolls a fixed physical distance). Left.
  - In one process `devicePixelRatio` is one global (`css.setDevicePixelRatio`), as before this card: it follows the shown tab.
- references: Chromium `components/zoom/zoom_controller.cc`, `content/browser/host_zoom_map_impl.cc`, `third_party/blink/common/page/page_zoom.cc` (the presets and the 25%–500% range).

## Status: done, 2026-11-16

Done note. Zoom is built whole for the three process modes, with no new IPC kind.
- `browser/zoom/` (12 files): the presets, the key of a URL, the map and its file `<profile>/zoom`; 3 unit tests (`aye test browser --module zoom`: 3 passed).
- One process: `Ui.page_zoom`, set by `syncZoom` once per loop iteration from the shown tab's URL and by `aimZoom` before a navigation or a traversal loads (a page of a host with a stored level is laid out at it from its first frame; the test found that the first animation frame saw the 100% width otherwise). `pageScale`, `pageX`, `pageY` (`ui/page-point.aye`) divide the points on their way to the page; the chrome keeps `Ui.scale`.
- `DWELLER_PROCESS=tab|site`: `TabProcess.page_zoom` (the tab's committed URL; a speculative renderer gets its target's level, a child frame's renderer its tab's), `Resize` sent again when only the scale changed (`given_scale`), `renderer/take-buffers.aye` sets the device pixel ratio (it was 1 in every renderer before).
- The window: Cmd/Ctrl with `=`, `+`, `-`, `0` and the numeric pad's `+`, `-`, `0` (`ui/zoom-shortcut.aye`), the percent chip in the address bar (a click resets), `zoom N` in `--state` when not 100.
- Verify, 2026-11-16: `cargo test --release --test browser -- window_zoom`: 3 passed (`window_zoom_keys`: `innerWidth`, `devicePixelRatio`, a width media query and a click's `clientX/Y` at 25, 80, 110, 200% and after Cmd+0 and a chip click, in one process and with `DWELLER_PROCESS=site`; `window_zoom_pixels`: the page's pixels doubled, the toolbar's unchanged, the chip drawn, the same PNG from one process, `tab` and `site`; `window_zoom_per_host_remembered`: the level kept across a navigation on the host, across two runs with one profile, 100% for a file, the file's bytes). The whole suite: 256 passed, 0 failed. `check_taste.py`, `check_layers.py`, `gen_property_ids.py --check`, `aye check browser`: clean.
- Shared files touched (small): `ui/window.aye` (25 lines: the field, the points, the shortcut, the chip, `syncZoom`, open and close), `ui/tab-process.aye` (2 fields), `ui/give-buffers.aye`, `ui/poll-tab-slot.aye`, `ui/service-children.aye`, `ui/service-speculative.aye`, `ui/send-mouse.aye`, `ui/forward-wheel.aye`, `ui/bubble-scroll.aye`, `ui/take-popup.aye`, `ui/pagedraw.aye`, `ui/agents.aye`, `ui/forms.aye`, `ui/script.aye`, `renderer/take-buffers.aye`, `tests/browser.rs` (the `mod` pair).
- Follow-up, 2026-11-19: a `resize` event at the window when the page's viewport changed since the last one (a zoom step, a window resize; not the first layout, not a print's paper layout): `engine/fire-resize.aye`, called by the window once per loop iteration (`ui/fire-shown-resize.aye`) and by a renderer after its layout and before it paints (`renderer/paint-frame.aye`), so the first frame at the new size already shows what the handler did. Verify: `window_zoom_resize_event` (three steps, three events with `innerWidth` and `devicePixelRatio`, none on a plain load; one process and `site`).
