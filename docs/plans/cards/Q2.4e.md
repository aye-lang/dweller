# Q2.4e: loads in the background under the process flag

- goal: with `DWELLER_PROCESS=tab` (and `site`), a renderer's loads run as they do in the window's own process: everything the engine loads in the background there (script-visible images, async fetch/XHR, module scripts, frames' documents) is a background load over IPC whose answer lands as a task on the renderer's loop; what the engine fetches concurrently there (style sheets, scripts, fonts, a page's images: `net.prefetch`, `startLoadAs` + `awaitLoads`) is in flight at once; the browser answers them in the background too (its window loop never runs a subresource or fetch request to the end before reading the next message); and a load the renderer drops (an `AbortController`, a removed frame, a page left) is cancelled: the browser releases its load, which aborts the transfer and closes the connection. Before, every load was one blocking round trip, and the browser ran it on its own loop: a page of 91 subresources with 40 ms each took 5.5 s under the flag and 0.8 s without.
- design:
  - IPC: one new message, type code 50 (after Q2.9's 43; Q2.10 takes 44 and up): R→B `fetch_cancel{id}`. The replies are Q2.4a's `fetch_head` / `fetch_body` (256 KiB chunks) / `fetch_end` / `fetch_fail`, now in any order between ids; the renderer routes them by id.
  - net, renderer side (`net.setRemoteLoads`, next to Q2.4a's `setRemote`): the loader's API (`startLoad`, `startLoadAs`, `startRequest`, `loadState`, `waitLoad`, `pumpLoads`, `releaseLoad`, `requestResponse`, `requestError`, `loadHeld`, `loadOf`, `loadFailed`, `failedHref`, `loadsRunning`, `liveRequest`, `prefetch`) works without a session: each call goes to the remote loader (`RemoteLoader`, `remote-*.aye`) when one is set. A load is a `RemoteLoad` (net's id, the wire id of its `fetch`, key and request codes, users, state). Loads of the same key and codes join, as in-process. A script's request (`startRequest`) keeps its response in the load until released; a joinable load's response goes to `landed` (at most 64 MiB, oldest dropped), where the synchronous `request` that follows (the in-process cache hit) takes it once by `cacheKey` and request codes (`takeLanded`, in `request` before the remote hook), so a no-cors image response never answers a cors request. Releasing a running load's last user calls the cancel hook.
  - renderer: `startRemote` sends `fetch` (the same `askFetch` as a synchronous load, one id sequence) and keeps a `PendingFetch` (id, nav, URL, the `Fetched` being filled); `scanReplies` takes the replies out of the inbox (pings answered): the awaited id's into the synchronous `awaitFetch`, any other into its pending load (`landFetched` → `net.landRemote` / `net.failRemote`; an id no longer pending, a cancelled one, is dropped, so no late callback). `pumpRemote` (net's `pumpLoads` between tasks with no wait, `waitLoad` with 100 ms) reads the socket; the loop's `answerAll` routes replies that arrive while it waits, sets `r.landed`, and `timerWait` is then 0 so the load's task runs at once. `cancelRemote` drops the pending load and sends `fetch_cancel`.
  - browser (`ui/`): `answerFetch` holds a fetch that is not the tab's navigation when net can run it in the background (`holdFetch`, `liveRequest`): a subresource GET without headers or body (kinds style, image, script, font, worker) warms the cache with `net.startLoadAs` (the request's `top` now kept by the load, `loadRequest`), then is answered by the same `net.request` as before, a cache hit, so its CORS, ORB, mixed-content and cookie handling are those of the synchronous path; a fetch()/XHR, a frame's document or a request with a method, headers or body is a `net.startRequest`, answered from `requestResponse` (or `fetch_fail` with `requestFailure`, the new failure code of the request). The held fetch keeps owned copies of its request (`HeldFetch`), since the message is gone; `answerHeld` (from `serviceTabProcess`, `serviceChild` and the agent relay's `askRenderer`) answers those no longer running; the window polls at 2 ms while any is held (`holdsFetches`). `fetch_cancel` (`cancelFetch`) releases the held load: net removes the libcurl handle mid-transfer, and libcurl closes that connection. A cancel of an id never sent kills (`bad fetch_cancel`); of one answered already, nothing.
  - agent commands in the renderer (`answerAgent`, so also the window's `--text` under the flag) first let the loads in flight land and their tasks run (`settleLoads`, at most 5 s), as the synchronous loads did before: the agent's `wait` on the real clock does not wait for a task whose load runs.
  - test server: `/hang/NAME?KEY` (held until the client closes the connection), `/hang-started?A,B` and `/hang-closed?A,B` (whether each was closed, within 5 s).
- Chromium read: `services/network/public/mojom/url_loader.mojom` (`URLLoaderClient`: `OnReceiveResponse` with the body as a data pipe, then `OnComplete`; a loader per request, many at once), `services/network/url_loader.cc` (`OnMojoDisconnect` → `DeleteSelf`: the renderer dropping its end cancels the `URLRequest`), `third_party/blink/renderer/platform/loader/fetch/resource_loader.cc` (`Cancel` → `HandleError`: the resource gets no further callbacks). Dweller takes: one request per id with its replies in order on the socket, the renderer's drop of a request as the cancel the browser acts on, and no callback after a cancel.

## Status: done, 2026-11-09

Left:
- the renderer's own navigation still loads as `dump` does: the document fetch blocks the renderer, then its sheets, scripts and images load concurrently and the load waits for them (no early show, no input meanwhile). The old page cannot run during the document fetch until the browser's commit checks allow it (Q2.3d: no `same_document` while loading). The browser answers a tab's navigation document on its own loop (synchronously), as before.
- body streaming: a response is sent in 256 KiB `fetch_body` messages (Q2.4a), but only once the browser has all of it; streaming as it arrives, with flow control, needs the loader to hand out partial bodies.
- `img.src` changed while its image loads does not cancel it, in either process: the page's image cache holds a running load until it ends (`holdLoad`, the practice "A dropped request must not abort the load a later one would join").
- workers' scripts and a worker's `fetch` still go through `fetchLocal` in the renderer (Q2.4a left): a worker thread cannot use the tab's socket.
- a landed response is taken once; a second request for the same URL in the renderer is a synchronous round trip (answered from the browser's cache). The browser's held fetches are polled every 2 ms, not woken by libcurl's sockets.
- `settleLoads` holds an agent command (and `--text`) up to 5 s while a load never ends (a long poll); the agent's real-clock `wait` should wait for load tasks itself.
- a failed background subresource load is answered `fetch_fail` Network, not the specific error the synchronous path would give.
