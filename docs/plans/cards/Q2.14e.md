# Q2.14e: `DWELLER_DAMAGE_CHECK` for a renderer's frames

- goal: Q2.14a's proposed readiness row 4 (cause row 2, 11 tests): with `DWELLER_PROCESS=site` the damage check says something true about the pixels the person sees, and the tests that require a silent check pass or fail for what they measure.
- source: `docs/plans/cards/Q2.14a.md` row 2.
- what the code showed: the check lived in the window's `checkDamage` (`ui/pagedraw.aye`): it draws the window's own display list whole and compares it with the page pixels. Under the flag the window has no display list (the page is the renderer's), so the "whole drawing" was the background colour and every frame differed (`2044 pixels differ ...`). The renderer's frames were not wrong.
- design: the property "the page pixels equal a whole drawing" is split where the pixels are made.
  - in the renderer (`renderer/check-frame.aye`, from `drawDamage` when `DWELLER_DAMAGE_CHECK` is set; the variable already passes, `rendererKeeps`): after the damage rects are drawn into the buffer, the display list is drawn whole into a scratch canvas with the same marks (find matches, the caret) and compared: `DAMAGE CHECK: N pixels of the renderer's frame differ from a whole drawing`.
  - in the window (`ui/check-tab-frame.aye`, from `checkDamage` when the tab has a renderer): the page pixels as composed by damage are kept, the shown buffers of the tab's renderer and of its child frames are copied whole, and the two are compared: `DAMAGE CHECK: N pixels of the window differ from the renderer's frames ...`. The lines go to the same stderr (process-model §6), so a test's `!err.contains("DAMAGE CHECK")` covers both.
  - a real difference the check then allowed to remove: the window drew its whole page area on every frame of a renderer's tab (`whole` was true whenever its own display list is null: `ui_damage_px 104000 1` for each frame). With a renderer the damage is now the renderer's rects (`addTabDamage`), so an unchanged frame copies and uploads nothing.
  - and one of the harness: a headless `--frames` run draws no frame while the renderer is behind (`scriptBehind`), so its first `ui_draw` record comes after the renderer's first frame, as in one process.
- IPC: none.
- files: new `browser/renderer/check-frame.aye`, `browser/ui/check-tab-frame.aye`; changed `browser/renderer/{draw-damage,new-tab-renderer,tab-renderer}.aye`, `browser/ui/{pagedraw,window}.aye`, `docs/process-model.md` (§6).
- verify (2026-11-16, the same runs as Q2.14b):
  - the whole suite with `DWELLER_PROCESS=site`, 217 / 263: no `DAMAGE CHECK` line in the log of any test (`grep -c 'DAMAGE CHECK' target/site5.log`: 0; the first run of the wave had it in all 11).
  - of the 11 tests, `window_damage` passes. The other 10 no longer fail at the check; what they fail at is under Left.
  - the whole suite in the default mode: 263 / 263 (the one-process check is unchanged: `checkDamage` returns to it when the tab has no renderer).
