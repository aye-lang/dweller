# Q2.12c: isolated Spaces on renderers, and crash semantics of hosted tabs

- goal: with `DWELLER_SPACES=renderer`, an `isolated` Space is hosted in the window like a `shared` one, with no Space process: the browser keeps a partition per isolated Space (a cookie jar, `localStorage`, and the HTTP cache and connection pool keyed apart) beside the person's profile, in memory only, never written to the profile and dropped when the Space goes; each hosted tab's cookie, storage and network requests use its Space's partition. A hosted tab whose renderer dies fails its requests with the protocol's "renderer crashed", is listed as `crashed` by `tabs`, can be closed with `tab_close`, and its Space and other tabs go on (`docs/process-model.md` §8, `docs/agent-protocol.md` Spaces).
- source: Q2.12's Left, second and fourth items.
- design:
  - partition: a number, 0 for the person's profile (and every `shared` Space), the Space's id for an isolated one (ids are never reused). It lives on the browser's own records, never in a message: `Space.partition` (set by `startHosted` for `!shared`, which now hosts both kinds), `TabSlot.partition` (`hostTab`), `TabProcess.partition` (a required argument of `startTabProcess`: the slot's for a tab, a hosted tab's restart and speculative swap, the parent's for an OOPIF child, the old process's for the relay's swap, 0 for the relay). Popups an agent's page opens go to its Space (`openedSlot` → `hostTab`), so they take the partition too.
  - net: `Request.partition` (default 0, so every other caller is unchanged). The session keeps `partitions` (`PartitionJar { id, jar }`, `net.openPartition` / `net.closePartition`), and `jarOf(session, partition)` picks the jar: the profile's for 0, the partition's, or none (no cookies sent or kept) for a partition that is not open. `requestHeaders` sends that jar's cookies, `prepare` puts the partition on the `Sink`, and `storeCookies` keeps a response's cookies there; `scriptCookies` / `setScriptCookie` take the partition (the in-process engine passes 0). A partitioned cookie is not noted for the Space processes' sharing (`noteStored`), and a partitioned response notes no HSTS (which the profile saves). `networkPartition` starts with `#ID ` for a partition, so the HTTP cache, the loader's de-duplication and the libcurl share (connections, TLS sessions, DNS) are apart. The loader keeps the partition on each `Load` (`startLoadAs`, `newRequest`) and its per-hop requests (`loadRequest`, `hopRequest`); a preflight carries its request's.
  - ui: `answerFetch` sets `req.partition = tp.partition` (held fetches keep it in `HeldFetch`, `heldRequest`); `docCookies` passes it to the jar. `answerStorage` keys a partition's `localStorage` as `#ID ORIGIN` (`partitionArea`) in the engine's in-memory store (the one `sessionStorage` uses: no profile read, no save, no sharing), and `tellStorage` sends `storage` events only to renderers of the same partition. `sessionStorage` is per tab already (hosted tab ids are unique). `freeSpace` calls `dropPartition` (closes the jar, drops the `#ID ` areas), so `space_close`, a stop and a replaced done Space drop it.
  - crashes: a hosted tab whose renderer is gone keeps its slot (as the person's sad tab does). `answerAsked` answers the request that was out on it, and `askTabRenderer` every later page command and `wait`, with `failCrashed`: `agent.failLine(line, mcp, "renderer crashed")` (the request's id; in MCP an error result), counted for `agents:N`. Window commands (`tabs`, `tab_select`, `tab_close`, `tab_new`, `spaces`) are answered as before; `listTabs` adds `"crashed":true` (MCP ` [crashed]`) for a hosted tab with a gone renderer (`tabCrashed`), so the person's tabs' listing does not change. The Space's state is computed from its connections, so it stays `idle`/`working`; `tab_close` frees the slot and its dead process (`endTabProcess`). The person's `DWELLER_PROCESS=tab` tabs keep "the tab's renderer is gone".
- IPC: no new message or type code (the partition is the browser's, not the renderer's).
- references (Chromium, read over HTTPS from `main`): `content/browser/storage_partition_impl.cc` (`Initialize`, `InitNetworkContext`, `is_in_memory()`: each partition owns its network context (cookie manager, HTTP cache, sockets) and its DOM storage context; an in-memory partition is given an empty path, so nothing is written). Dweller takes: one partition per isolated Space that owns a jar, a `localStorage` and a network partition key, an in-memory partition that has no path to write to, and the frame's partition chosen by the browser from its own record of the frame, never from the renderer.
- files: new `browser/net/{partition-jar,jar-of,open-partition,close-partition}.aye`, `browser/ui/{partition-area,drop-partition,fail-crashed,tab-crashed}.aye`; changed `browser/net/{net,http,session,loader,load-request,hop-request,network-partition,network-partition_test,note-hsts,preflight}.aye`, `browser/engine/window_api.aye`, `browser/ui/{spaces,start-hosted,host-tab,tabs,tab-process,start-tab-process,start-speculative,start-child,poll-tab-slot,ask-tab-renderer,follow-swap,relay-agent-main,answer-fetch,held-fetch,hold-fetch,held-request,doc-cookies,answer-storage,tell-storage,answer-asked,list-tabs}.aye`; tests `tests/browser/window_spaces.rs` (new `window_spaces_isolated_in_renderer`, `window_spaces_crash_in_renderer`); `docs/process-model.md` §8, `docs/agent-protocol.md` (Spaces: hosted Spaces).
