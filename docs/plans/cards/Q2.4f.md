# Q2.4f: renderer-started navigations carry their initiator, so SameSite holds

- goal: with `DWELLER_PROCESS=tab`, a navigation the browser starts for a renderer (`begin_navigation`: a link click, a form submission) carries the page that began it, so net decides SameSite as for the window's own process: a cross-site form POST sends no Lax cookie, a cross-site link sends Lax but not Strict ones. A URL the user typed, a bookmark, back, forward and reload stay browser-initiated (no initiator, as before). Before this, net counted every renderer-started navigation as same-site (Q2.4d left list).
- design:
  - the browser keeps `tp.nav_initiator`: the URL of the document that asked for the pending navigation, from its own record (`topOf(tp)` in `beginNavigation`, before `tp.committed` moves to the target), never from the message. `queueNavigate` (the address bar, history, reload) clears it.
  - `answerFetch`: the document fetch of that navigation (`navigates`, while `tp.loading`) gets `nav_initiator` as its referrer; the referrer the message names is not used for it. A fetch the agent path lets through (`fetchNavigates` without a pending load) keeps the checked referrer of the message, as before.
  - net does the rest as for the window's own process, where `noteNavigation` gives a page's navigation its referrer: the referrer is the SameSite initiator of the whole chain (`fetchHttp`), so a redirect hop keeps the original initiator and a hop to another site makes the rest of the chain cross-site (`crossed`); `contextOf` sends Strict only same-site and Lax only on a cross-site top-level GET; `referrerOf` applies the referrer policy (strict-origin-when-cross-origin) to the `Referer` it sends. The request stays `Initiator.Browser` as in-process (an `Initiator.Page` would also run the mixed-content and ORB checks of a subresource on a top-level navigation).
- Chromium read: `content/browser/renderer_host/navigation_request.cc` (`common_params().initiator_origin`, set by the browser for a renderer-started navigation, becomes the `request_initiator` of its loader), `net/cookies/cookie_util.cc` (`ComputeSameSiteContextForRequest` / `ComputeSameSiteContext`: the initiator against the whole URL chain; a main-frame navigation is lax-cross-site for a safe method, strict only same-site). Dweller takes: the browser, not the renderer, names the initiator of the navigation, and net derives the cookie context from it and the redirect chain.
- files: `browser/ui/{tab-process,start-tab-process,end-tab-process,begin-navigation,queue-navigate,answer-fetch}.aye`; new `browser/tests/net/samesite_links.html`; `tests/browser.rs` (new `window_renderer_samesite`); `docs/plans/cards/Q2.4d.md` (the left item now names this card).

## Status: done, 2026-11-08

Left:
- net sends no `Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-User` and no `Origin` on a navigation in either process (`originHeader` only for `Kind.Other` or CORS): both processes match, but the Fetch Metadata headers and the `Origin` of a POST navigation are a net card of their own.
- the renderer's scripts (`location`, `form.submit()`, `window.open`) and links in iframes still do not ask the browser (Q2.3c left list), so they do not go through `begin_navigation`.
- the page's own referrer policy (`<meta name=referrer>`, `Referrer-Policy`, `rel=noreferrer`) is not applied in either process; net always uses strict-origin-when-cross-origin.
- a `begin_navigation` that arrives after the browser already fetched the next document is credited to that document (`topOf`), as Q2.4d's requests are; per-document ids are Q2.6.
