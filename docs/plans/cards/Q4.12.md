# Q4.12: HTTP cache with expiry and revalidation, on disk; request priorities; the preload scanner

## Status: cloud part done, 2026-11-22 (slices a to d done, 2026-11-19; what each leaves is in its section; the row's verify, live W8 and zol, is in the Mac queue below)

- goal (the row): an HTTP disk cache with revalidation and expiry in the browser process, request priorities by kind, and the preload scanner checked. A revisit is served from cache; live W8 does not drop. Q0.4d (zol's live document load hits the 30 s timeout) needs the live site: Mac queue.
- what exists (2026-11-19): `net/cache.aye`, an in-memory cache of the session keyed by network partition and URL (`cacheKey`), for GET subresources with a 2xx status. `Cache-Control: no-store` is not kept; nothing else of the response's cache headers is read: an entry never expires within a session and is never revalidated, and nothing survives the process. Its users: `fetchHttp` (net/http.aye), the loader (`startLoad`, `keepLoad` in net/loader.aye), the concurrent prefetch (net/multi.aye), and a renderer's loads through the browser (`remote-start.aye`, `take-landed.aye`). Network stays in the browser process (docs/process-model.md), so the cache does too.

## Design of slice a

- chromium: `net/http/http_cache_transaction.cc` (`BeginCacheValidation`, `RequiresValidation`), `net/http/http_response_headers.cc` (`GetFreshnessLifetimes`, `GetCurrentAge`); blink: `platform/loader/fetch/memory_cache.cc`, `resource_fetcher.cc` (`DetermineRevalidationPolicy`).
- an entry keeps when it was stored, its freshness lifetime and the load epoch it was stored in. The epoch moves at each top-level document fetch. An entry of the current epoch is used as it is (the page's own memory cache). An older one is used when fresh; when stale and it has a validator the request carries the validator, and a 304 makes the entry fresh again with the new headers; otherwise it is fetched and replaced.
- lifetime: `max-age` (`s-maxage` is for shared caches, not read); else `Expires` minus `Date`; else a tenth of `Date` minus `Last-Modified`; else 0. `no-cache` and `must-revalidate` with age over the lifetime: 0. `Vary` other than `Accept-Encoding`: lifetime 0 (the request headers are not kept; the entry is revalidated).

### Left of slice a

- `Vary` is not matched against the request: any `Vary` but `Accept-Encoding` makes the entry stale at once.
- A 304 keeps the stored headers; only the freshness comes from the 304 when it carries `Cache-Control` or `Expires`.
- `Age`, `stale-while-revalidate`, `immutable` and `only-if-cached` are not read. A reload (cmd+r) revalidates like any navigation; a hard reload that skips the cache does not exist.
- The epoch is the session's, not a page's: a navigation in one tab makes the next relayout of another tab revalidate its stale entries (conditional requests, no wrong result).
- A 304 for an entry that was dropped meanwhile (the cache over `MAX_CACHE_BYTES`) is kept for one use with an empty body in the loader's path.

## Slice b: done, 2026-11-19

- design (chromium: `net/disk_cache/simple/`, one file per entry and an eviction by size; `net/http/http_cache.cc`):
  - `<profile>/cache/<16 hex digits of the key's FNV-1a hash>`: a line `dweller-cache 1`, a line of nine numbers (stored, lifetime, status, and the lengths of the key, MIME type, charset, final URL, headers and body), then those six byte runs. Written to `cache/writing` and renamed, so a killed process leaves no half file under an entry's name. A file whose stored key is not the key asked for (a hash collision, a damaged file) is not used.
  - stored (`diskStorable`): 2xx responses the session keeps, that are fresh for a time or have an `ETag` or `Last-Modified`; not the one-use entries, not `no-store` (never kept at all), and not the entries of a partitioned Space (the key starts with `#` and the partition's number, which means another Space in the next process).
  - read when a key is not in memory (`foundEntry`, `loadCached`), with an epoch no page load has (`DISK_EPOCH`), so its freshness is always checked. A 304 rewrites the file with the new stored time and lifetime.
  - only with a profile this process holds the lock of (`openDiskCache` from `openProfile`); a renderer has no profile and asks the browser process.
  - at start the directory is trimmed when over the cap (256 MB; `DWELLER_DISK_CACHE_BYTES` for tests): oldest files first, down to three quarters. Decision: by the file's time (written, or rewritten by a 304), not by last use: a read does not touch the file. The plan's table said least recently used; that needs an index kept across runs.
- files: new `browser/net/disk-cache-path.aye`, `disk-storable.aye`, `store-cached.aye`, `load-cached.aye`, `parse-cached.aye`, `dup-cached.aye`, `found-entry.aye`, `trim-disk-cache.aye`, `open-disk-cache.aye`; `net/cache.aye` (`Cache.dir`; `has`, `lookup`, `keep`, `deinit`), `net/stale-validators.aye`, `net/refresh-entry.aye`, `net/session.aye` (`openProfile`, 1 line). Test `http_cache_survives_restart`.

### Left of slice b

- Bodies are written on the thread that finishes the load, whole, and read whole on the first lookup: no streaming, no write behind. A page with many large images pays the writes in its load.
- Eviction only at start; a long session can pass the cap until the next one. No count of entries, no index.
- Documents are not cached (the session never kept them), so a revisit still fetches the HTML.
- A profile another process holds is neither read nor written.

## Slice c: done, 2026-11-19

- found first: every load went to the curl multi handle at once, and libcurl queues beyond 6 connections a host first in, first out. In the window a static page already asks for its sheets and scripts before its images (the order they are found in); what was wrong is a sheet or script found after many images were started (by a script, or late in the document): it waited behind all of them on an HTTP/1.1 host.
- design (chromium: `services/network/resource_scheduler/resource_scheduler.cc`, `ShouldStartRequest`: delayable requests, at most 6 a host, and one while a layout-blocking request is in flight; requests to hosts that multiplex are not held):
  - an image load is held in the loader (`Load.held`, state Running, no transfer) while its host has `hostLimit()` transfers in flight (`mustHold`). Each finished transfer starts the held loads that may go (`releaseHeld`, at the end of `harvest`). Everything but images starts at once and so is ahead of the held images in libcurl's queue.
  - a host seen to answer with HTTP/2 or later (`noteMultiplexed`, `CURLINFO_HTTP_VERSION`) is never held: its requests share a connection. They get an HTTP/2 stream weight by kind instead (`streamWeight`: 256 documents, sheets, scripts; 128 fonts and fetches; 32 images).
  - `DWELLER_HOST_CONNECTIONS` sets the connections a host (for tests; default 6 as before).
  - decision, changed after slice d's measurement: the first version also held images to one at a time while any sheet or script was in flight (Chromium's rule for layout-blocking requests). The loader cannot tell a render-blocking script from any other, and on `scan.html` six images then loaded one after the other behind a 400 ms script (the last asked for at 282 ms, 113 ms before the slice). That rule is removed; with the host rule alone the same image is asked for at 104 ms and a late `@import` at 54 ms (114 before).
  - decision: only images are delayable. Fonts block text and are few; "in view" is not known to the loader.
- files: new `browser/net/must-hold.aye`, `release-held.aye`, `start-load-job.aye`, `host-limit.aye`, `authority-of.aye`, `multiplexes.aye`, `note-multiplexed.aye`, `drop-multiplexed.aye`, `stream-weight.aye`; `net/loader.aye` (`Load.held`, `Loader.multiplexed`, `startLoadAs`, `harvest`, `finishLoad`, the loader's end), `net/multi.aye` (`startJob`, 1 line), `net/pool-options.aye`. Test server: `/ordered/NAME`, `/order`; page `browser/tests/net/priority.html`; test `request_priority_sheet_before_waiting_images`.
- numbers (the order requests reach the test server for `priority.html`: eight images started by a script, then a sheet added, and a script element):

  | 2 connections a host | not settable | `late.js i1 i2 late.css i3 …`: 4th, in `dump`, in the window and with `DWELLER_PROCESS=site` |

## Slice d: done, 2026-11-19 (a check; nothing changed but slice c's rule above)

- what there is: no separate preload scanner. The document is parsed whole, then the engine starts the loads of its scripts (`prefetchScripts`), sheets (`prefetchSheets`) and images (`prefetchImages`) before the first script runs. That finds everything a scanner finds, once the document is complete.
- method: `browser/tests/net/scan.html` has one of each kind after a parser-blocking script that takes 400 ms (`/ordered/slow-block.js`); `/order-at` gives when each request reached the server. Found ahead = asked for before the blocking script's response ended. The window, in process, ms after the first request:

  | resource | asked at | found ahead |
  | --- | ---: | --- |
  | sheets in `head`, before and after the script (2) | 0, 1 | yes |
  | the blocking script, a later script, a module, an async one (4) | 1 to 2 | yes |
  | a deferred script | 52 (the 7th request: it waits for one of 6 connections) | yes |
  | `img src`, `srcset`, `picture source`, `input type=image`, an `img` in the rest of the body (5) | 53 to 104 | yes |
  | `@import` in a style element, a `@font-face` font in use, a background image (3) | 54 to 106 | yes |
  | `link rel=preload as=image` | 456 | no: after the script ran |
  | an `iframe`'s document | 457 | no (Chrome's scanner does not preload frames either) |
  | `img loading=lazy`, in view | 459 | no |
  | `video poster` | never | not requested at all |

  16 of 19 before the blocking script ends. With a renderer per site the same 16, at the same times.
- what is missed:
  - in process, nothing is asked for until the whole document has arrived. `/parts/net/scan.html` sends the first half, holds the rest about 1.3 s: in process the first subresource request comes when the rest does (2961 ms after the server's start against 1666 with `DWELLER_PROCESS=site`, which streams the document, Q2.4e). A scanner over the bytes as they arrive is what that needs.
  - `link rel=preload` is started when the link element is handled, after the blocking script, not with the first loads.
  - `video poster` is never fetched.
  - `dump --js` (no window) asks for sheets after the scripts ran (455 ms) and images after the blocking script (402 ms): it has no early loads for them.
- files: `browser/tests/net/scan.html`; `/order-at` and the 400 ms `slow` names in `browser/tests/server.py`. No test: the times are a measurement, and the order they show for sheets and scripts is covered by `request_priority_sheet_before_waiting_images`.

- verify (slices c as changed, and d): wave tip merged; `cargo test --release --test browser` → 344 passed, 0 failed (`target/q412d-suite1.log`); `check_taste.py`, `aye check browser` pass.
