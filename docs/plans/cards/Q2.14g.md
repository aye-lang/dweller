# Q2.14g: the product gaps the count found

- goal: Q2.14a's proposed readiness rows 7 to 11 (cause rows 13, 14 and 16 to 18, 7 tests): each gap is a difference a person or an agent sees with `DWELLER_PROCESS=site`, not an artefact of the tests.
- source: `docs/plans/cards/Q2.14a.md` rows 13, 14, 16, 17, 18.
- slices:
  1. `dweller agent|mcp --width PX --height PX` in the renderer modes (`agent_errors`, `agent_screenshot`). The relay refused every option but `--no-js`. The options are now parsed once (`agent/serve-options.aye`, used by `serveMain` and by `ui/relay-agent-main.aye`, one usage line in both modes), and the relay sends the size before its first request: B→R `agent_viewport{width, height}` (82), which the renderer keeps for its headless session (`renderer/agent-session.aye`, `agent.headlessSession(alloc, width, height)`).
  2. `Sec-Fetch-User` only for a navigation with user activation (`fetch_metadata`; security: request metadata). The browser sent `?1` for every navigation a renderer began. `begin_navigation` now ends with `user` (0 or 1; any other value is `bad begin_navigation`), which the renderer fills from `engine.hasTransientActivation` (links, forms, `location`, frame links), and `answerFetch` uses `tp.nav_user` (true for a navigation the browser itself starts, `queueNavigate`). Chromium trusts the renderer for the same bit (`has_user_gesture` of `BeginNavigationParams`); a compromised renderer can claim a gesture and gets nothing but the header.
  3. the agent's navigations from a page send `Referer` (`agent_forms_http`: the GET form and the link of `net_cookies.jsonl`). `net.noteNavigation` keeps the page's URL for the next document fetch in the net session, and a renderer has none, so the hint was dropped. A renderer now keeps it itself (`net.setNavigationNoter`, `renderer/fetch-through.aye` `noteRemoteNavigation` / `hintedByPage`) and puts it on the `fetch` it sends, in a headless agent session for every navigation and in a window's renderer for a page-initiated one (a tab's own navigation gets its referrer from the browser, `nav_initiator`). The browser checks it as before (`referrerAllowed`: the origin of the document that asks). `requestLive` uses the same two functions (`net/navigation-hinted.aye`, `forget-navigation.aye`).
  4. the agent's reply to a 401 has `auth_required` (`net_basic_auth`). `net.authRealm` reads the challenges the net session noted; in a renderer the page's own 401 is now noted from the response it was given (`renderer/note-challenge.aye`, `net.basicRealmIn` over the headers a renderer already gets, `net.setRealmKeeper`). The second half of Q2.14a's row 17 (`***` in the URL of reply 2) no longer shows: reply 2 is `loaded http://alice:wonderland@...` in both modes.
  5. "the window's loop blocks on the network in `net_sync` and `prefetch`" (`window_history_steps`, `window_paints_early`): not a gap of the window. The two records are the renderer's (its stderr is the browser's, process-model §6): the renderer loads its navigation document and the document's blocking scripts synchronously (`net_sync 613 ms`, `prefetch 613 ms` with the page's URL as label), while the window's iteration takes 0 ms besides. What the tests then require, a first paint three iterations before the slow script runs, needs the renderer to show the page before its scripts are in: the readiness row "the renderer streams its navigation document and paints before the whole body" [Q2.4e, Q2.12b], lane proc-speed. Nothing changed here.
