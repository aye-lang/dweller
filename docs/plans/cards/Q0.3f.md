# Q0.3f: a renderer runs a replayed load's scripts one task each, as a live load's

- goal: archive measurements (W7, `window_perf.py report --replay --process site`) showed a long renderer load task that live browsing does not have: youtube-search 2.0 s, youtube 5.4 s, zol 2.5 s (P1.S6 and Q4.29's Left). Make a replayed (and a recorded) load run its scripts as tasks, as a live load does, so that replay measures what a person gets.
- method: `browser/build.sh` (safe) at a5f0f178 (main 888e5c91 plus PR #432, #433 and #434, `origin/n23-Q4.29`), and the same plus the fix. This Mac (M2 Pro, load 1.5 to 4). Logs: `target/q03f/` in the worktree.

## Before

- `report --replay --process site --site youtube`, 1 run: window loop 17 ms, wheel to frame p50/p95 97.1/410.4 ms, idle 85.1%, renderer task 2085 ms.
- The `scroll` run of the same report with `--log`: the longest renderer task (`r_task` 2037 ms) is the renderer's first task, the staged load. It holds 46 `scripts` records (one per step of `engine.stepPageScripts`: the begin, each parser-blocking and deferred script, the end) that sum to 1850 ms. One of them is `kevlar_base` (1562 ms). The task also holds `js_parse` 742 ms and `css_parse` 260 ms.
- A live load of a local page steps. `browser/tests/perf/replay_scripts.html` (an external script, then six inline scripts of 100 ms) from the test server in site mode: six renderer tasks of 100 to 133 ms, and a wheel sent once the page is shown is handled after the first inline script. The same page replayed from an archive: one renderer task of 644 ms, and the wheel is handled after the last script.

## Cause

- `stageLoad` (`browser/renderer/stage-load.aye`) ran the whole load at once (`finishStaged`) when `net.liveRequest(&p.url)` was false. Q2.14j added that check so that a `file:` page runs its scripts before its first frame, as in the window's own process. But `liveRequest` is also false under `DWELLER_REPLAY`, and since Q0.3e under `DWELLER_RECORD`. So a replayed or recorded http(s) load ran every script back to back in one task. Its subresources come over the renderer's socket as a live load's do, so nothing made it different from a live load.

## Change

- `stageLoad` finishes a load at once only when the document is not http or https (a `file:`, `data:` or `about:` page, as before). A replayed or recorded page goes the live way. `advanceStaged` shows the first frame once the sheets are in, and then each turn of the renderer's loop runs `stepStaged` (50 ms of `stepPageScripts`, one script at least, Q4.25d). This is the same stepping code, with the same order, parser-blocking rules and `DOMContentLoaded`/`load` steps, and no second copy. A page that a service worker controls (the other case where `liveRequest` is false) is not changed: `startEarly` starts no load for it, so `advanceStaged(r, true)` runs its scripts in the same call, as `finishStaged` did.
- An agent command (`answerAgent`) and a new navigation (`load`) still call `finishStaged` first, so an agent in a window still sees the whole load. `dweller agent` and `dump` do not use `stageLoad`: a headless renderer (width 0) loads with `loadShared`, and `dump --md` runs in the process. So `page_load.py check` and `check --agent` run the same code as before.
- `browser/engine/PERF.md` ("Archive semantics") documents this.

## Test

`window_renderer_loads::window_renderer_loads_replayed_scripts` (`tests/browser/window_renderer_loads.rs`, page `browser/tests/perf/replay_scripts.html` and `replay_scripts.js`). `dump` records the page from the test server, and the server is then stopped. The window replays the page with `DWELLER_PROCESS=site`, and the test expects these results: all scripts ran, no archive miss, at least six renderer tasks of 90 ms or more and none of 300 ms, and a wheel (sent after `painted`) handled before the last script. The window's own process (`DWELLER_PROCESS=single`) replays the page too and must run the same scripts.
- Before the fix: FAILED (`wheel after external 0 1 2 3 4 5`).
- After: ok. Renderer tasks of 90 ms or more: 138, 101, 99, 100, 99, 100. The wheel was handled after `external 0`. The test passes when the suite runs in default mode and with `DWELLER_PROCESS=single`.

In that task, `getComputedStyle`'s styling (`computedStyling` in `engine/window_api.aye`, which calls `pageAuthorSheets`) parses the page's author sheets again: 268 `css_parse` records, 490 ms. This is the page's own work as a person gets it. The fix is not in this card (Left).
- Idle CPU did not change in a way that the runs can separate from noise.

## Determinism

- `page_load.py check --agent` on all 22 archives (`target/sites` of the main checkout, with no `DWELLER_PROFILE`), once: exit 1. bbc, zol and mistral miss their expectations with archive misses. The base build gives the same misses (bbc: 2 `gampad/ads` with other `correlator` values; zol: `ckmap.mediav.com/m` and `show-g.mediav.com/s`; mistral: 10 gtag `measurement/conversion` and `g/collect`). A build of origin/main (888e5c91) passes bbc and mistral, and zol fails there with the same 2 misses. So bbc and mistral come from PR #432/#433 (Q4.28 lets mistral's gtag run past the stack limit, so it makes requests that the archive does not have), and zol fails on main as well. None of these comes from this change, which the `dump` path never reaches. The other 17 judged sites pass. `sites.json` did not change.
- A first run with `DWELLER_PROFILE` set to one scratch directory for all sites failed youtube-search too: `dump` opens the profile and keeps cookies, storage and service workers from site to site. Do not set a profile for `page_load.py`: `dump` and `agent` open none without one.
- Agent tasks (`page_load.agent_task`, the code that `check --agent` runs, called directly because `check` skips the task of a site whose content fails): github pass, bbc pass, mistral pass (archive misses reported, not judged). youtube-search has no task.
- bbc record and replay with this build: a live `dump --md --js` with `DWELLER_RECORD` (44 s, 241 archive files), then a replay of it with `DWELLER_REPLAY`. Both made the same 243 requests in the same order (the `requests` records). The Markdown is the same. There was no miss and no fallback.
