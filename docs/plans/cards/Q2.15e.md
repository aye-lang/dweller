# Q2.15e: the hit-test slow path

- goal: readiness list for Q2.14, "What a person sees", second bullet [Q2.10]. The browser routed a mouse event to the top-most cross-site frame whose clipped rect holds the point. So a click on something the parent paints above a frame (a modal, a sticky header) went to the frame's process, and a frame with `pointer-events: none` took clicks meant for what is under it. Now, where the fast path cannot know, the browser asks the frame's embedder first (process-model §5).
- design:
  - the flag: the `subframes` record has `hit_test` (0 or 1; the record grows by one u32, `badSubframe` refuses other values). The parent's renderer sets it when the frame's box has `pointer-events: none` (`engine.frameIgnoresPointer`) or when its display list draws something after the frame's items that meets the frame's shown rect (`paint.coveredFrame`: a `Fill`, `Image`, `Svg`, `Tiles`, `Shadow`, or the start of a `Text` or `Quad`). It is a "may be covered": the answer comes from the renderer's real hit test.
  - IPC: B→R `HitTest{id, x, y}` (101: a point in the asked renderer's buffer, device px) and R→B `HitTestReply{id, key}` (102: the key of the remote frame at the point, 0 for none). The renderer answers with `engine.remoteFrameAt`: `nodeAt` (reverse paint order, transforms, overflow clips, `pointer-events`), then down through its local frames to a remote one.
  - browser: `holdsMouse` runs before a mouse event is handled. `unaskedHit` walks down as `hitFrame` does; at a flagged child with no answer for this point it stops: the event goes to the tab's queue (`TabProcess.hit_queue`, the SDL event itself), `HitTest` goes to the child's embedder, and every later mouse event of the tab waits behind it, so the order holds. `serviceHitTest` (each poll) takes the reply, keeps it as an answer (`hit_answers`: frame, key, point, inside) and runs the queue through `forwardMouse` again; `hitFrameWith` reads the answers, an event that meets another flagged frame deeper asks again and keeps the answers it has, and they are dropped once the event is sent. A captured mouse (button down) asks nothing. An embedder that is gone answers "outside".
  - the wheel does not wait: over a flagged frame it goes to the frame the last mouse move went to (`wheelTarget`, `TabProcess.mouse_frame`), which was asked for.
  - checks: `HitTestReply` with an id the browser did not ask this renderer for kills it (`unexpected hit_test_reply`); the key is only compared with the child asked about. A renderer may not send `HitTest` (`fromRenderer`).
  - headless waits: `renderer:input` also waits while a hit test is open or the queue is not empty (`inputWaits`).
- decision: transforms are not a reason to ask. A rotated or scaled frame is drawn unrotated at its bounding box (Q2.15d Left), and the fast path hits that drawn rect; asking the renderer would hit the transformed shape that is not on screen. When the pixels follow the transform (Q8), the flag is set for it too.

## Status: done, 2026-11-16

Left:
- the pixels: what the parent paints above a frame is still drawn under the child's pixels (the "over" buffer, process-model §5). Clicks now go where the page means them, the picture does not show the cover.
- each mouse move over a flagged frame is one round trip to the embedder (Chromium does the same for ask regions); not measured.
- a hit test has no timeout: an embedder that hangs holds the tab's mouse queue until the hang path (Q2.5) kills it.
- `coveredFrame` reads item rects without the clips around those items, so content clipped away above a frame still sets the flag (one needless question, the answer is right).
- two frames that overlap: an "outside" answer sends the event to the embedder, not to the frame below.
- drag-selection, the cursor and the status URL of a child are as Q2.10 left them.
