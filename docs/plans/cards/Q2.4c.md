# Q2.4c: a renderer opens no profile file

- goal: with `DWELLER_PROCESS=tab`, a renderer opens no file of the profile and holds no cookie jar, cache, storage or history file. The browser starts it with a minimal environment and only the descriptors it needs; the renderer's code cannot reach the profile helpers; a test lists the renderer's open files while it shows a page that uses `document.cookie` and `localStorage`.
- what was open before (read from the code; the new test was not run on the old code):
  - descriptors: the renderer was started with `posix_spawnp` and no file actions, so it inherited every descriptor of the browser that was not close-on-exec. The profile's `lock` file (`net/profile.aye` `lockProfile`, opened without `O_CLOEXEC` and held while the browser runs) was one of them: each renderer held the profile's lock open and kept the `flock` past the browser's exit. libcurl's sockets and any other plain `open` were inherited too.
  - environment: the renderer got the browser's whole environment, `DWELLER_PROFILE`, `DWELLER_COOKIE_FILE` and `DWELLER_TELEMETRY_DIR` included.
  - code path: `main` ran `net.start` before it looked at `--renderer`, and `net.start` reads the cookie file that `DWELLER_COOKIE_FILE` names. With that variable set, a renderer read the cookie jar.
- design:
  - spawn (`ui/spawn-renderer.aye`): the socket's end goes to fd 3 (`posix_spawn_file_actions_adddup2`) and the renderer is told `--renderer 3`. macOS: `POSIX_SPAWN_CLOEXEC_DEFAULT` with `addinherit_np` for 0, 1, 2 and 3, so nothing else crosses `exec`. Linux: `posix_spawn_file_actions_addclosefrom_np(4)` (glibc 2.34+). The two shared-memory buffers are not inherited: they come later over the socket (`resize` with 2 fds, SCM_RIGHTS), as before.
  - environment (`ui/renderer-env.aye`, `ui/renderer-keeps.aye`): only `PATH`, `HOME`, `TMPDIR`, `LANG`, `TZ` and the `DWELLER_`, `SDL_`, `XDG_`, `LC_` variables, without `DWELLER_PROFILE`, `DWELLER_COOKIE_FILE` and `DWELLER_TELEMETRY_DIR`. `HOME` stays for system libraries (fontconfig's user fonts and cache); no Dweller code that a renderer runs builds a path from it (`ui/window.aye`'s `~/.dweller` and `perf.telemetryStart` are not reached from `renderer.serve`).
  - code path: `main` skips `net.start` for `--renderer` (`renderer-run.aye`), so a renderer never has a net session, a jar, a cache or a profile. `net.start`, `net.openProfile`, `net.profileDir` and `net.profileWritable` call `noProfileInRenderer`: once `net.setRemote` has run (the renderer's `fetchThrough`), reaching any of them is `unreachable`, a panic in debug and safe builds (the tests build safe). `engine/storage.aye` reaches the profile only through `net.profileDir` / `net.profileWritable`, so localStorage's files are covered by the same check.
  - Spaces keep `spawnProgram` (the whole environment and the descriptors that are not close-on-exec); its argument and environment code moved to `ui/c-args.aye` and `ui/process-env.aye`, which both spawns use.
- Chromium read: `content/browser/child_process_launcher_helper_posix.cc` and `base/process/launch_posix.cc` (`LaunchOptions.fds_to_remap`: a child gets only the descriptors mapped for it, the rest are closed; `clear_environment` with an explicit environment). Dweller takes: an explicit list of descriptors (stdio and the IPC socket at a fixed number) and an allow list for the environment.
- files: new `browser/ui/{spawn-renderer,c-args,process-env,renderer-env,renderer-keeps,renderer-keeps_test}.aye`, `browser/net/no-profile-in-renderer.aye`, `browser/renderer-run.aye`; `browser/ui/{start-tab-process,spaces}.aye`, `browser/net/session.aye`, `browser/main.aye`; `tests/browser.rs` (new `window_renderer_no_profile_files`, `open_files`).
- verify (2026-11-08, macOS):
  - `aye check browser`: exit 0. `python3 browser/tools/check_layers.py`: exit 0. `python3 browser/tools/check_taste.py`: exit 0.
  - `aye build browser`: exit 0. `aye test browser`: 227 passed, 0 failed, 18 modules (new: `rendererKeeps`).
  - `scripts/capped.sh cargo test --release --test browser -- window_renderer_no_profile_files window_renderer_ window_login_in_renderer storage_between_tabs aye_unit_tests`: 13 passed, 1 failed: the new test, whose first version expected one child of the window (the agent's page is served by a Space, a second browser process with its own renderer). With the test walking the Space's children too: `window_renderer_no_profile_files` passes (1 passed, 0 failed); only the test changed between the two runs.
  - `window_renderer_no_profile_files`: a window with `DWELLER_PROCESS=tab`, `DWELLER_PROFILE` set to a fresh directory and an agent socket; the agent (served by a Space, which has its own renderer) navigates to `storage/script-cookies.html` over http and evaluates `localStorage.setItem` / `getItem` and `document.cookie` (`kept js=1`). While the page is shown the test lists the open files of every renderer (`--renderer 3` among the window's children and the Space's, at least two): macOS `lsof -F ftn -p PID`, Linux `/proc/PID/fd`. None is under the profile; every regular file is a mapped image (`txt`: the binary and libraries), the binary, or under `/System/`, `/usr/`, `/Library/Fonts/`. Linux CI runs the same test through `/proc`.
  - No golden re-blessed; every window run headless (`SDL_VIDEODRIVER=dummy`).

## Status: done, 2026-11-08

Left:
- the OS sandbox that enforces this (Q2.8a/b): today a renderer could still `open` a profile path it guessed; this card proves it does not.
- `HOME` is still in the renderer's environment, for system libraries; the sandbox can drop it with fontconfig pointed at a cache it may read.
- `lockProfile` and other plain `open`s in the browser are still without `O_CLOEXEC`; the renderer no longer inherits them, but a Space (`spawnProgram`) still does.
- IndexedDB has no store yet; when it gets one it must go through the browser like localStorage (Q2.4b).
