### Cause and proposal (no code change in this step)

1. JS parse trees (350 MB here): a script's tree stays alive for the life of the page so that functions compile from it when first called (`vmLookup`), and the property caches are indexed by tree node. Proposal: keep the source and each function's range, free the tree when the script's top level has run, and parse a function again when it is first called (V8's lazy parsing; `v8/src/parsing/preparser.h`); the property caches move into the compiled bytecode. Verify: a counter of live tree bytes after load, and youtube-search's renderer at least 300 MB smaller. A JS engine step, not a small fix.
2. CSS arena growth (part of the 262 MB tokens and 159 MB declarations): `tokens()` and every list of `Sheet` (`decls`, `rules`, `complexes`, `compounds`, `simples`) grow inside the sheet's arena, and an arena never frees the buffer a list grows out of, so about half of each list's bytes are dead. Proposal (small, the next fix): build the token list with `sheet.alloc` and copy it into the arena once at its final size (raw declarations keep slices of it, so the copy must stay), and give the sheet's lists the general allocator, freed in `Sheet.deinit`. Verify: a test page with a 4 MB generated style sheet whose renderer footprint (or a `css_bytes` counter) stays under a stated bound in the default mode and with `DWELLER_PROCESS=single`; expected about −200 MB on youtube-search.
3. The object, property and value tables (654 MB together): the next measure is the size of `Obj` and `Prop` against the live counts (`Heap.objs` holds about 2M slots here); shrinking them is a JS engine step of its own.

### Budget (decided)

- **M1: on the archives of the judged sites, a site's renderers' footprint (macOS `phys_footprint`, at load + 10 s, measured as above) is at most 1.5× the footprint of Chrome's renderers of the same tab, and the window's is at most Chrome's browser and GPU processes together.**
- 1.5× leaves room for an engine without Chrome's compressed heap and pointer compression, but not for keeping data Chrome drops (parse trees, dead list buffers).
- today: the window part holds on 8 of 8; the renderer part on 1 of 8 (hn 0.67×); zol 4.0×, youtube 6.9×, youtube-search 5.3×, mistral 9.6×, bbc 2.8×, github 5.1×, wikipedia-en 2.6×.
- the cap of this card's code part (48 MB a renderer) is right for small pages (hn: 65 MB) and far low for heavy ones; it stays until the renderers are within the budget.
