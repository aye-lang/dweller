# Q2.13: process limits (code part): a cap on renderers, reuse over it, hidden child frames throttled

## Status: in progress, 2026-11-19 (the cap and reuse are done and tested; memory is not measured)

- goal: the code part of Q2.13. A soft cap on renderer processes with Chromium's formula; over the cap a new tab of a site that already has a renderer joins it; a cross-site frame out of its embedder's view is throttled. Memory per tab measured here goes into this card; the Chromium comparison and the M1 budget go to the Mac queue.

Done (tested):
- the cap and reuse, with `DWELLER_PROCESS=site`: `ui/max-renderers.aye` (`DWELLER_MAX_RENDERERS=N`, else half the physical RAM divided by 60 MB a process, clamped to 3..82, as `GetMaxRendererProcessCount`; the 60 MB is a placeholder, not measured), `ui/renderer-count.aye` (live renderers counted by pid), `ui/reused-process.aye` (at the cap, a new tab whose URL's site has a live tab renderer of the same partition is attached to it with `attachTabProcess` and context 0; else a new renderer, the cap is soft), called from `ui/poll-tab-slot.aye`. The renderer accepts `attach_tab` with context 0 as a tab with a context of its own (`renderer/attachable.aye`).
- `window_renderer_limits::window_renderer_limits_cap` passed once (`cargo test --release --test browser -- window_renderer_limits`): with `DWELLER_MAX_RENDERERS=1` a second same-site tab has the first tab's pid and loads (`title Child 127.0.0.1?two`); a `localhost` tab gets another pid; without the variable two same-site tabs have two pids.
