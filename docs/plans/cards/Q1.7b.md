# Q1.7b: headless runs never block on the stuck bar

- goal: a headless window run (tests, `window_perf.py`, agents with `--exit-when-idle`) never waits for a click on the Q1.7 bar "This page is not responding". When nobody can answer, the bar chooses Wait, logs one line on stderr (`stuck: page busy N ms, waiting`), and the run goes on. Interactive windows are unchanged.
- cause (found by Q4.16b): `askStuck` (`ui/ask-stuck.aye`) pumped scripted words and SDL events until a click on Wait or Stop. A headless run with no such click in its `--events` (most runs have none) looped there for good once a task ran over 5 s.
- design:
  - Headless is the flag the window already has: `uiOptions` takes `o.frames > 0 || o.exit_when_idle` as headless (scripted words, `--state` and `--save` need it; `SDL_VIDEODRIVER=dummy` is set by the tests on top). `withFonts` passes it to `watchStuck`, which keeps it beside the `Ui` pointer. No second flag.
  - In a headless run the pump reads the scripted words once (`resumeScript`, which goes on until a `frame` word). If they answered (a click on Wait or Stop, or the new word), that answer stands, so `window_stuck_script` keeps testing the bar's buttons. Otherwise it answers Wait at once and logs the line. It never waits on SDL events, and a word that waits (`agents:N`, `painted`) cannot hold it either.
  - The new script word `stuck:stop` answers Stop while the bar is shown (and does nothing otherwise), so a test can choose Stop without the bar's coordinates.
  - N is the task's time so far: the hang hook is now `fn(u64) bool` and `pageGoesOn` passes `now - task_began`. The renderer's `busyHook` takes the same argument and ignores it.
  - Agents: the agent socket has no command that answers the bar, and the pump does not read the socket, so an agent run with `--exit-when-idle` takes the automatic Wait. An interactive window with an agent socket (no `--exit-when-idle`) keeps the bar as before.
  - `DWELLER_PROCESS=tab` (Q2.3e): the renderer's hang hook (`renderer/busy-hook.aye`) only sends `LongTask { on: 1 }` for the "The page is busy" chip and returns true at once. It never waits for an answer, so it cannot block a headless run; nothing changed there.
- files: `browser/ui/ask-stuck.aye`, `browser/ui/script.aye` (`stuck:stop`), `browser/ui/window.aye` (passes headless), `browser/engine/{set-hang-hook,page-goes-on}.aye` (the hook gets the busy ms), `browser/renderer/busy-hook.aye` (signature), `browser/tests/ui/stuck_load.html` (new), `tests/browser.rs` (`window_stuck_headless`)
- verify: `window_stuck_headless`: `stuck_load.html` runs a 6 s loop in its first script; with `--frames 200 --until-idle` it exits 0 within a 60 s hard limit (the child is killed after it, so a regression fails), its stderr is exactly one `stuck: page busy N ms, waiting` line, and `--state` has `unresponsive 1` and the text `start done`. Then `stuck.html` with `click:50,65 stuck:stop frame click:50,115`: `unresponsive 1`, log `start hang after` (Stop: no `catch`, no `finally`), empty stderr. `window_stuck_script` (Q1.7, Wait then Stop by clicks) still passes.
