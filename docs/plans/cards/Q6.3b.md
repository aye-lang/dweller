## Slice 1: static position of abspos children in vertical writing modes

- cause: `flexStaticShift` took the container for horizontal-tb: the main axis was horizontal for `row`, `direction: rtl` flipped only the horizontal axis, and the block axis never flipped.
- design (css-flexbox-1 4.1, css-writing-modes-4 6.4):
  - `flexStaticFactor` (new): the main axis is physical-horizontal when `row` and a horizontal mode, or `column` and a vertical mode. The inline axis flips with `direction: rtl`, the block axis with `vertical-rl`; `row` takes the inline flip on the main axis and the block flip on the cross axis, `column` the other way round.
  - `flexStaticShift`: the static spot of a child of a `vertical-rl` container is its block-start (right) edge and `staticFlip` already moves the box left of it, so the horizontal shift there is `room * (factor - 1)`.
  - `staticAlignFactor`: `left`/`right` are physical only on the container's inline axis (`right` in a vertical mode is the bottom); on the block axis they are `start`. `last baseline` falls back to `end`.
  - `startsFar` (new): `self-start`/`self-end` use the child's own writing mode and direction.
- references: https://drafts.csswg.org/css-flexbox-1/#abspos-items , https://drafts.csswg.org/css-align-3/#positional-values , https://drafts.csswg.org/css-writing-modes-4/#logical-to-physical . No Chromium file read.

## Slice 2: the scroll origin in vertical writing modes

- cause: `scrollOrigin` (which edge a scroll container's scrollable overflow starts from, css-overflow-3 2.2) read `direction` as the horizontal axis and the flex direction as if the container were horizontal-tb. In `vertical-rl` the block axis runs right to left, so the origin is the right edge, and in a vertical mode `direction: rtl` flips the vertical axis. `negative-overflow-002/003/004` count the overflow on the flipped side: `scrollWidth` and `scrollHeight` were the client size there.
- design (css-overflow-3 2.2, css-flexbox-1 5.1, css-writing-modes-4 6.4): the origin is taken on the logical axes, then mapped. The inline axis is far when `rtl`; the block axis is far in `vertical-rl` and `sideways-rl`. In a flex container `row` takes `row-reverse` on the inline axis and `wrap-reverse` on the block axis, `column` the other way round. A vertical mode puts the block axis on x and the inline axis on y. Only a scroll container (`isScroller`) has a flipped origin: a box with `overflow: visible` or `clip` counts its overflow from the top left, as before (`css-overflow/scrollable-overflow-height-with-flex-item-margin-inline-end-rtl` keeps its 3 there). `sideways-lr`'s bottom-to-top inline axis is not taken: the layout does not lay it out bottom to top, and taking it lost subtests.
- found with it: setting `scrollLeft` or `scrollTop` to the value a box already reads (clamped to a range that shrank to 0) kept the old stored offset, so it came back when the range grew again (`select-size-scrolling-and-sizing`: the `sideways-lr` case read 100 after the `vertical-rl` case's cleanup). `akSetScroll` now stores the clamped offset.
- references: https://drafts.csswg.org/css-overflow-3/#scroll-origin , https://drafts.csswg.org/css-writing-modes-4/#logical-to-physical . No Chromium file read.
- files: `browser/engine/scroll-origin.aye`, `browser/engine/scrollable-overflow.aye`, `browser/engine/geometry.aye` (`akSetScroll`); `browser/tools/conformance/css_css-flexbox.json`.
- verify (2026-11-22, WPT e58225abb9, proxy variables unset):
