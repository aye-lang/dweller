# Q3.3c: load and error events for parser-inserted scripts; import() credentials

- goal: scripts in the page's HTML (classic and module, external `src`) fire `load` after they run, and `error` when the fetch fails, the status is not ok or the CORS check fails, as scripts inserted by a script already do. `import()` uses the fetch options of its referencing script: credentials `include` from a `crossorigin=use-credentials` module, classic script or inline module, else `same-origin`. The `credentials` option of `new Worker(url, {type: 'module'})` is used for the worker's module fetches. Cross-origin modules also load on the normal path (preload scan, background loads, graph prefetch), not only on the synchronous one.
- source: Q3.3b's "left" list.
- design:
  - Events: `runScriptElement` (`engine/script.aye`) passes the result of `runModuleElement`, or of the new `runClassicElement` (`engine/run-classic-element.aye`), to `fireScriptEvent` (`engine/fire-script-event.aye`). If the script did not run, it fires `error`. If it ran and has a `src`, it fires `load`. Inline scripts get no event. This is HTML's "execute the script element": a null result fires `error`, and "from an external file" fires `load`. A classic script is null when its `src` is empty, the URL does not parse, the fetch fails (a network error or a failed CORS check) or the status is not 2xx. Before this card, a parser classic script ran the body of a 404. An inline module whose graph fails to load also gets `error`, for parser scripts and for inserted ones (`akScriptPrepare` returns 3).
  - `hostEvent` (`engine/prelude.aye`) no longer bubbles `error` at an element. HTML's "fire an event named error" makes a non-bubbling event. Before this card, a script's or an image's `error` bubbled up to the window's `error` listeners (testharness.js reports those as harness errors).
  - `import()` credentials: `ImportCall` has `include: bool`. The parser takes it from `Interp.script_include`. `runCode` sets it from the element's `crossorigin` while a classic script parses. `moduleRecord` sets it from the module's own fetch credentials, and an inline module gets it from its element (`parseModule`'s third argument). `vmModuleRuntime` passes it to `dynamicImport`. Before this card, the loader took `include` from `moduleMap.get(referrer)`. That works only for an external module, because a classic script and an inline module have the document's URL as their referrer. This follows V8 and Blink, which keep the referrer's fetch options on the compiled script (host-defined options, `ReferrerScriptInfo`). The task asked for "from an inline module, the document's default". The spec takes the inline module's own `crossorigin` instead (prepare the script element: "module script credentials mode"). With no attribute, that is `same-origin`, which is the document's default. Dweller follows the spec.
  - Module workers: the Worker constructor reads `credentials` ("omit", "same-origin", "include"; any other value is a TypeError, as WebIDL's enum). Only a module worker reads it, and a classic worker always uses "same-origin". The page answers the worker's `FETCH_MODULE` asks with that credentials mode (`wkFetch`'s fourth argument, `engine/worker-credentials.aye`). The worker's top-level script is still fetched same-origin (`FETCH_SAME_ORIGIN`).
  - Cache key decision. Q3.3b said that cross-origin modules load only on the blocking path "until the cache keys on mode and credentials". The spec's module map keys on (URL, module type), and Dweller's already does (`moduleKey` in `lib.aye`). Fetch's HTTP cache keys on the URL (and the partition), not on mode or credentials. Chromium is the same: `kSplitCacheByIncludeCredentials` in `net/http/http_cache.cc` is disabled by default. The CORS check runs on every response, also on one from the cache. So no key changes in this card. Three things change:
    - `fetchHttp` (`net/http.aye`) reads and fills the session cache for CORS requests too. `net.request` runs `corsChecked` on the cached headers, as it does on a fresh response. A response tainted by a cross-origin redirect is not kept. `net/cors-applies.aye` is deleted (it had no other user).
    - A background load can be a CORS request. `Load` has `mode`, `credentials` and `initiator` (`net.startLoadAs(href, req)`, `net/load-request.aye`; `startLoad` is now a wrapper). A CORS load does not follow redirects: the synchronous fetch does them, with their CORS checks.
    - The engine starts module loads with the module's request (`engine/module-request.aye`; `scriptRequest` for elements). This applies to the preload scan (`engine/prefetch-scripts.aye`, which replaces `scriptHrefsOf` plus `net.prefetch` there), inserted scripts (`akScriptFetch`), `import()` and graph background loads (`moduleLoad`, which gets the importer's `include` as a fourth argument), and the graph prefetch (`pagePrefetchModules`, which gets `include` from `lib.aye`). No credentialed no-cors request goes out first for a cross-origin module. The cross-origin module's own request is the one that fills the cache. `scriptHrefs` (the early loads while the HTML is parsed) still skips CORS-mode elements.
  - Request origin (found by the new test): the `same-origin` credentials check (`contextOf`) and the `Origin` header (`originHeader`) used the referrer. For a module's import, the referrer is the importing module's URL. So a cross-origin module's `same-origin` import of its own origin sent cookies, and a `use-credentials` import from it sent the module's origin as `Origin`. Both now use the request's origin, which is the initiator page (`net/request-origin.aye`, `net/same-origin-request.aye`), and fall back to the referrer as before. Fetch: a request's origin is its client's origin, not its referrer.
- changed goldens: none. `jsdom_fixtures` and `js_conformance` print the same output.

  - spec: https://html.spec.whatwg.org/multipage/scripting.html#execute-the-script-element (null result → `error`; external → `load` after it runs), https://html.spec.whatwg.org/multipage/webappapis.html#hostloadimportedmodule (the referencing script's fetch options), https://html.spec.whatwg.org/multipage/webappapis.html#module-map (key: URL and module type), https://fetch.spec.whatwg.org/#concept-request-origin.
  - Chromium `third_party/blink/renderer/core/script/script_loader.cc` (`ModuleScriptCredentialsMode`: not set and anonymous → same-origin; `DispatchErrorEvent`), `core/script/pending_script.cc` `ExecuteScriptBlock` (`DispatchLoadEvent` when external), `core/script/modulator_impl_base.cc` `ResolveDynamically` with `ReferrerScriptInfo` (credentials mode kept per compiled script), `net/http/http_cache.cc` (`kSplitCacheByIncludeCredentials`, disabled by default). ## Status: done, 2026-11-08

- Status (perf gate fix, 2026-11-08): `net_sync` on `animated` (2) and `article` (3) was over its budget of 1. Cause: the new `prefetchScripts` and `pagePrefetchModules` call `net.startLoadAs` for every script, also one that the early loads already put in the cache, and `net.awaitLoads` counted a `net_sync` for each of those loads. The old `net.prefetch` skipped cached URLs. Fix: `awaitLoads` (`net/await-loads.aye`) waits and counts only a load that is still `Running`. A cached load is `Done` and does not block.

- left:
  - The `credentials` option does not apply to a module worker's top-level script, which is fetched same-origin through `FETCH_SAME_ORIGIN`. It applies only to that worker's `FETCH_MODULE` imports.
  - The session cache does not key on credentials, as in Fetch and Chromium. A credentialed no-cors response for a URL (an `<img>`, a classic script) can be served to a later uncredentialed CORS request for the same URL, if its CORS check passes.
  - Code that `eval` or `new Function` parses, timer strings and event handler attributes have no referencing script: their `import()` uses `same-origin`.
  - `<link rel=preload>` and the WPT areas are not done (not in this card).
