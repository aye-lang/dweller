# Q4.16c: canvas 2D `drawImage` on rows of taps and an over-only composite loop

- goal: Q4.21 cost 2 (mistral's rAF `akCanvasDraw`: `canvasPaint` 1638 ms of 2930 per 10 s, `sampleImage` 1031, `canvasComposite` 573, per-pixel `mix`/`premul`). The image paint of a canvas draw samples per column and row, not per pixel, and a plain source-over composite runs without the per-pixel mode tests. Pixel results unchanged.
- design:
  - `browser/paint/image-taps.aye`: `imageTaps` maps each column (or row) of the draw area once through the inverse matrix to an `ImageTap` (source index, next index, 1/256 weight, or invalid), with the repeat and the natural-size range check of the old loop; nearest sampling is a tap with `i1 = i0`, `t = 0`.
  - `browser/paint/pattern-row.aye`: `patternRow` blends one row from the column taps and the row's tap: copy when both weights are 0 and the texel is opaque, integer bilinear without premultiplying when the four texels are opaque, else the premultiply-then-mix arithmetic of `sampleImage` inline. Same rounding as `sampleImage`/`premul`/`mix`, so no byte changes.
  - `browser/engine/paint-image.aye` (`canvasPaintImage`): the axis-aligned case (inverse matrix with `b == 0 && c == 0`: every draw without rotation or skew, including `drawImage` and `createPattern` under scale/translate) builds the taps and calls `patternRow` per row; `paint-image-affine.aye` keeps the old per-pixel loop for rotated and skewed matrices.
  - `browser/engine/composite-over.aye` (`compositeOver`): `canvasComposite` calls it for `source-over` without a clip: the old formulas with `fs = 1`, `cover = 1` folded (exactly, in floating point), no mode if-chain per pixel.
- not done: the source image is not kept premultiplied in a cache per image. `image.Bitmap` is overwritten whole in places (`c.bmp.* = image.Bitmap { ... }`, `evict-decoded`, the SVG raster in `canvasSource`) and canvases change in place, so a cache field would leak or go stale; the premultiply is instead inline per tap and skipped for opaque texels, which is where nearly all of the cost was. Path fill (`svg.render`) was not touched: it is 0.8% of the benchmark's instructions (mistral: 690 of 2930 ms per 10 s, Q4.21).
- references: `third_party/skia/src/core/SkBitmapProcState.cpp` (matrix classes: for a scale+translate matrix the x and y source positions are computed once per column and row), `src/core/SkBlitRow_D32.cpp` (source-over blit in a loop with no per-pixel mode); read via raw.githubusercontent.com/google/skia/main. Dweller takes the idea of per-axis sample tables and a mode-free over loop; the arithmetic stays Dweller's own (it must match the old bytes).
- files: new `browser/paint/{image-taps,pattern-row}.aye`, `browser/engine/{paint-image,paint-image-affine,composite-over}.aye`, `browser/tests/perf/canvas_drawimage.{html,png}`; changed `browser/engine/canvas_api.aye` (`canvasPaint` kind 4 calls `canvasPaintImage`; `canvasComposite` calls `compositeOver`).
