# Q4.30: crossorigin sheets and scripts load early again (github's first paint 2.6 → 1.1 s)

- goal: W8 (live first paint against Chrome) on github was 429 ms on 2026-11-04 (fast build, one process) and 2.1–2.6 s on 2026-11-25 (P1.S8; safe build, site mode, and 2.6 s with `DWELLER_PROCESS=single`), against Chrome's 0.54–0.59 s. Find what changed and fix it if the engine regressed.
- method: this Mac (M2 Pro), live network, 1-min load under 4 before each timed run. Builds with `browser/build.sh` (fast and safe), each with the aye at its own AYE_REV (87f48633: aye 0953905, built from its tarball; main d835ef10: aye fa807ee). "Real first paint" here is the `ui_first_paint` record (the first frame that shows the page) of a headless window run to `painted` (`--events "painted frame key:cmd+w"`), `DWELLER_PROCESS=single`, 3 samples per build alternating old/new. W8 is `window_perf.py report --live --chrome` (the binary's default, site mode).

## Cause

Q3.3 made a `crossorigin` element's fetch a CORS-mode request. A CORS-mode request for another origin without `use-credentials` sends no cookies, and the cache key has the credentials in it (`net.cacheKey` → `networkPartition`, `0/` against `1/`), so the early loads' no-cors responses were of no use to those fetches. Q3.3 left such elements out of the early loads instead of loading them with their own request: `sheetHrefs` skipped links with `crossorigin` (later also `referrerpolicy`), and `scriptHrefsOf` skipped `crossorigin` scripts and modules from another origin. On github all 19 sheets and all scripts are `crossorigin="anonymous"` on github.githubassets.com, so `startEarly` (the window's and the renderer's preload scan) started nothing:

1. With no sheet and no script loads, `sheetsIn` and `scriptsIn` are true at once, so the navigation's first `advanceLoad(at_once)` ran every script before the first paint (`prefetch` 0.3 s, `scripts` 0.36–0.78 s).
2. The style pass's `prefetchSheets` used `sheetHrefs` too and prefetched nothing, so `linkedSheet` fetched the 19 sheets one at a time (`net_sync` 37–72 ms each): `sheets` 1.03–1.09 s.

Main (fast, single), one sample: document 247 ms → `ui_navigate` 273 → `prefetch` 298 → `scripts` (core 101, code-view 141, ...) → `sheets` 1030 (19 requests in a row) → `ui_relayout` 1209 → `ui_raf` 115 → `paint` 215 → first paint 2456. Before Q3.3 the sheets loaded together right after the document and the page was painted before its scripts ran.

Chrome starts the render-blocking sheets from its preload scanner as the document arrives, all on the one HTTP/2 connection to github.githubassets.com, and the module scripts are deferred, so they do not hold its first contentful paint (0.52–0.60 s).

## Fix

- The early loads and the style pass's prefetch load each element with the request its fetch makes, so they share its cache key:
  - sheets: `startSheetLoads` (`engine/start-sheet-loads.aye`) starts a load per link with `sheetRequest` (`sheet-request.aye`, the request `sheetFetch` makes: CORS mode from `crossorigin`, the link's referrer policy, the top page). `unfetchedSheetLinks` (`unfetched-sheet-links.aye`) replaces `sheetHrefs`: no `crossorigin`/`referrerpolicy` exclusion, and a link counts as fetched by its own mode (`sheetMode`). `prefetchSheets` and `startEarly` (through `pageSheetLoads`) use it; so does `stylingWithoutFetch`, which used to see a page with only `crossorigin` sheets as having none to fetch.
  - scripts: `startScriptLoads` (`start-script-loads.aye`) is `prefetchScripts`' loop (`scriptRequest`, CSP-refused URLs left out); `prefetchScripts` and `startEarly` use it. The early loads used to skip the CSP check.
  - `scriptHrefs`, `scriptHrefsOf`, `startLoads` and `sheetHrefs` are gone (no other users).
- test: `early_loads_crossorigin` (`tests/browser/http_cache.rs`, page `browser/tests/net/early_cors.html`): two `crossorigin` sheets and a `crossorigin` module script, each answered after 0.4 s (`/ordered/slow-*`), a background image that only a layout asks for, and a script after the module that asks for `ran.txt`. From the server's `/order-at`: the three must be asked for within 300 ms of each other, and the background image before `ran.txt`; in one process and with a renderer per site. Base fails: `slow-m.js:12781 ran.txt:13197 slow-a.css:13262 slow-b.css:13675 laid-out.png:14091` (894 ms apart, the scripts before the first layout). Fix: passes in both modes.

## Security review: CORS and credentials of the early loads

Q3.3 (its card, line 6) kept `crossorigin` elements out of the early loads so that no credentialed no-cors request goes out for them first, and said that `fetchHttp` neither reads nor fills the HTTP cache for a `Cors` request. Checked on this branch:

1. A background load gets the same request handling as the synchronous path. `startJob` → `prepare` → `requestHeaders` / `contextOf` (`net/http.aye`, `net/cookies.aye`) are the functions `transfer` uses. So a `Cors` load sends `Origin` and `Sec-Fetch-Mode: cors`, and it sends cookies only when `contextOf` allows them; `SameOrigin` credentials to another origin give `Context.Omit`. A `Cors` load does not follow a redirect (`finishLoad`): it fails, and the fetch that follows makes the request itself, with the CORS redirect rules. A background load only puts its response, with its headers, into the browser's HTTP cache (`keepLoad`). Nothing hands a load's body to a page except `net.request`, which runs `corsChecked` and then ORB on every response, cached or not. A failed check is `FetchError.Network`, a load error. In site mode a renderer's loads run in the browser (`answerFetch` → `holdFetch` → `startSecuredLoad`). When one ends, `finishHeld` answers with `net.request(heldRequest(h))`, so the check runs in the browser before `sendFetched` gives the renderer a body; a failure sends `FetchFail`. The renderer keeps the responses that land under the cache key plus `requestCode` (kind, credentials, mode).
2. Joins. `findKeyed` matched the cache key alone. The cache key has the credentials flag (`networkPartition`: `0/` or `1/`), so an anonymous use of another origin never joined or read a no-cors load. A same-origin anonymous use, or a `use-credentials` use, has the key of the no-cors use, though. Such a pair was one load, and one request with the first element's mode. Fixed: `findKeyed` (`net/find-keyed.aye`) also matches the request mode and the credentials mode, as Blink's `Resource::CanReuse` does. The HTTP cache key is unchanged. The renderer side already matched them (`remoteKeyed`, `landedAt`).
3. Cache. Q3.3's rule no longer holds. Q3.13 (59eca2d7, the same day) keyed the HTTP cache by top-level site, frame site and credentials, and dropped `req.mode == Mode.NoCors` from `fetchHttp`'s `cacheable`. Since then the synchronous `Cors` path reads and fills the cache. A `Cors` background load does the same as that path: `startLoadAs` takes a cached key as done, and `keepLoad` stores under the same key. It is safe for two reasons:
   - An anonymous use of another origin has a key of its own, so it never gets a credentialed response.
   - Every read is checked in the browser against the reader's own request: `corsChecked` with the stored headers, then ORB.

   What remains is as in Chromium's HTTP cache, which has no mode in its key either. When both uses send credentials, one entry serves both modes. Dweller also reuses an entry within a page load even with `Vary: Origin` (`usableEntry`: same epoch). The worst case is a false CORS failure, not a leak: a `use-credentials` use reads a no-cors response that has no ACAO.
- test: `early_loads_keep_credentials` (`tests/browser/http_cache.rs`, page `browser/tests/net/early-mixed.html` through `/with-other/`, a second server on 127.0.0.1 as the other origin of the same site, cookies from `/samesite/set`). The same URL is used with and without `crossorigin="anonymous"`, in both orders, for sheets (`/logged-acao/`, the server logs `Origin` and `Cookie`) and scripts (`/cookie-module?acao`, the script reports the `Cookie` header of the response it ran). The test checks five things:
  - each sheet URL is two requests: one without `Origin` and with the cookies, one with `Origin` and no `Cookie`;
  - the anonymous scripts ran with `""`;
  - the no-cors scripts ran with the cookies;
  - an anonymous script without ACAO does not run;
  - a same-origin sheet pair (`/meta/`) is two requests, one `Sec-Fetch-Mode: cors`.

  Without the `findKeyed` change it fails: the same-origin pair is one `no-cors` request. With it, it passes in default (site) mode and with `DWELLER_PROCESS=single`.

## Left

- github's gap is still about 0.5 s (1.08–1.10 s against 0.53–0.60 s). After the document: the sheets about 0.25 s, style and layout 0.18 s, the viewport paint 0.22 s (0.32 s in replay, P1.S8). The paint is the largest part we own.
- `window_perf.py scroll` falls back to `ui_navigate + ui_relayout + ui_draw` when a run has no `ui_first_paint`; that sum can be a frame without the page (2026-11-04's 429 ms). P1.S8 found that single-mode light pages (abehiroshi, duckduckgo) still write no `ui_first_paint`, so the fallback is still in use. The window should write the record for a navigation that ran before its loop too; then the fallback can go.
- Images with `crossorigin` or `referrerpolicy` are still left out of the early image loads (`prefetchImages`, `images.aye`) for the same reason as the sheets were. They do not hold a first paint; not measured.
- The HTTP cache keeps one entry per key for every request mode, and within a page load it does not honor `Vary: Origin`. So when a no-cors use and a `use-credentials` (or same-origin) CORS use of one URL both load, the CORS use can read the no-cors response and fail its check. That is a false load error, not a leak. Chromium's cache honors `Vary`, so there a server that sends `Vary: Origin` gets separate entries. Not changed here: the cache key stays as it is.
