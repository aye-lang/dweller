Conclusions:
- With a renderer per site the window's loop leaves script: bbc 553 → 50, react 138 → 20, zol 726 → 18 (click runs). Mistral does not: 1176 → 1415, because the window waits on something outside its own records (PERF.md note 4). Bbc click runs have one 200 ms `ui_draw` in 2 of 3.
- The renderer's longest task grows: bbc 499 (in process) → 4133 ms, zol 511 → 1531, react 44 → 407. In process the window runs the load's scripts one per iteration (`stepPageScripts`); the renderer runs them in one `scripts` task (`runDocument`).
- The person still waits for the renderer: the window presents 14–22 ms after a wheel (p95) and 2–5 ms after a click, but with the old pixels; the scrolled frame comes with the renderer's `input_ack`, after its task (bbc: up to 503 window iterations, tasks up to 5094 ms). So the window's loop passing 100 ms does not make the page interactive. The as-seen time had no record; `step_ms` measures it, but its runs were cancelled to free the machine lock.
- Zol with a wheel hangs in site mode (3 of 3, 0% CPU).
- React in process: a click costs two 293 ms `restyle` `subtrees`.

## Note: W7 with a renderer per site

1. The window stays responsive: the window's longest loop iteration < 100 ms over the load and 40 wheels (`longest_loop_ms`).
2. The page answers: from each wheel to the renderer's frame that holds it, p95 < 33 ms, and from each click to the renderer's next frame, p95 < 100 ms (`step_ms` p95 of the scroll and click runs); idle CPU < 5% summed over the window and its renderers (today `idle` reads the window's pid only, so a site-mode mistral would look idle).
Command per site: `DWELLER_PROCESS=site DWELLER_REPLAY=target/sites/S python3 browser/tools/window_perf.py scroll URL --step "renderer:loaded wheel:-3 renderer:input" --run-frames 8000` (and the click step with `--frames 10`). (c) What the window needs to scroll from a renderer's last frame while the renderer is busy:
1. Pixels outside the viewport. A renderer's buffer is the viewport (`docs/process-model.md` §5); the renderer must paint a taller buffer (for example a screen above and below), the window shows a window of it at an offset with P4.36c's ring (`rollRing`, two rects in `presentPage`), and a scroll past it draws the background and counts a miss.
2. The root scroll offset owned by the window during a gesture: the window applies the wheel delta at once and sends it on; the renderer takes it at its next task (scroll events, IntersectionObserver, `input_ack{consumed}` later).
3. When it may not: the frame carries the regions with non-passive wheel listeners, and the fixed and sticky items as their own buffer (P4.36a's pinned layers across the process line); nested scrollers stay with the renderer at first.
Chromium:
- `cc/input/input_handler.h`: `ScrollBegin`/`ScrollUpdate` run on the compositor thread; `ScrollThread::kScrollOnMainThread_NotUsed` (all scrolls are impl-side now); `HasBlockingWheelEventHandlerAt` decides when the main thread must see the wheel first.
- `cc/trees/layer_tree_host_impl.cc`: `CalculateRenderPasses` draws checkerboard quads for missing tiles instead of waiting; `DidScrollContent` raises new-content priority when a scroll checkerboards.
- `docs/threaded_compositing.md` is not in this checkout; read instead `docs/website/site/developers/design-documents/compositor-thread-architecture/index.md` (lines 16, 32, 114–119): input goes to the impl thread first, it scrolls the snapshot while the main thread is blocked, tiles are prioritized by distance from the viewport.
