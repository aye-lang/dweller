# Q1.12: the webaudio SIGSEGVs of the 2026-11-09 conformance run

- goal: find and prove the cause of `CRASH exit -11` on `webaudio/the-audio-api/the-audiobuffersourcenode-interface/{audiobuffersource-basic,audiobuffersource-playbackrate-negative,audiosource-time-limits}.html` in the weekly run 42610008144 (Ubuntu). Suspect: the compiler bump to aye 2c95915 (O7.7 bounds-check elimination) in 8d8e259e; `AYE_REV` is now e758396, which also has O7.9 (6aa893b, "safe mode's checks jump to one panic call per kind").
- build mode: the weekly job runs `browser/build.sh` with no `--mode`, so it is `--mode safe` (checks on).
- ran (Mac, arm64, Dweller `main` bd2e1695, aye e758396 at `/Users/solemnis/Documents/ayelang/aye/target/release/aye`):
  - `AYE=... scripts/capped.sh browser/build.sh --mode safe > target/build.log` (ok)
  - `scripts/capped.sh python3 browser/tools/wpt.py run <the three pages> -j 1 --results-dir target/q112-results`: all three `CRASH`, `exit -11: ` with an empty stderr. **Reproduced on macOS arm64 at e758396.**
  - `lldb -b -o run -o bt -- target/dweller wpt http://127.0.0.1:8771/webaudio/.../audiobuffersource-basic.html --timeout 10` with `wpt.py serve --port 8771` (script: `wpt.py serve` in the background, then lldb):
    `EXC_BAD_ACCESS (code=1, address=0x40725c003072450)` in `libsystem_platform.dylib _platform_strlen + 4`, main thread. `bt` did not print (`-o` stops after the crash; it needs `-k bt`). The second run with `-k 'bt 12'` was stopped while it waited 40+ minutes for the machine lock.
- what the evidence says so far (likely, not proven):
  - A `strlen` on a wild pointer with nothing printed on stderr fits a safe-mode check that **fired** and then crashed in the panic call: `aye_panic` prints `AYE_FILE(line)` and `msg` with `%s`. Since O7.9 the message pointer reaches `aye_panic` through the function's `aye_pm_` local (`AYE_PANIC_GO` stores it, then `goto aye_panic_`; `AYE_PANIC_AT` at the end of the function calls `aye_panic(aye_pl_, aye_pc_, aye_pm_)`, `src/cgen.rs` lines 559-580 and `fn func` about line 2680). A garbage `aye_pm_` / `aye_pl_` (never stored on the path that reached the label) gives exactly this crash. That would make it a compiler bug in O7.9, not a check removed by O7.7, and not a memory-safety hole: the check did its job, the report of it crashed.
  - The check that fires is very likely `f as u64` in `frameAt` (`browser/audio/audio.aye` line 469): all three pages pass a time whose frame does not fit `u64`. `audiobuffersource-basic` calls `start(Infinity)` (`start-stop-exceptions.js`; the JS in `browser/engine/audio_api.aye` `_start` only rejects `!(when >= 0)`, so `Infinity` reaches `audio.start`), `audiosource-time-limits` calls `stop(1e300)`. The negative-playbackrate page was not read. So there is also a browser bug: those times must be clamped (or `start(Infinity)` must throw `TypeError`, which the test expects) instead of reaching a checked cast; before O7.9 this would have been a clean `panic: float to integer cast out of range`, exit -6.
- ruled out:
  - The cast check itself: a 20-line copy of `frameAt` (`frameAt(&cx, 1e300)`, `aye build --mode safe`) panics correctly, `main.aye:14:14: panic: float to integer cast out of range`, exit 134, in debug and safe mode (fast prints a wrong value, as allowed). So the joined panic works in a small function; what differs in Dweller is not known yet.
  - The aye compiler has no switch to turn O7.7 off (`aye build --help`; `bce::program` always runs in `oir::lower`).
- WebGL pages (not run here): the 4gb / 2gb-in-4gb wasm pages work with sizes near `u32`/`usize` limits, so a failed cast or overflow check whose panic report crashes would also give `exit -11` there; the two `exit -6` pages are what a panic that works looks like. So this cause would plausibly explain them, but that is not checked.
