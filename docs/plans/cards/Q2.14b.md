# Q2.14b: a headless `--events` / `--frames` run waits for the renderer by itself

- goal: Q2.14a's proposed readiness row 1 (cause rows 1 and 5, 22 tests), and what Q2.14d left to it: a headless window test written for one process (`--frames N --events "..." --state --text`, no `renderer:` word) gives the same output with `DWELLER_PROCESS=site`, with no edit of the test.
- source: `docs/plans/cards/Q2.14a.md` rows 1 and 5; `docs/plans/cards/Q2.14d.md` "Left". The branch `q2-14b-events-wait` (bb1c471, c66353a) had no card; this one is written in the wave of 2026-11-16 and covers the branch and what was built on it.
- what the branch did: a script without a `renderer:` word sets `Ui.auto_waits`; an event word then waits while `rendererBehind` (no hello yet, loading, a traversal, a URL not committed, input not acked), and a frame drawn while the renderer is behind is not counted for `--frames`.
- what the first run of the wave showed (180 / 249, the three branches merged): none of row 1 passed. Four causes, none of them the wait itself:
  1. with `--frames 1` the run ended at the first counted frame, before the script was resumed: in one process `Ui.script` feeds every word before the loop starts, under the flag the first word is held;
  2. `--state` printed the window's own (empty) page: `scroll 0`, no `element` / `value`, no `frames` / `frame_urls`;
  3. `--state` ended with the `renderer ...` lines (pids), which no golden of a one-process test has;
  4. real differences of the renderer's page, found once 1 to 3 were out of the way (below, "product gaps").
- design:
  - the script before the frame (`ui/script.aye`, `ui/window.aye`, new `ui/script-behind.aye`): `resumeScript` notes `Ui.script_held` when an event word is held for the renderer; the loop resumes a held script at the top of each iteration, and a frame is counted only when `scriptBehind` is false (script not held, renderer not behind, and, in an automatic script, no wheel delta waiting for the iteration's flush). `rendererBehind` also waits for a find reply (`find_seen != find_id`): the renderer keeps one find command, so two `key:return` in a row were one step. Nothing changes when `auto_waits` is false (one process, or a script with `renderer:` words).
  - the page's state from the renderer: two messages, B→R `ask_state{with_text}` (80) and R→B `state{scroll, frames, focus, content}` (81), both on frame 0. At the end of a headless run with `--state` or `--text` the window asks once (`ui/ask-state.aye`, the shape of `askRenderer`: it answers the renderer's own asks while it waits) and `writeState` prints the renderer's `scroll`, `frames` / `frame_urls` and `element` / `value` lines where its own page would be; `--text` prints `content`. The lines are written by the same code in both modes: `pageview/write-focus.aye` and `pageview/write-frames.aye` (moved out of `ui/forms.aye` and `ui/script.aye`). Before it answers, the renderer lands its loads and runs its due tasks (`settleLoads`, `runTimers`): what the agent `wait` of the removed `ui/renderer-text.aye` did, without that command's full layout (Q2.14d's Left: the extra `cascade`).
  - `--processes` (new, only with `--state`): the `renderer`, `renderer-cursor`, `renderer-site`, `renderer-pids`, `renderer-child`, `renderer-frame` and `sad-tab` lines are printed only with it, after the page's lines. The `window_renderer*` tests pass it. Decision (nobody to ask, so by the plan's default "tests need no edit"): the alternative, every exact `--state` comparison stripping lines it never asked for, would touch each one-process test and still fail on pids.
  - a `select` popup in an automatic script: `takePopup` waited for the button's release, which a scripted `click:` never sends (one process acts on the press); it now opens at once when `auto_waits`.
- product gaps found and fixed (each was hidden behind causes 1 to 3):
  - a renderer never scrolled to a URL's fragment (`long.html#end`: `scroll 0`, in one process `scroll 958`), and a link to a fragment of the shown document loaded the document again through the browser. Now `renderer/load.aye` aims at the committed URL's fragment unless the entry has a saved offset, `renderer/settle-fragment.aye` scrolls after the next layout (the id's or `a name`'s box; `top` and the empty fragment are the top), and `renderer/follow-fragment.aye` navigates in the document (`engine.fragmentNavigate`, popstate and hashchange, the link keeps the focus), which `reportHistory` tells the browser as `same_document`. Left: a traversal to an entry whose saved offset is 0 scrolls to its fragment (in one process the saved 0 wins).
  - a click on a row of a list box (`select multiple` or `size`) did nothing in a renderer. The window's `clickListBox` is now `pageview/click-list-box.aye` (with `list-row-at.aye`, `choose-list-option.aye`), called by the window and by `renderer/click-at.aye`.
- IPC: 80 `ask_state`, 81 `state` (`ipc/message.aye`, `decode.aye`, `put-payload.aye`, `from-renderer.aye`; unit test `ipc/state_test.aye`).
- the untrusted renderer: `state` outside an ask is a bad message (`unexpected state`, kill). In an ask, the scroll is checked with `badScroll`, `frames` and `focus` are at most 64 KiB, `content` is bounded by the payload limit (the renderer cuts it at 900 000 bytes); a reply that fails a check is dropped and the window prints its own lines. The text goes only to the stdout of a headless run, which a test reads about its own page; the window reads none of it back.
- files: new `browser/ipc/state_test.aye`, `browser/pageview/{write-focus,write-frames,click-list-box,list-row-at,choose-list-option}.aye`, `browser/renderer/{say-state,aim-at-fragment,settle-fragment,follow-fragment}.aye`, `browser/ui/{ask-state,said-state,script-behind}.aye`; removed `browser/ui/renderer-text.aye`; changed `browser/ipc/{message,decode,put-payload,from-renderer}.aye`, `browser/renderer/{answer-all,adopt-page,click-at,load,new-tab-renderer,paint-frame,run-act,tab-renderer}.aye`, `browser/ui/{forms,renderer-behind,renderer-sent,script,take-popup,window}.aye`, `tests/browser.rs` (`WINDOW_USAGE`), `tests/browser/window_renderer*.rs` (`--processes`; `window_renderer_input` compares its scroll and field with the in-process run instead of requiring `scroll 0` and no `value hello`, which described the window's old empty copy).
