#### P4.75r: a full restyle is fast

- goal: make one full restyle cheap instead of avoiding it (P4.75g/k/l/q barely moved github): github's `style_full` 2603 ms over 9 full restyles (~290 ms each) and `script_layout` 1497 ms over 7 forced layouts (P4.75q, fast build).
- measurements (github, P4.75d archive, `browser/build.sh` fast binary of `origin/p4-75q-has-invalidation`, M2 Pro, capped; temporary counters in `computeStyles`/`considerRule`, not committed; macOS `sample` of the whole run):
  - one full restyle (the 5th): 2428 elements (43 in shadow trees), 19339 author rules, 29648 complex selectors, 275 rules in the index's fallback bucket; 978569 candidate rules (403 per element), 763452 complexes rejected by the ancestor Bloom filter, 1483769 complexes matched (611 per element), 25819 rules matched (10.6 per element).
  - time: selector matching 385 ms, cascade + value computation + inheritance + allocation (`compute`) 11 ms of one instrumented restyle: 97% is matching. The `sample` agrees: `matchSimple` 1063, `Document.attr` 159, `Document.node` 147, `matchFrom` 125, `upElement` 112, `considerRule` 91, `heapSort` 88 samples, against `computeValues` 21 and `specified` 17.
  - top selectors by matching time (per-complex clock): 10 complexes of the form `.prc-ActionList-ActionListItem-So4vC:not([data-is-disabled],[data-has-subitem=true]):where([data-inactive=true]) * :not([popover],.prc-ActionList-InactiveWarning-1Dszv)` (Primer), each tried on all 2426 elements at ~32 µs each: about 65% of the matching time. Next, at about 1% each: `:is(…) .octicon`, `:is(…) [class…]`, `.Primer_Brand__SubNav-module__SubNav__link…[aria-current]:not(…) *`.
- cause: (1) the subject `:not(…)` puts these rules in the fallback bucket, and the Bloom filter's key (`ancestorKey`) came only from the nearest compound left of the subject, here `*`, so there was none: every element was tried. (2) Each try costs O(depth²): for each ancestor matching ` *`, `matchFrom` walked all ancestors again for `.prc-ActionList-ActionListItem-So4vC`. (3) The filter was 256 bits with 2 bits per id, class and type: on github's deep, class-heavy ancestor chains it is mostly full, so even a good key passed about half of the elements. (4) After those, sorting every element's ~400 candidates (`heapSort` + `ruleBefore`) was the largest cascade cost left.
- design (Blink's algorithms, no code copied):
  - `ancestorKeys`: up to 4 keys per complex, from every compound reached through descendant or child combinators (sibling compounds are skipped), as Blink's `CollectDescendantCompoundSelectorIdentifierHashes`; `ancestorsMayMatch` needs all of them.
  - the ancestor filter is 2048 bits (`[32]u64`), still 2 bits per key (Blink: 8192 bits, 1 bit).
  - `matchSelector` returns a `MatchStatus` (`Matches`, `FailsLocally`, `FailsAllSiblings`, `FailsCompletely`), as Blink's `SelectorChecker::MatchForRelation`: a descendant combinator whose left part fails for every ancestor fails completely, so the outer loop stops; a child combinator turns a local failure into failing for all siblings; `~` stops on anything but a local failure. `matchFrom` is `matchSelector(…) == Matches`. This makes `A * B` linear in the depth.
  - `considerCandidates`: the index's candidates come in any order with repeats; the cascade matches each, keeps the rules that match (`MatchedRule`: rule, specificity) and sorts those (about 10 per element) into source order, as Blink's `SortAndTransferMatchedRules`, instead of sorting the ~400 candidates. `pseudoCandidates` still sorts. `considerRule` = `ruleSpec` + `offerRule`.
