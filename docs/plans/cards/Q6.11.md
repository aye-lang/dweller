# Q6.11: WPT `url`, UTS #46 host processing

- goal: `url` goes from 66.7% to its threshold (80). The largest failure cluster with one cause was `domain to ASCII`: `uts46ToAscii` only lower-cased ASCII, so every internationalized host (`IdnaTestV2`, `toascii`, `url-constructor`/`url-origin`/`a-element` host rows) was wrong.
- design:
  - new core module `browser/idna/` (layer `core`, imported by `url`): `pub fn toAscii(alloc, domain, out)` is UTS #46 Processing with the URL Standard's flags: UseSTD3ASCIIRules false, CheckHyphens false, CheckBidi true, CheckJoiners true, Transitional_Processing false, VerifyDnsLength false, IgnoreInvalidPunycode true.
  - steps, one file each: `map-domain`/`map-char` (mapping table: valid, mapped, ignored, disallowed), `normalize-nfc` (`decompose-char`, `reorder-marks`, `compose-in-place`, `compose-pair`, Hangul algorithmic), `decode-labels`/`decode-label`/`decode-ace` (`xn--` labels through `punycode-decode`; an invalid one is kept as is), `check-domain`/`check-label` (NFC, no leading mark, every code point valid), `check-joiners` (ContextJ), `check-bidi-label` (RFC 5893 rule, applied when a label has R, AL or AN), `encode-labels`/`punycode-encode`.
  - IgnoreInvalidPunycode: a `xn--` label that fails Punycode decoding, decodes to ASCII only or fails validity or the bidi rule is kept; but a domain that keeps such a label and also has a non-ASCII non-`xn--` label fails (`check-retained-ace`, from `toascii.json` `xn--a.ß`).
  - tables are binary files (`browser/idna/*.bin`, little-endian u32 words) read with `@embedFile`, generated by `browser/tools/gen_idna.py` from the Unicode 18.0.0 files (`https://www.unicode.org/Public/idna/latest/IdnaMappingTable.txt`, UCD `UnicodeData.txt`, `DerivedNormalizationProps.txt`, `extracted/Derived{CombiningClass,JoiningType,BidiClass,GeneralCategory}.txt`). The generator's docstring says how to rerun it. UTS #46 deviation characters are valid (non-transitional) and the STD3 statuses fold to valid/mapped (UseSTD3ASCIIRules false). Total about 230 KB.
  - rule 6: no C library with UTS #46 data is linked (libcurl is built without IDN, nothing else carries ICU), so the tables are generated from Unicode data, not hand-written.
  - `browser/url/domain-to-ascii.aye` calls `idna.toAscii`; `uts46-to-ascii.aye` (the lower-casing stub) is gone. `check_layers.py` lists `idna` in the core layer.
- references: https://url.spec.whatwg.org/#concept-domain-to-ascii , https://www.unicode.org/reports/tr46/ , https://www.rfc-editor.org/rfc/rfc3492 , https://www.rfc-editor.org/rfc/rfc5893 , https://www.unicode.org/reports/tr15/ . Chromium `url/url_canon_icu.cc` (`IDNToASCII` through ICU `uidna_nameToASCII` with UIDNA_CHECK_BIDI | CHECK_CONTEXTJ | NONTRANSITIONAL_TO_ASCII; algorithm only): Dweller takes the same flag set, with its own tables.
- files: new `browser/idna/*.aye`, `browser/idna/*.bin`, `browser/idna/to-ascii_test.aye`, `browser/tools/gen_idna.py`; changed `browser/url/domain-to-ascii.aye`, `browser/tools/check_layers.py`, `browser/tools/wpt_areas.json` (url threshold 80 -> 88), `browser/tools/conformance/{url.json,history.csv}`, `docs/conformance.md`; removed `browser/url/uts46-to-ascii.aye`.
