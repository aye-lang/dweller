## Row 1, as built

- `window.close()`: in a renderer a close is no longer left to the engine's in-memory serving (which only runs outside input and closes nothing real). `engine.closeThroughBrowser` (set by `renderer.serveOn`) makes `closeContext` note the context (`remote-closes.aye`) and mark it `closing`; `reportPage` sends each as `context` (64) with `ask` 2 (`sendCloses`), from any turn, a page's load included. The browser accepts `ask` 2 without the gesture check (`closeAsk`; a close needs none), and `askClose` marks the tab: the one whose home is that context in the sender's process (a popup the sender opened, or the sender itself when it is a popup at home), else the sender itself when a script opened it (`TabSlot.by_script`, set by `openedSlot`). `closeAskedTabs` (after the poll round; never inside it, since the sender's own slot may be the one that goes) removes the tab and shows its opener's tab when it was shown, as the one-process window does; the last tab is never closed. A hosted Space's tab closes in `closeHostedAsked` once no request is out on it. The forged-message test's value for a bad `ask` is 3 now.
- `closed`: true once `close()` was called on the window (`BrowsingContext.closing`), as the specification's "is closing"; the opener's message handler of the sign-in round trip reads it before the tab is gone.
- a message between two tabs of one renderer: `queueMessage` counts (`takeLocalMessages`), and after a tab's batch `reportOthers` wakes the other tabs when one was posted (`wakeForMessage`), so a hidden opener handles its popup's message at once (Q2.15n's Left item).
- `rendererSettled`: a tab whose next navigation is recorded but not sent yet (`tp.url` cleared by `openTarget`) is not settled; `--until-idle` ended the run in that gap (1 run in 2 of the named-target part of the test under the suite's load; 0 in 3 after).
- verify: `DWELLER_PROCESS=site cargo test --release --test browser -- window_login_popup`: passed 3 times of 3; `window_renderer_popup` (12 tests, `tab` and `site`): 0 failed.

## Row 2, as built

- The person's tab's own process answers. `ask_user_context` (IPC 95, browser to renderer: `id`, `point`) and `user_context` (96, renderer to browser: scroll, selection, `hovered`, `focused` and, for a pointing, the node) are new. The renderer builds the two nodes with the agent's own ref table (`agent.userNode`, `agent.pointedNode`; `renderer/answer-user-context.aye`), from its mouse position (`TabRenderer.mouse_in`, `mouse_at`, kept by `mouseInput`), its focused control and its selection. The browser checks the reply (`takeUserContext`: sizes, the two members parse as JSON) and adds what it owns: the tab, the URL, the title, what was pointed at last (`rendererContext`).
- `user_context` of a hosted Space is parked (`parkForContext`, `checkContext`) until the person's tab has a process that has loaded and has taken the person's input (`personBusy`), then asked and answered when the reply is in. A question that came before the tab had a process was answered from the window's own empty tab; it waits now.
- Cmd+Shift+K asks the same way with `point` 1 (`askPointed`, `takePointed`, `tellPointed`). The agents' next lines are not served while the pointing's answer is out, nor while a scripted word of the person is held (`personAhead` in `serveLines`), so `user_pointed` comes before the answers to what the agents asked after it, as in one process.
- The window's start-up events are handled before the script's first word (`startUpEvents`). SDL's own `leave` events of the window's creation came after the script's first words in one process and before them under the flag, so `hovered` differed. The golden `isolation.out` is blessed for that (ids 1 and 21: `hovered` was `null`, is `generic [e2]`): the mouse is at 400,300 over the page's tall `div` when the agent asks; `null` was the start-up `leave` arriving after the scripted move.
