# P4.75n: eval inside a function does not see the page's global bindings

- symptom: P11.14 group 3, 170 WebGL conformance pages: `wtu.failIfGLError(gl, 'gl.pixelStorei(gl.UNPACK_COLORSPACE_CONVERSION_WEBGL, gl.NONE);')` logs `threw exception ReferenceError: gl is not defined`.
- reduced case: `js/webgl-test-utils.js` defines `var failIfGLError = function(gl, evalStr) { try { eval(evalStr); } ... }` inside a strict IIFE. The `gl` the string reads is that function's parameter, not a global. On `origin/p11-14-webgl-cts` (no P4.75f) both engines run every `eval` as an indirect (global) eval, so the parameter is invisible: `function f(gl, s) { return eval(s) } f({}, "gl")` throws. With P4.75f (this branch's base) the CTS page passes the eval (checked with the real `js-test-pre.js`, `webgl-test-utils.js`, `tex-image-and-sub-image-2d-with-canvas.js` at 193020cd37 and a stub context). Globals were never the problem: `var`/`let`/`const`/function at a classic script's top level, read from a helper in another `<script>` or file, by direct, `(0, eval)` and `window.eval`, inside a function or at top level, with the VM on and off, all resolve.
- second bug found while reducing: indirect eval ran its code as a script (`evalScript` → `Resolver.script`), so its top-level `let`/`const`/`class` went into the realm's global lexical record and later evals saw them: `(0, eval)("let nl = 5"); eval("nl")` gave 5, not a ReferenceError; a strict indirect eval's `var` leaked to the global object.
- cause: PerformEval for indirect eval makes a new declarative environment over the global environment (ECMA-262 19.2.1.1 steps 16–18); the script path has none.
- fix: indirect eval goes through the direct-eval path (P4.75f) with a fresh empty script scope as its call site (`globalEval` appends a `SCOPE_SCRIPT` `ScopeInfo` and calls `runEval`). The eval body is resolved as an arrow below that scope: its lexicals stay in its own scope, sloppy `var`s and functions still go to the global object (`evalHoistVars`), strict ones stay local. The shared tail of `directEval` moved to `runEval`.
