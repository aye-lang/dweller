# Q4.12a: a slow transfer that keeps receiving bytes is not cut off; a stall limit replaces the 30 s total limit

- goal: a response that keeps arriving loads however long it takes; only a transfer that receives no byte for a while fails. Found on zol: its ad CDN sends an 818 KB script at about 10 KB/s. Chrome keeps loading it; Dweller cut every transfer at 30 s (`TIMEOUT_MS`, libcurl `CURLOPT_TIMEOUT_MS`, a limit on the whole transfer) and logged a network error, 2 console errors over the site's limit.
- rule (chromium): `net/` has no total time limit on a transfer that progresses. A connection that stops is ended by an idle timeout. The only read idle default in `net/` is QUIC's idle connection timeout, 30 s (`net/quic/quic_context.h`, `GetIdleConnectionTimeout`; 300 s behind the `kQuicLongerIdleConnectionTimeout` feature). Over TCP Chrome has no read timeout: TCP keep-alive after 45 s (`net/socket/tcp_socket_posix.cc`, `kTCPKeepAliveSeconds`) only ends a dead peer, and a live server that sends nothing is waited for. `net/socket/client_socket_pool.cc`'s 5 minutes (`g_used_idle_socket_timeout_s`) applies to idle sockets in the pool, not to a transfer.
- N = 30 s, QUIC's idle connection timeout. It is the same number as the old total limit, so a server that sends nothing fails as soon as before. Dweller is stricter than Chrome over TCP for a live server that sends nothing.
- fix:
  - `net/http.aye` `prepare` (every transfer: documents, subresources, workers' scripts, `fetch` and XHR, the agent's fetches, downloads): `CURLOPT_LOW_SPEED_LIMIT` 1 and `CURLOPT_LOW_SPEED_TIME` `stallSeconds()` instead of `CURLOPT_TIMEOUT_MS` 30000. The 10 s connect timeout, `MAX_DOCUMENT` and `MAX_SUBRESOURCE` stay as they are.
  - `net/stall-seconds.aye` (new): `STALL_SECONDS` 30; `DWELLER_STALL_SECONDS` sets it (for tests, as `DWELLER_HOST_CONNECTIONS`).
  - `net/endless-job.aye`: a request marked `stream` (EventSource, a fetch body read as a stream) gets `CURLOPT_LOW_SPEED_LIMIT` 0, so it has no stall limit, as it had no total limit before. `Job.endless` is removed: only `lengthenJob` read it.
  - `net/lengthen-job.aye`: a loop pass of over 5 s still lengthens the connect timeout. It no longer lengthens a total limit, and the stall limit needs no lengthening: bytes that arrive while the loop is blocked wait in the socket, and libcurl reads them before it checks the speed.
  - limits that the page sets stay as they are: `AbortSignal.timeout` and an abort are the page's timers (`engine/prelude.aye`).
- how libcurl measures a stall: it fails a transfer whose speed stays under 1 byte/s for N seconds. The speed is the average over its last 5 one-second samples (`lib/progress.c`). A response that sends no byte of its body fails N s after the request. A response that stops after some bytes fails 5 to 6 s later than N. Measured with `curl` 8.7.1 and `--speed-limit 1 --speed-time 2`: the head only, exit 28 after 2.0 s; the head and 100 bytes, exit 28 after 8.1 s.
- tests (`tests/browser/net.rs`, the window by default and with `DWELLER_PROCESS=single`, `DWELLER_STALL_SECONDS=2`, `DWELLER_CONSOLE=1`):
  - `stall_limit_lets_a_slow_response_load`: `net/stall_trickle.html`, a script sent in 8 parts, one every 500 ms (`/drip/500/8`), 4 s, twice the limit: it loads and the console has no error.
  - `stall_limit_fails_a_stalled_response`: `net/stall_head.html`, a script whose server sends the head and then nothing (`/head-hang`): it fails, the console has `[error] Failed to load script: <url>` as for any failed script, and the server measured 1.5 s to 10 s from the request to the browser's close (`/hang-took`; the server's request log had the requests 2.07 to 2.09 s apart). Before, it failed at the 30 s total limit, after the window had ended at its 3000 frames.
  - the server times the stall, not the test: on this Mac the first run of a freshly built binary, with a renderer per site, sent its first request 14 s after the launch (in both tests, in the default arm that runs first; the `single` arms after it had no such wait). So the window's run time is no measure of the limit.
  - test server (`browser/tests/server.py`): `/drip/MS/N?KEY`, `/head-hang?KEY` and `/hang-took?KEY`.
- default N, measured once (the window, `DWELLER_PROCESS=single`, a script sent in 35 parts, one every second, `/drip/1000/35`): this branch loads it in 35.3 s. origin/main's binary (947e1268) cuts it: `[error] Failed to load script: …/drip/1000/35?long` after 90.2 s, 3 times the 30 s limit (see Left).

## Left

- a script that fails is fetched 3 times in the window, one request after the other. The test server logged 3 requests for `/head-hang?stall`, 2.07 s apart, by default and with `DWELLER_PROCESS=single`. A failed early load is not kept for the fetch that follows ("failures are left to the fetch that follows", `prefetch` in `net/multi.aye`). So a stalled script holds the parser for 3 times the stall limit, 90 s by default. Before, it was 3 times the 30 s total limit, as the 90.2 s above shows. Chrome uses the failed preload's result and does not send the request again.
