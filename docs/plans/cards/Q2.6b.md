# Q2.6b: a process per site on navigation

- goal: with `DWELLER_PROCESS=tab`, a cross-site navigation of a tab commits in a new renderer and retires the old one; a same-site navigation stays in its renderer. Site = scheme + eTLD+1 (`net.siteOf`), port not part of it. Without the flag nothing changes.
- design:
  - site lock: each `TabProcess` has `site` (`ui/write-site.aye`: `http://a.com`, `https://a.com`, `file:` for every file page; nothing for `data:`, `about:` and other schemes). It is set when the first document response of the renderer is answered (before any byte of it goes to the renderer) and never changes. `--state` prints `renderer-site SITE` and `renderer-pids P1 P2 ...` (the tab's renderers in order, the last is the live one).
  - the decision is made on the final response: the renderer's document fetch goes through the browser's net (`answerFetch`), which follows redirects, so the browser knows the final URL before it sends anything. `takesSwap`: when the final URL's site is not the renderer's lock, the response is kept in the old renderer (`swap_to`) and not sent; the old renderer waits on its fetch and keeps showing the old page. A redirect a.com → b.com → a.com stays in a.com's renderer; a.com → b.com swaps.
  - the swap (`ui/service-speculative.aye`, from `pollTabProcesses`): `startSpeculative` starts a new renderer (`slot.speculative`) locked to the final site, moves the response into it (`primed`), and carries over the document counter (`doc_seq`, so entries of two renderers never look like one document) and push-or-replace of the navigation. After its `hello` it gets its frame buffers first (`giveBuffers`), then `navigateSpeculative` sends `session_history` and `navigate` to the final URL; its document fetch is answered with the kept response (`sendPrimed`), so the network sees the request once (a POST is not sent twice). When it reports `loaded` (Q2.3d's `commitMatches` against the final URL), `commitEntry` records the entry, the old renderer is killed and reaped (`dropTabProcess`: SIGKILL + `waitpid`, then `endTabProcess`), and `slot.process` is the new one. If the new renderer cannot start or dies before its commit, the old renderer's fetch fails (`FetchFail`) and it shows its own load error; the old one is never killed before the new one commits.
  - back, forward, reload and the address bar go the same way: a traversal to an entry of another document is a fresh `navigate` in the current renderer (Q2.6a's `goToEntry`), and its response decides the process. Entries do not store a site: the site is always taken from the response, as Chromium re-checks the SiteInstance at response time.
  - renderer-initiated (links, forms, `location`) and browser-initiated (address bar, back, forward) navigations swap the same way: in Chromium with site-per-process a cross-site top-level navigation always needs another process; the difference is only the BrowsingInstance, and Dweller has no cross-renderer BCG yet.
  - `about:blank` never reaches the browser's net (the engine makes it), so it stays in the current renderer; a `data:` URL from the address bar has no site and stays in the current renderer with an opaque origin (Chromium puts a browser-initiated `data:` in a new opaque process; noted in Left); a top-level `data:` from a page is refused (Q2.6a).
  - the way back to a site is a new renderer (new pid): the old one is retired at the swap, as Chromium's RenderProcessHost exits once it hosts no frame (no bfcache, no spare process here).
- Chromium read: `content/browser/renderer_host/render_frame_host_manager.cc` (`GetFrameHostForNavigation`, `CreateSpeculativeRenderFrameHost`, `CommitPending`: a speculative RFH for a cross-SiteInstance navigation, re-picked when the response's final URL needs another SiteInstance; the current RFH stays until the speculative one commits, a failed navigation leaves it), `content/browser/site_instance_impl.cc` and `content/browser/site_info.cc` (`GetSiteForURL`: scheme + registrable domain with private registries, port dropped; `file:` is one scheme-only site; `about:blank` can be in any SiteInstance; `data:` has its own opaque site), `content/browser/renderer_host/navigation_request.cc` (`OnResponseStarted` selects the final RFH after redirects; redirects are followed in the network service before that).
- files: `browser/ui/{tab-process,start-tab-process,end-tab-process,answer-fetch,poll-tab-processes,tabs,write-tab-process}.aye`, new `browser/ui/{write-site,takes-swap,send-primed,fail-swap,start-speculative,navigate-speculative,service-speculative}.aye`; new `browser/tests/ui/renderer_sites.html`; `tests/browser.rs` (new `window_renderer_sites`; `window_renderer_net` drops every `renderer*` state line when it compares pages).

## Status: done, 2026-11-08

Left:
- Q2.7: the lock is recorded (`tp.site`) but no message is checked against it yet. Requests, cookies and storage already use the browser's record (`tp.top`, `tp.docs`, set from the final URL by `sendFetched`), never the renderer's claim (Q2.4b/d); the gap is that `tp.docs` (frames, popups in the renderer's engine) may be of another site than the lock until OOPIFs (Q2.9), and a renderer may name any of them.
- agent navigations (`agent_acts`) that cross sites still commit in the current renderer (no swap; the lock is not updated).
- `window.open` children and frames live in the renderer's engine: a cross-site swap of the top drops them with the old renderer.
- a browser-initiated `data:` stays in the current renderer (Chromium: a new opaque process).
- no zombie check in the test (the retire path is `dropTabProcess`'s blocking `waitpid`, as Q2.5's sad-tab test checks for kills).
- a network error before the response keeps Q2.6a's behaviour (the current renderer shows its error page); a new renderer that dies before its commit makes the old one show a load error instead of its old page.
- process reuse limits, spare renderers, bfcache: out of scope.
